# 遗留文件说明

本目录下的两个文件是**早期原型的残留**，不参与任何构建，保留仅为历史可追溯。

| 文件 | 状态 | 说明 |
|---|---|---|
| `src/preload.c` | **死文件** | 221 行的早期原型。功能已被 `src/runtime/preload.c`（4600+ 行）完全取代 |
| `src/config.h` | **死文件** | 只被上面的 `src/preload.c` 引用；真正被使用的是 `src/runtime/config.h` |

## 判定依据（实测）

```sh
# 1) 构建脚本与 Makefile 都没有引用它们
$ grep -n 'src/preload\.c\|src/config\.h' BUILD_RUNTIME.sh Makefile
（无输出）

# 2) src/runtime/preload.c 的 #include "config.h" 解析到同目录的
#    src/runtime/config.h（引号形式的头文件优先查当前目录），
#    不是本目录这个
$ grep -n '#include "config.h"' src/runtime/preload.c
41:#include "config.h"
$ ls src/runtime/config.h
src/runtime/config.h        ← 真正生效的那份

# 3) 编译产物里不含本目录文件的任何符号
```

## 为什么不删除

- 这是**源码**而非可执行软件，删除不影响任何功能，但保留成本为零；
- 本项目的一条既定约束是"不删软件"，此处从宽处理；
- 它们记录了早期设计（例如 `get_rootfs()` 只读环境变量、没有 bind/l2s 概念），
  对理解"为什么后来改成现在这样"有一点参考价值。

## ⚠️ 给后来者

**不要**在 `src/preload.c` 里改代码 —— 改那里不会有任何效果（不参与构建）。
本项目的运行时源码是 **`src/runtime/preload.c`**。

这个歧义本身也值得记录：**两个同名文件放在不同目录**，是排查时容易走偏的坑
（红队在做编译单元审计时就因此困惑过）。若将来要清理，删这两个文件即可，
无任何依赖。
