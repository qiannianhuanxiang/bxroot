## 1. 高危缺陷

### H1 —— `launcher.c`：`fprintf` 缺少 2 个实参，用户敲错命令即 SIGSEGV

**基准版本**：`src/launcher/launcher.c` md5 `d64ae6d4b98359fb3a7007b5f969ce82`（旧版 326 行）
**当前状态**：✅ **已在审计过程中被修复**（现为 376-377 行，补上了 `errno, strerror(errno)`）

旧版代码（`launcher.c:322-329`）：

```c
if (cmd[0] == '/') {
    /* 绝对路径：加上 rootfs 前缀 */
    snprintf(resolved_path, sizeof(resolved_path), "%s%s", cfg.rootfs, cmd);
    if (access(resolved_path, F_OK) != 0) {
        fprintf(stderr, "错误: rootfs 内找不到命令 %s (实际路径: %s) errno=%d %s\n", cmd, resolved_path);
        /*              ^^ %s 已用      ^^ %s 已用        ^^ 缺     ^^ 缺      */
        free_config(&cfg);
        return 1;
    }
```

**为什么是缺陷**

格式串声明了 4 个转换（`%s %s %d %s`），实参只有 2 个。aarch64 的变参调用约定下
（`x0`=format，`x1`=`cmd`，`x2`=`resolved_path`，之后从**调用者未初始化的栈/寄存器保护区**取值），
`%d` 会拿到任意 32 位值、`%s` 会拿到任意 64 位值并被当作指针解引用。
`fprintf` 内部对 `%s` 走 `strlen()` → 野指针 → SIGSEGV。

编译器其实早就报了警（这是三件套里唯一被工具抓到的高危项）：

```
$ gcc -fsyntax-only -Wall -Wextra -Wformat=2 -D_GNU_SOURCE src/launcher/launcher.c
src/launcher/launcher.c:326:81: warning: format '%d' expects a matching 'int' argument [-Wformat=]
src/launcher/launcher.c:326:84: warning: format '%s' expects a matching 'char *' argument [-Wformat=]
```

**最小复现（已实测）**

```sh
# 用仓库里未改动的产物 build/libbxroot.so
mkdir -p /tmp/lp/emptyrootfs
/tmp/lp/libbxroot.so -r /tmp/lp/emptyrootfs /nonexistent-cmd-xyz
```
实测输出：
```
EXIT=139            # ← SIGSEGV；stdout/stderr 一个字都没打出来
```
崩溃点之所以"什么都打不出来"，是因为 `fprintf` 在**格式化阶段**就崩了，
连这条错误消息本身都没能落地 —— 现场表现为"静默消失"，极难排查。

**判决实验（证明根因就是缺实参）**

把同一份源码只补上第 3、4 个实参、其余一字不改，重新静态编译：

```sh
sed -i 's|", cmd, resolved_path);|", cmd, resolved_path, errno, strerror(errno));|' launcher_fixed.c
gcc -O2 -static -D_GNU_SOURCE -o libbxroot_fixed.so launcher_fixed.c
/tmp/lp/libbxroot_fixed.so -r /tmp/lp/emptyrootfs /nonexistent-cmd-xyz
```
实测输出：
```
错误: rootfs 内找不到命令 /nonexistent-cmd-xyz (实际路径: /tmp/lp/emptyrootfs/nonexistent-cmd-xyz) errno=2 No such file or directory
EXIT=1              # ← 唯一的差别就是补了实参 = 根因确证
```

**触发条件**：`-r <rootfs>` 加一个 rootfs 里不存在的绝对路径命令。
这是**最常见的用户错误**（写错路径、rootfs 没挂上、路径多打一个字符），
不是恶意构造。

**建议修法**（当前修复已采用同样的做法，保留在此供后来者理解）：

```c
fprintf(stderr, "错误: rootfs 内找不到命令 %s (实际路径: %s) errno=%d %s\n",
        cmd, resolved_path, errno, strerror(errno));
```

**根因预防**：`BUILD_RUNTIME.sh` 的 `CFLAGS` 是 `-w`（吃掉全部警告），
`Makefile` 的 `COMMON_CFLAGS` 也从没有 `-Wformat=2`。
本条缺陷之所以能存活到"用户可见的崩溃"，就是因为格式化字符串检查被全局静音了。
建议至少在 `Makefile` 里加回 `-Wall -Wextra -Wformat=2`（不要 `-w`）。

### H2 —— `launcher.c`：64 KiB 堆缓冲无界 `strcat`，16 条长 bind 即堆溢出

**基准版本**：`src/launcher/launcher.c` md5 `d64ae6d4b98359fb3a7007b5f969ce82`（旧版 251-259 行）
**当前状态**：✅ **已在审计过程中被修复**（现为 249-305 行，改为先精确计算 `need` 再 `malloc`，
并用 `stpcpy` 写入，另加 1 MiB 防御性上限）

旧版代码（`launcher.c:249-263`）：

```c
if (cfg.bind_count > 0) {
    char *bind_env = malloc(65536);          /* 固定 65536，不校验实际需要多少 */
    if (bind_env) {
        bind_env[0] = '\0';
        for (int i = 0; i < cfg.bind_count; i++) {
            if (i > 0) strcat(bind_env, ";");
            strcat(bind_env, cfg.binds[i * 2]);      /* ← 无长度检查 */
            strcat(bind_env, ":");
            strcat(bind_env, cfg.binds[i * 2 + 1]);  /* ← 无长度检查 */
        }
        setenv("BXROOT_BINDS", bind_env, 1);
        free(bind_env);
    }
}
```

**为什么是缺陷**

`-b` 的校验**只有条数**（`launcher.c:127`：`if (cfg->bind_count >= MAX_BINDS)`，`MAX_BINDS == 16`），
**完全没有校验每条路径的长度**。而 `argv` 里单个参数的长度只受内核 `ARG_MAX`（~2 MiB）限制。
于是 16 条 × 约 3 KB 的路径就能超过 65536 字节，`strcat` 直接越界写堆。

**最小复现（已实测）**

```sh
A=$(python3 -c "print('a'*3000)")
ARGS=""; for i in $(seq 1 16); do ARGS="$ARGS -b /$A/$i:/$A/$i"; done
/tmp/lp/libbxroot.so -r /tmp/lp/emptyrootfs $ARGS /bin/true
```
实测输出（带 `_FORTIFY_SOURCE` 的静态构建）：
```
*** buffer overflow detected ***: terminated
EXIT=134            # SIGABRT（__strcat_chk 命中）
```
同一命令在更长路径（每侧 6000 字节）下同样 `EXIT=139`。

**关键点**：`_FORTIFY_SOURCE` 只是在**本机这个构建**里把静默越界变成了可见的 abort。
不带 FORTIFY 的构建（`BUILD_RUNTIME.sh` 的 `CFLAGS` 里没有 `-D_FORTIFY_SOURCE`）
就是**静默堆越界写** —— 而且溢出的是 `bind_env` 之后紧邻的堆块，
破坏内容取决于分配器布局，症状不可预测。

**触发条件**：bind 条数完全合法（≤16），只是路径较长。
不是"用户故意使坏"，是"多挂几个长路径的目录"。

**建议修法**（当前修复已采用，此处保留供理解）：

```c
size_t need = 1;
for (int i = 0; i < cfg.bind_count; i++) {
    const char *a = cfg.binds[i * 2], *b = cfg.binds[i * 2 + 1];
    if (a == NULL || b == NULL) continue;
    need += strlen(a) + 1 + strlen(b);
    if (i > 0) need += 1;
    if (need > (size_t)1 << 20) { /* 报错退出 */ }
}
char *bind_env = malloc(need);   /* 精确长度 */
/* 用 stpcpy 顺序写入，不再 strcat */
```

### H3 —— `syscall_guard.c`：64 KiB 环形池的分配是**无锁、非原子、非 TLS** 的

**位置**：`src/runtime/syscall_guard.c:361-372`

```c
#define SG_POOL_SIZE (64 * 1024)
static char sg_pool[SG_POOL_SIZE];
static unsigned int sg_pool_off;

char *tbuf;
size_t need = 4096;

/* 池内按 256 字节对齐切块，避免回绕时切碎 */
if (sg_pool_off + need > SG_POOL_SIZE)
    sg_pool_off = 0;
tbuf = sg_pool + sg_pool_off;
sg_pool_off += need;                       /* ← 非原子的读-改-写 */
```

**为什么是缺陷**

这三行是一段典型的 **非原子 read-modify-write**。`syscall()` 是本层导出的全局符号，
**任何线程**调用 `syscall(291, ...)` / `syscall(79, ...)` 等都会进到这段代码。
两个线程可以：

1. 都读到 `sg_pool_off == N`；
2. 都算出 `tbuf == sg_pool + N`；
3. 都调 `bxroot_translate_path(pth, tbuf, need)` —— **写同一块缓冲**。

后果与 §4 记录的那条历史判决实验完全同类（该项目自己在 `syscall_guard.c:342-350`
记录过：**"复用缓冲会崩、每次 malloc 不崩 → 说明调用方会在内核返回后继续持有该指针"**）。
也就是说，这里被踩坏的不是"我们自己的临时变量"，而是**客户（例如 node/libuv）
在 `svc` 返回后仍在使用的路径指针**。症状是随机路径被翻译成错误的长度/内容，
或者 `strlen` 读到 `-1`（README 里 `dsh web` 崩溃的原始现场就是这个形状）。

**为什么现有注释挡不住它**

`syscall_guard.c:286-295` 的注释解释了"为什么必须是 thread_local"
（避免 A 线程翻译时 B 线程被误判为重入），并给出结论：**"用全局标志的话：
A 线程正在翻译时，B 线程的翻译会被误判为重入而跳过"**。
但最终落地的实现里**既没有 thread_local，也没有那把"全局标志"** ——
守卫只存在于注释中。`grep` 全文，`dgl`/`in_syscall`/`reentrancy` 这类变量一个都没有：

```
$ grep -n "d291\|in_syscall\|reentran\|guard" src/runtime/syscall_guard.c
250:            log_num("[bxroot] syscall_guard: 拦截 ", number, " -> ENOSYS\n");
275:         *     static _Thread_local int d291;
279:         * **但那个结论是错的**：`d291` 只增不减，所以顺序调用也会
```
（第 275/279 行都在**注释**里。）

**判决实验（确定性，不依赖调度运气）**

`/tmp/pool2.c` 精确复刻这三行，然后按调度器**允许**的交错执行：

```c
sg_pool_off = 3*4096;
unsigned int snapshot = sg_pool_off;   /* 两个线程都读到这个值 */
char *a = sg_pool + snapshot;          /* 线程 A 得到的槽位 */
char *b = sg_pool + snapshot;          /* 线程 B 得到的槽位 */
```
实测：
```
A's slot = 12288
B's slot = 12288
same buffer? YES -> concurrent statx() calls overwrite each other
```

另一件必须指出的：**第 368 行的注释与代码不符**。
注释写"池内按 **256** 字节对齐切块"，但 `need = 4096`，实际步长是 **4096**。
注释描述的是一版从未落地的实现。

**什么在"保护"它（以及为什么不算保护）**

唯一挡在竞态前面的是"这 3 条语句恰好没有跨线程让出点"——
没有锁、没有原子操作、没有 `_Thread_local`，**没有任何代码层面的保证**。
`-O2` 下编译器完全可以把 `sg_pool_off` 的读-改-写重排到 `bxroot_translate_path()`
调用之后（该函数不在同一 TU，编译器看不到它对 `sg_pool_off` 的依赖，
而 `sg_pool` / `sg_pool_off` 都是文件作用域 `static`，
编译器还知道 `sg_pool + sg_pool_off` 的地址不逃逸给 `bxroot_translate_path` 之外……）。
只要它一重排，或者一次中断/信号落在两条语句之间，竞态立即成立。

**建议修法**（按优先级）

1. **首选**：把槽位索引改成真正的 per-thread 状态。项目已确认
   `_Thread_local` 在本机自研加载器下不可用，所以用
   `pthread_key_t`（构造函数早期不可用的顾虑可解：惰性创建 + 失败时回落到全局锁），
   或用 `__atomic_fetch_add(&sg_pool_off, need, __ATOMIC_RELAXED)` 做原子取槽。
   注意**仅**把 `sg_pool_off` 原子化只能保证"两个线程拿到不同的槽"，
   仍然解决不了"32 KB 池在多线程下回绕过快"的问题，所以还要：
2. **同时**把 `SG_POOL_SIZE` 从 64 KiB 提高（或改成环形链表 + 每线程槽位），
   使回绕周期与"调用方持有时长"匹配；
3. 给"池被回绕覆写"加一个**可观测的计数器**（复用一个槽 = 记一次），
   让这个故障从"随机崩溃"变成"可测量的告警"。

### H4 —— `proc.c`：`px_envout env;` 未初始化，失败路径对栈垃圾调 `px_free()`

**位置**：三处代码联合构成缺陷

1. `src/proc/proc.c:2568` —— 局部变量声明，**没有初始化**：
```c
static int px_do_execve(const char *path, char *const argv[],
                        char *const envp[], const char *path_env,
                        int use_search)
{
    char host[PX_PATH_MAX];
    char guest[PX_PATH_MAX];
    px_envout env;                 /* ← 未初始化；px_envout 含 buf/v/offs/alloc 等指针 */
    px_argv_plan plan;
    char *vec[PX_ARGV_MAX + 1];
```
（`px_envout` 定义见 `proc.h:336` 附近，含 `char *buf; char **v; size_t *offs; ... const px_alloc *alloc;`）

2. `src/proc/proc.c:2303-2321` —— `px_runtime_build_env()` 的**四条提前返回**：
```c
int px_runtime_build_env(char *const envp[], px_envout *out)
{
    px_env_kv forced[4];
    px_envpolicy pol;
    int nf;

    if (out == NULL)  { errno = EINVAL; return -1; }
    if (g_rt_ready && !g_rt_cfg.inject) {
        return -1;      /* 用户显式关掉了 */          /* ← 不写 *out */
    }
    if (!g_rt_ready || !g_rt_cfg.have_preload) {
        /* 没有自身路径 → 注入无意义 */
        return -1;                                    /* ← 不写 *out */
    }
    nf = px_build_forced(&g_rt_cfg, forced, 4);
    if (nf <= 0) {
        return -1;                                    /* ← 不写 *out */
    }
```
注意：**函数只在成功时才写 `*out`**（经由 `px_env_build`）。这是一条隐含契约，
但**没有写在 `proc.h` 的声明处**（`proc.h:874` 的注释只说
"返回 PX_OK / PX_ENOMEM / PX_ENOSPC / PX_EINVAL"，没有说
"失败时 `*out` 保持原样 / 还是被清零"）。

3. `src/proc/proc.c:2657-2661` —— 失败路径上的清理：
```c
    px_plan_dispose(&plan);
    if (env.v != NULL) {           /* ← 读一个从未被初始化的指针成员 */
        px_env_dispose(&env);
    }
```
`px_env_dispose`（`proc.c:633-656`）内部做的是：
```c
if (out->buf  != NULL) px_free(out->alloc, out->buf);
if (out->v    != NULL) px_free(out->alloc, out->v);
if (out->offs != NULL) px_free(out->alloc, out->offs);
```

**为什么是缺陷**

`env` 是**栈上未初始化的自动变量**。3 条真实的失败路径
（`BXROOT_INJECT_ENV=0`、`g_rt_ready == 0`、`have_preload == 0`）
**一个字节都不写 `*out`**，所以 `env` 保持它进入函数时的栈残留内容。
随后第 2658 行 `if (env.v != NULL)` 去读这个残留值：

- 残留值恰好为 NULL → 侥幸跳过（当前很可能就是这种情形）；
- 残留值非 NULL → `px_env_dispose` 对**野指针**调 `px_free()`。

`px_free` 在 `alloc == NULL` 时走 malloc 路径（`px_free(NULL, p)` → `free(p)`），
于是就是一次对任意地址的 `free()` —— 堆元数据被破坏，
症状是**在完全无关的地方崩**（本项目自己在 `crash.c:23-24` 记录过
"fakeroot 测试里的 double free 崩在 tcache 内部，堆栈完全看不出根因"，
正是这一类的现场）。

**判决实验（严格证明 `*out` 在失败时不被触碰）**

`/tmp/uv2.c`：把 `px_envout` 整体填成哨兵 `0xAB`，
按 `proc.c:2312-2321` 的形状复刻三条失败路径，逐字节比较调用前后的 `*out`：

```
case 1 (inject=0): rc=-1  *out modified? NO
        out.v = 0xabababababababab  ->  `if (env.v != NULL)` guard PASSES on garbage
case 2 (!ready)  : rc=-1  *out modified? NO
case 3 (!preload): rc=-1  *out modified? NO
```
结论：**三条失败路径都让 `*out` 完全保持原样**。
`0xabababababababab != NULL`，所以那个守卫在真实残留值非 NULL 时**必然放行**。

**触发条件（三条都是常规配置，不是边缘情况）**

| 触发路径 | 如何进入 | 说明 |
|---|---|---|
| `g_rt_ready && !g_rt_cfg.inject` | 设 `BXROOT_INJECT_ENV=0` | 用户显式关闭 envp 注入 |
| `!g_rt_ready` | `px_runtime_init()` 尚未跑过就发生 exec | 早期/异常初始化顺序 |
| `!g_rt_cfg.have_preload` | `px_cfg_merge_preload()` 判不出自身库路径 | 代码自己的注释就把它当常规分支："连自己是谁都不知道 → 整体禁用注入" |

即：**只要 envp 注入被关掉或不可用，每一次 exec 失败都会走一遍这个清理**。
`exec` 失败是高频事件（"容器里跑一个不存在的命令几千次"——
项目自己在 `proc.c:2650-2654` 就是用这个场景论证 `px_plan_dispose` 的必要性）。

**为什么工具没抓到**

`-fanalyzer` 没有报，因为 `px_runtime_build_env` 与 `px_do_execve` 在同一个 TU 里
但分析器没有把"`*out` 可能不被写"这条路径与后面的 `env.v` 读关联起来
（`px_env_build` 内部有 `goto fail; px_env_dispose(out);` 的**成功写 + 失败写**
混合路径，把 `*out` 的初始化状态判定复杂化了）。
**这类"失败时是否写 out 参数"的契约问题，静态分析器系统性地不可靠。**

**建议修法（两处，任一即可断根；建议都做）**

```c
/* 修法 A（必做，一行）：在声明处初始化 —— 与同文件 proc.c:1946 附近
 * "px_envout 用 offsets 而不是指针" 的谨慎风格一致 */
px_envout env;
memset(&env, 0, sizeof(env));       /* 或 px_envout env = {0}; */

/* 修法 B（推荐，把契约显式化）：让失败路径也保证 *out 是"已释放"状态，
 * 这样调用方的 if (env.v != NULL) 就永远正确 */
int px_runtime_build_env(char *const envp[], px_envout *out)
{
    if (out == NULL) { errno = EINVAL; return -1; }
    memset(out, 0, sizeof(*out));    /* ← 先归零，任何返回路径都安全 */
    ...
}
```
并在 `proc.h:874` 的声明注释里**明确写下契约**：
"失败时 `*out` 被清零（可安全传给 `px_env_dispose`）"。
这类"out 参数在失败时的状态"是 C 接口最容易出错的一处，
本项目已经有 `px_bump_free` / `px_env_dispose` 的"NULL 安全、幂等"约定
（`proc.h:355`），把 `px_runtime_build_env` 纳入同一约定即可。

> **同类扫描（已逐个核实：五处同源，全部未初始化）**
>
> ```

## 2. 中危缺陷

### M0 —— `bind()`/`connect()`：`is_unix_path_sockaddr` **先解引用 `sa_family`、后校验 `addrlen`**

**位置**：`src/runtime/preload.c:3953-3962`

```c
static int is_unix_path_sockaddr(const struct sockaddr *addr, socklen_t len,
                                 const char **out_path, size_t *out_off)
{
    const struct sockaddr_un *un;

    if (addr == NULL || addr->sa_family != AF_UNIX)   /* ← 先读 2 字节 */
        return 0;
    /* 至少要能装下 sun_family + 1 字节路径 */
    if (len <= (socklen_t)offsetof(struct sockaddr_un, sun_path) + 1)
        return 0;                                     /* ← 后校验长度 */
```

**为什么是缺陷**

`len` 是调用方（客户程序）给的 `addrlen`，它**不受我们控制**。
这个函数在校验 `len` 之前就读了 `addr->sa_family`（`sa_family_t` = `unsigned short`，
2 字节）。若客户传一个"只有 1 个可读字节、且该字节位于页尾"的缓冲，
这次 2 字节读会**跨进相邻的不可读页** → SIGSEGV。

**与内核的对照（这就是判据）**

我实测了内核对同一形态的处理（`/tmp/nulls.c`）：

```
faccessat(AT_FDCWD, NULL, F_OK)        = -1 errno=14 (Bad address)
fchmodat(AT_FDCWD, NULL, 0644, 0)      = -1 errno=14 (Bad address)
newfstatat(AT_FDCWD, NULL, ...)        = -1 errno=14 (Bad address)
openat(AT_FDCWD, NULL, O_RDONLY)       = -1 errno=14 (Bad address)
statx(AT_FDCWD, NULL, AT_EMPTY_PATH, ..) = -1 errno=14 (Bad address)
```

内核的通行做法是**先校验长度、再解引用**：
`SYSCALL_DEFINE3(bind, ...)` 经 `move_addr_to_kernel()` →
`if (ulen < sizeof(sa_family_t)) return -EINVAL;` —— **长度检查在拷贝之前**。
也就是说：`bind(fd, ptr, 1)` 在原生 Linux 上返回 `EINVAL`，
在 bxroot 下则可能 SIGSEGV。这是**与内核的语义分歧**，不只是理论风险。

**判决实验（已实测跨页读会真的 SIGSEGV）**

`/tmp/sg2.c`：`mmap` 2 页 → 第 2 页 `PROT_NONE` → 从"第 1 页最后一个字节"
开始读 2 字节：

```
reading 2 bytes starting at last byte of readable page...
EXIT=42
[stderr] SIGSEGV: read crossed into guard page
```
（`/tmp/sg.c` 里我同时写了"内核式顺序"与"bxroot 式顺序"两个函数，
前者不读越界，后者会。）

**可达性如实说明（影响定级）**

我**没有**在真实 bxroot 下构造出 `bind()` 走到这条路径的完整用例 ——
需要客户程序故意传 `addrlen < 2` 且缓冲恰好贴着页边界。
正常程序不会这么做（它们传 `sizeof(struct sockaddr_un)`），
所以这是"恶意/畸形客户输入"才触发的路径，定级**中危**。
但注意 `bind`/`connect` 是**客户可任意调用**的公共符号，
而本层的定位是"替客户做路径翻译"，对畸形输入应当与内核同样稳健。

**建议修法**（改两行的顺序，成本近零）

```c
static int is_unix_path_sockaddr(const struct sockaddr *addr, socklen_t len,
                                 const char **out_path, size_t *out_off)
{
    const struct sockaddr_un *un;

    if (addr == NULL)
        return 0;
    /* 先校验长度，再解引用 —— 与内核 move_addr_to_kernel 的顺序一致。
     * 否则 addrlen < 2 时这里会读越界（客户缓冲贴着页尾就是 SIGSEGV）。 */
    if (len < (socklen_t)sizeof(sa_family_t))
        return 0;
    if (addr->sa_family != AF_UNIX)
        return 0;
    if (len <= (socklen_t)offsetof(struct sockaddr_un, sun_path) + 1)
        return 0;
    ...
```

### M1 —— `path_arg_index()` 的 `case 1024` 在 aarch64 上不存在（任务 §E 重点）

**位置**：`src/runtime/syscall_guard.c:221`

```c
case 1024: return 0;   /* open(path, flags, mode) —— 已废弃仍在用 */
```

**核对结论：编号错，且注释错。**

依据 `asm-generic/unistd.h`（aarch64 用的就是这一套编号）：

```
$ grep -n "NR_open\b" /usr/include/asm-generic/unistd.h
（无输出 —— __NR_open 在 asm-generic 上根本没有定义）
```

本机实测（`/tmp/sc1024.c`）：

```
syscall(1024, "/etc/hostname", O_RDONLY) = -1 errno=38 (Function not implemented)
syscall(56=openat, AT_FDCWD, "/etc/hostname", O_RDONLY) = 6 errno=0 (Success)
syscall(2, "/etc/hostname", O_RDONLY)    = -1 errno=22 (Invalid argument)
```

即：`1024` 是 **i386 的 `__NR_open`**（`arch/x86/entry/syscalls/syscall_32.tbl`），
在 aarch64 上是"空洞"编号。而 `openat` 的原生编号 `56` 已由 `case 56` 正确覆盖。

**是否构成内存缺陷：否。** aarch64 内核（`arch/arm64/kernel/sys.c`）的
`invoke_syscall()` 会在派发前用 `if (scno > __NR_syscalls) return -ENOSYS;` 挡掉，
`do_el0_svc` 根本不会走到 `sys_call_table[1024]`，因此 `path_arg_index(1024)`
永远不会被调用，`return 0` 也就永远不会把 `a0` 当指针解引用。
**但它是危险的知识陷阱**：注释写着"open(path,...)——已废弃仍在用"，
后来者会据此以为"1024 这条路是活的、a0 是路径"，在 aarch64 上做出错误推断。
建议**直接删掉这个 case**，或把注释改为
`/* 1024 = i386 的 __NR_open；aarch64 上不存在此编号，此行是死代码 */`。

> 附带一条：`case 221: return 0;`（`execve(path, argv, envp)`，路径在 a0）—— **正确**。
> 逐项核对表见 §5。

### M2 —— `__getcwd_chk` 丢弃 `buflen`，静默关掉 FORTIFY 保护

**位置**：`src/runtime/preload.c:2920-2923`

```c
char *__getcwd_chk(char *buf, size_t size, size_t buflen) {
    /* 边界检查版 getcwd；转发后复用 getcwd 的反向翻译逻辑 */
    (void)buflen;                       /* ← 丢掉编译期已知的目标大小 */
    return getcwd(buf, size);
}
```

**为什么是缺陷**

`__getcwd_chk(buf, size, buflen)` 的第 3 个参数是 FORTIFY 在**编译期**得知的
`sizeof(buf)`。它的唯一职责就是"若调用方要写的 `size` 超过实际缓冲 `buflen`，
就中止而不是写溢出"。这里把它 `(void)` 掉，等价于**把 FORTIFY 的这道检查关掉**，
而调用方（一个用 `_FORTIFY_SOURCE` 编译过的客户程序）**仍然以为自己受保护**。

对照实测（`/tmp/chk2.c`，直接链接 glibc 的真 `__getcwd_chk`）：

```
calling __getcwd_chk(buf, 4096, 8)        # buf 只有 8 字节
```
→ 未触发 `__chk_fail`，但走的是"安全的失败"路径（实测返回 `NULL` + `ERANGE`，
绝不写满 8 字节）。而 bxroot 的钩子把 `size=4096` 原样交给真 `getcwd()`，
写满客户那个 8 字节栈对象 —— 栈溢出。

**这与本文件自己写下的规则直接矛盾**。`preload.c` 的 `__readlink_chk` 钩子（现约 1690-1695 行）的注释写着：

> 多出的第 4 个参数是编译期已知的目标缓冲区大小，用于边界检查。
> 转发时必须原样传下去 —— 丢掉它等于让 FORTIFY 失效（安全检查被绕过），
> **那比不 hook 更糟：程序以为自己受保护，实际没有。**

`__readlink_chk` / `__readlinkat_chk` / `__realpath_chk` 都老老实实把 `buflen` 传下去了，
**只有 `__getcwd_chk` 违反了这条自定规则**。

**最小复现思路**

编译一个开了 `_FORTIFY_SOURCE=2` 的客户程序：

```c
char small[8];
getcwd(small, sizeof(small) * 512);   /* 触发 __getcwd_chk(small, 4096, 8) */
```
- 原生 glibc：安全（`__chk_fail` 或 `ERANGE`，实测不越界）；
- 经 bxroot：`buflen` 被丢弃 → 真 `getcwd` 按 `size=4096` 写进 8 字节栈对象。

**建议修法**

```c
char *__getcwd_chk(char *buf, size_t size, size_t buflen) {
    static char *(*fn)(char *, size_t, size_t) = NULL;
    if (fn == NULL)
        fn = (char *(*)(char *, size_t, size_t))dlsym(RTLD_NEXT, "__getcwd_chk");
    if (fn == NULL) { errno = ENOSYS; return NULL; }
    /* 不能简单回落 getcwd —— 那会绕过 FORTIFY。
     * 需要保留反向翻译，同时把 buflen 语义交给真实实现：
     * 真 __getcwd_chk 会自己调用 getcwd 并把结果交给同一段反向翻译，    */
    ...
}
```
最保守且正确的做法是：**先按 `buflen` 做一次自检**（`size > buflen` 时
直接 `__chk_fail()` 或返回 `NULL` + `ERANGE`，与 glibc 一致），
再走 `getcwd(buf, size)`。这样至少不再"假装保护"。

### M3 —— `stub-loader.c`：用 `e_phnum` 做 VLA 尺寸 → 64 KiB 栈数组（且整条路径未接线）

**位置**：`src/stub-loader/stub-loader.c:112`

```c
Elf64_Phdr phdr[ehdr.e_phnum];        /* e_phnum 是 Elf64_Half = uint16_t */
if (lseek(fd, ehdr.e_phoff, SEEK_SET) < 0) { close(fd); return NULL; }
if (read(fd, phdr, ehdr.e_phnum * sizeof(Elf64_Phdr)) !=
    ehdr.e_phnum * sizeof(Elf64_Phdr)) { close(fd); return NULL; }
```

**为什么是缺陷**

数组**不在函数开头**声明（前面已经有 `int fd`、`Elf64_Ehdr ehdr` 的初始化），
所以这是一条真正的**变长数组**（VLA）。`e_phnum` 是 16 位字段，
理论上限 65535，× `sizeof(Elf64_Phdr)`(56) ≈ **3.6 MB**；
常见的恶意/损坏 ELF 也能轻易给出 `e_phnum = 1000` → **56 KB 栈数组**。
上面唯一的校验是 `ehdr.e_phentsize < sizeof(Elf64_Phdr)`，
**没有对 `e_phnum` 做任何上限约束**，也没有检查
`e_phoff + e_phnum * e_phentsize <= 文件大小`。

叠加两点使危害升级：

1. 这是**未检查的栈分配** → 栈溢出（aarch64 上直接踩到相邻栈帧/保护页）；
2. 该函数后续用 `malloc(st.st_size)` 后 `read(fd, file_data, st.st_size)`，
   而 `read` 的返回值**未检查**（`stub-loader.c:160-163`），
   短读时 `file_data` 尾部是未初始化堆内存，随后被整个 write 出去 → **信息泄漏**。

**可达性（重要，影响定级）**

`patch_static_elf()` 在本仓库里**没有任何调用者**：

```
$ grep -rn "patch_static_elf" src/ | grep -v "^src/stub-loader/stub-loader.c"
（无输出）
```
`src/runtime/preload.c` 里也没有"检测静态二进制（无 PT_INTERP）→ 调 stub-loader"
的那段逻辑（文件头注释描述的第 1 步不存在）。
`libbxroot-stub-loader.so` 只被 `launcher.c` 探测存在性后
`setenv("BXROOT_STUB_LOADER", ...)`，没有任何代码读这个变量去调用它。

所以当前定级为**中危**：缺陷真实存在、且一旦按设计接线就会变成高危，
但**今天不可达**。建议接线时**同时**修掉：
`if (ehdr.e_phnum > 128) return NULL;` + 改用堆分配 + 校验 phdr 表落在文件内 + 检查 `read` 返回值。

### M4 —— `bridge.c`：未初始化局部变量 + 只查 `< 0`，把栈垃圾当"对端声明的长度"

**位置**：`src/bridge/bridge.c:139-150`

```c
ssize_t nread;                                              /* ← 未初始化 */
if (read(bridge_fd, &nread, sizeof(nread)) < 0) {           /* ← 只挡 < 0 */
    return -1;
}

if (nread > 0 && nread <= (ssize_t)count) {
    if (read(bridge_fd, buf, nread) < 0) {                  /* ← 用 nread 当长度 */
        return -1;
    }
}
return nread;
```

**为什么是缺陷（两条叠加）**

1. **`nread` 未初始化**。`read()` 在"对端已关闭 / EOF"时返回 **0 且不写任何字节**，
   这在 POSIX 里**不是错误**，所以 `read(...) < 0` 这个守卫**挡不住它**。
   此时 `nread` 保持它进入函数时的栈垃圾值。
2. 紧接着 `nread` 被**当作对端声明的长度**使用：参与 `nread <= count` 判断，
   决定是否再 `read(bridge_fd, buf, nread)`，并作为函数返回值交给调用方。
   也就是说，**栈上残留值直接变成了"我认为对端发了多少字节"**。

`nread` 的类型是 `ssize_t`（8 字节），`read()` 返回的也是一次**可能短读**的
字节数 —— 代码同样只比较 `< 0`、**从不校验 `== sizeof(nread)`**。
对端只发 4 字节时，高 4 字节是上一层栈帧的残留，
得到的是一个 `0x????????_????????` 形状的"长度"。

**判决实验（已实测）**

`/tmp/br.c` 精确复刻这 6 行，用 `pipe` 当对端（`memset` 成 `0xEE` 让垃圾可见）：

```
bridge.c:144 `ssize_t nread;` is never initialized, and the guard
is `read(...) < 0` -- which does NOT catch a 0-byte (EOF) return.
  [peer sent 8 bytes then EOF] read() returned 8 (errno=0)
  [peer sent 8 bytes then EOF] nread = 0x4847464544434241
  [peer closed immediately (EOF)] read() returned 0 (errno=0)
  [peer closed immediately (EOF)] nread = 0xeeeeeeeeeeeeeeee  <-- UNCHANGED GARBAGE
  [peer closed immediately (EOF)] -> `if (nread > 0 && nread <= count)` is
                                    evaluated on that garbage
```
即：对端一关闭，`nread` 就是纯栈垃圾，随后被当成"要读多少字节"。

**为什么这是指针/缓冲缺陷（而不只是逻辑错误）**

只要垃圾值恰好落在 `(0, count]` 区间（例如 `0xee...` 被截断参与比较、
或真实栈残留是个小正数），代码就会执行 `read(bridge_fd, buf, nread)`，
**按一个未经验证的长度写调用方的缓冲**。`count` 是调用方声明的缓冲大小，
守卫 `nread <= count` 看似兜住了 —— 但那个 `count` 是**客户自己的**上限，
而垃圾 `nread` 完全可能是个小于 `count` 的正数，
于是走一次语义上无意义的 `read`，把管道里**别的请求的响应**读进 `buf`。
更直接地说：**"信任一个未初始化变量作为长度"本身就是 CWE-457（Use of
Uninitialized Variable）**，后果由栈残留内容决定，不可预测。

**同类问题（同一文件）**

`bridge_open`（`bridge.c:106-113`）：
```c
int result_fd;
if (read(fd, &result_fd, sizeof(result_fd)) < 0) { ... return -1; }
return result_fd;
```
同样的 `int result_fd;` 未初始化 + 只查 `< 0` + 短读不校验 —— 对端在
"新建连接后立即关闭"时，返回的是一个**未初始化的 fd 号**给调用方，
而调用方会拿它去 `read`/`write`。注意 `result_fd` 的**符号**很重要：
垃圾值若为负，调用方会看到"看起来像错误"的 fd；若为正，
则是一个**指向任意 fd 编号**的句柄。

**可达性如实说明**

`bridge_open` / `bridge_read` 在本仓库内**没有调用者**
（`libbxroot-bridge.so` 是个未接线的骨架，见 M3 的同一段分析），
所以今天不可达。但与 M3 不同的是：这里的缺陷**不需要**"按设计接线"
就已经是完整的 CWE-457 + 长度信任问题了，一旦接线就是客户可控的内存写入。
定级**中危**（潜在）。

**建议修法**

```c
ssize_t nread;
ssize_t r = read(bridge_fd, &nread, sizeof(nread));
if (r != (ssize_t)sizeof(nread)) {
    /* r == 0 → 对端关闭；r < 0 → 真错误；0 < r < sizeof → 短读（协议不允许） */
    if (r < 0) return -1;
    errno = EPROTO;              /* 或 EIO */
    return -1;
}
```
即：**初始化 + 严格校验返回值等于期望字节数**。
`bridge_open` 的 `result_fd` 同理。此外 `bridge_read` 的第二次
`read(bridge_fd, buf, nread)` 也应改成读满 `nread` 字节的循环
（一次 `read` 不保证读满请求量，即使管道里有那么多数据）。

### M5 —— `bridge.c`：整结构体 `write(fd, &req, sizeof(req))` —— **今天不泄漏，但极度脆弱**

**位置**：`src/bridge/bridge.c:88-104`（`bridge_open`）、`:122-136`（`bridge_read`）

```c
struct {
    uint32_t cmd;
    uint32_t flags;
    uint32_t mode;
    char path[4096];
} req;

req.cmd = 1; req.flags = flags; req.mode = mode;
strncpy(req.path, path, sizeof(req.path) - 1);
req.path[sizeof(req.path) - 1] = '\0';

if (write(fd, &req, sizeof(req)) < 0) {          /* ← 发整个 4108 字节 */
```

**当前是否真的泄漏：否。** 我把每一条都核对过了：

- `sizeof(req)` = 3×4 + 4096 = **4108**，无尾部 padding（`uint32_t` 4 字节对齐，
  `path` 紧随其后）；
- `strncpy(dst, src, 4095)` 会把 `path[0..4094]` **全部**写满
  （源串之后的字节由 `strncpy` 补 `'\0'` —— 这是 `strncpy` 唯一一次"帮上忙"）；
- `path[4095]` 由下一行显式赋值；
- `cmd`/`flags`/`mode` 逐个赋值。

所以这几个字段**全部有确定值**，`write` 出去的都是确定内容。

**为什么仍要记一笔**：这个正确性**完全依赖 `strncpy` 的填零副作用**，
是"意外的正确"。任何一处小改动都会立刻变成栈信息泄漏：

| 改动 | 后果 |
|---|---|
| `strncpy(..., sizeof-1)` → `strncpy(..., strlen(path))` | `path` 尾部残留栈数据被发出 |
| `strncpy` → `memcpy(req.path, path, strlen(path))` | 同上（更明显） |
| 结构体加一个 `uint16_t port;` 字段 | 出现 2 字节 padding 空洞，未初始化即发出 |
| 改成本地 `char *path` 指针字段 | **直接泄漏一个栈地址**（配合 ASLR 绕过） |

这是经典的 CWE-200 / CWE-908（"发送含填充的结构体"）。
`bridge_read` 的小结构体 `{uint32_t cmd; int32_t fd; size_t count;}` 同样：
今天 3 个字段都被赋值，但 `size_t`(8) 对齐会在 `fd` 后引入 **8 字节 padding**
（`uint32_t cmd` + `int32_t fd` = 8 字节，恰好对齐，**这里没有空洞**）
—— 这个"恰好没有"同样是偶然的。

**建议修法**（两行，成本极低，且把正确性从"偶然"变成"显然"）

```c
memset(&req, 0, sizeof(req));       /* 先整体清零 */
...逐个赋值...
/* 只发生效字节数，而不是整个结构体 */
ssize_t n = write(fd, &req, offsetof(typeof(req), path) + strlen(req.path) + 1);
if (n != (ssize_t)(offsetof(typeof(req), path) + strlen(req.path) + 1)) { ... }
```

## 4. 已核对为安全（避免后人重复检查）

下面每一条我都**追到了具体代码**，并给出了"为什么安全"的理由。

### S1 —— `translate_path()` 的 `strncpy` 用法（`preload.c:301, 314, 336, 405`）

```c
strncpy(out, path, out_size - 1);
out[out_size - 1] = '\0';
```
这是 `strncpy` 的**正确**用法：手动补第 N 个字节保证了 NUL 终止，
且 `out_size >= 1` 时 `out[out_size-1]` 在界内（`translate_path` 第一行
已经用 `out_size == 0` 挡掉了零长）。
调用方一律是 `char translated[MAX_PATH_LEN]; translate_path(x, translated, sizeof(translated))`，
`MAX_PATH_LEN == PATH_MAX*2 == 8192`，尺寸真实。**安全。**

### S2 —— `translate_path()` 的两处 `snprintf` 都检查了返回值（`preload.c:414`、`:368` 附近）

```c
int ret = snprintf(out, out_size, "%s%s", rootfs, path);
if (ret < 0 || (size_t)ret >= out_size) { LOG("path too long: %s", path); return -1; }
```
`(size_t)ret >= out_size` 正是防"截断后用错长度"的正确判据
（注意 `ret` 是 `int`，`snprintf` 返回的是**本来会写多少**，不是实际写了多少）。
bind 分支同样检查了。**安全。**

### S3 —— `/proc/self/exe` 的 6 段 `strncmp`/`strchr` 边界（`preload.c:1500-1514`、`2490-2507`）

```c
} else if (strncmp(path, "/proc/", 6) == 0) {
    const char *p = path + 6;              /* path 至少 6 字节（strncmp 已证） */
    const char *slash = strchr(p, '/');
    if (slash != NULL && strcmp(slash, "/exe") == 0 && slash != p)
```
`path + 6` 是安全的：`strncmp(path, "/proc/", 6) == 0` 成立意味着
`path` 至少有 6 个可读字节（否则 `strncmp` 会先遇到 NUL 而不相等）。
`slash != p` 排除了 `"/proc//exe"`。**安全。**
（`path != NULL` 的判空在 `preload.c:1499` / `2494` 已有。）

### S4 —— `l2s() l2s_join()` 的边界（`l2s.c:199-222`）

```c
if (dlen + (need_slash ? 1u : 0u) + strlen(base) + 1 > outsz) return L2S_ENAMETOOLONG;
memcpy(out, dir == NULL ? "" : dir, dlen);
if (need_slash) out[dlen] = '/';
strcpy(out + dlen + (need_slash ? 1 : 0), base);
```
左侧全部是 `size_t`，**没有 `int` 混入**，不存在负数转巨大的问题。
实测边界：`l2s_join("/", "x", out, 64)` → `"/x"`；
`l2s_join("/aaaa", "xy", out, 8)` → 正确拒绝（`ENAMETOOLONG`，不写越界）。
根目录特判（`dlen==1 && dir[0]=='/'` → `need_slash=0`）正确避免了 `"//x"`。
**安全。**

### S5 —— `l2s_runtime` 的 `probe_fake_link` / `resolve_final` 的 `target[n] = '\0'`

`l2s-runtime.c:192-195`、`:220-223`：
```c
n = g_ops->readlink(path, target, sizeof(target) - 1);   /* 留 1 字节 */
if (n <= 0) return 0;
target[n] = '\0';                                        /* n <= sizeof-1，界内 */
```
`readlink` 的返回 `n` 最多是 `sizeof(target)-1`（因为第三个参数就传了 `sizeof-1`），
所以 `target[n]` 最大写到 `target[sizeof-1]`。**安全。**
（本项目历史上在官方实现里踩过 issue #22 的同款越界读 —— 这里是对的。）

### S6 —— `readlink`/`readlinkat` 的"不补 NUL"**不是**缺陷（撤回一条初期判断）

我最初把 `preload.c:2518-2525` 记为"未终止缓冲"缺陷，核对 `man 2 readlink` 后**撤回**：

> `readlink()` does not append a null byte... `buf` will not be null-terminated.

内核本身在缓冲被填满时也不写 NUL。bxroot 的 `memcpy(buf, guest_exe, len); return len;`
（`len` 已 clamp 到 `buf_size`）与内核语义**逐字一致**，而且代码里有长注释
解释了"不能好心多写一个字节（`buf_size == len` 时多写就是溢出）"。
这是**正确的**实现。真正会越界的责任在调用方 —— 违背 `readlink` 契约去
`strlen(buf)` 的客户程序，在原生 Linux 上同样会越界。
**结论：不是缺陷。**

### S7 —— `is_unix_path_sockaddr` 的长度运算不会下溢（`preload.c:3961-3970`）

```c
if (len <= (socklen_t)offsetof(struct sockaddr_un, sun_path) + 1) return 0;
...
memchr(un->sun_path, '\0', (size_t)len - offsetof(struct sockaddr_un, sun_path));
```
`offsetof(...) == 2`（`sun_family` 在 aarch64 上是 2 字节），
上面的早退保证进入 `memchr` 时 `len >= 4`，所以 `(size_t)len - 2 >= 2`，
**不会下溢成巨大的 `size_t`**。`socklen_t` 是 `unsigned int`，
`len` 为 0 时走早退分支。**安全。**
（唯一的瑕疵是**校验顺序**，见 M0 —— 那是"先解引用后校验"，不是算术问题。）

### S8 —— `bind()`/`connect()` 的目标缓冲尺寸检查（`preload.c` 的 `bind()` 目标缓冲检查，现约 3995-4015 行）

```c
char buf[sizeof(struct sockaddr_un) + MAX_PATH_LEN];
if (off + tl + 1 > sizeof(copy->sun_path)) { errno = ENAMETOOLONG; return -1; }
if (off + tl + 1 > sizeof(buf))            { errno = ENAMETOOLONG; return -1; }
memset(buf, 0, sizeof(buf));
memcpy(buf, addr, off);
memcpy(buf + off, translated, tl + 1);
```
两个上界都查了，且 `sizeof(buf)` 远大于 `sizeof(copy->sun_path)`，
`memcpy(buf, addr, off)` 只拷贝 2 字节（`off == offsetof(...) == 2`）。
`translated` 一定以 NUL 结尾（`translate_path` 保证），所以 `tl + 1` 正确。
**安全。**

### S9 —— `fakeroot_getgroups()` / `preload.c getgroups()` 的边界

`fakeroot.h:182` `gid_t groups[FR_NGROUPS_MAX]`（64），
`fakeroot.c:1688` `if (n > (size_t)FR_NGROUPS_MAX) return FR_EINVAL;`
—— 写入循环前就挡住了。`preload.c:3435-3445` 的钩子
`if (size < n) { errno = EINVAL; return -1; }` 也挡住了客户缓冲过小的情况。
`n = fs->ngroups` 只可能由 `fakeroot_setgroups` 写入，已被 clamp 到 ≤64。**安全。**

### S10 —— `fakeroot_map` 的所有权契约（**逐条追过，正确**）

这是 fakeroot 层最容易出错的地方（堆键的所有权转移），我把全部 7 条路径追完了：

- `fakeroot_key_path()`（`fakeroot.c:327-350`）`malloc(len+1)` + `memcpy` **深拷贝**，
  **不持有调用方指针** —— 这点最关键，因为钩子传进来的路径是客户栈上的。
  长度先判（`if (len >= FR_PATH_MAX) return FR_ENAMETOOLONG;`）再分配。
- `fakeroot_map_put()`（`fakeroot.c` 中段）**按约定接管键的所有权**，
  并且**每一条失败路径都 `fakeroot_key_dispose(&k)`**：
  `m == NULL / slots == NULL / rec == NULL`、`m->disabled`、
  `fr_map_compact` 失败、`idx == SIZE_MAX`（表满）—— 四处全部释放，**无泄漏**。
- **覆盖路径正确**：`if (found) { fakeroot_key_dispose(&m->slots[idx].key); m->slots[idx].key = k; }`
  —— 先释放旧键再转移新键，**既不泄漏也不 double free**。
- `fr_map_compact()`（`fakeroot.c:448-499`）所有权转移后把源槽位显式置为
  `FR_SLOT_EMPTY` 并把 `key.kind` 重置，避免后面 `free(old_slots)` 造成二次释放；
  回滚路径（`idx == SIZE_MAX`）先 `free(new_slots)` 再恢复 `m->slots = old_slots`
  并重算 `count`/`tombs`，**无 UAF、无泄漏**。
- `fr_slot_release()` 只在 `FR_SLOT_LIVE` 时 `fakeroot_key_dispose`，
  避免对墓碑重复释放。
- `fakeroot_map_get()`（只读）**不释放、不转移**，`*out = m->slots[idx].rec`
  是**值拷贝**（`fr_record` 里没有指针成员），不会把内部指针漏给调用方。
- `fakeroot_map_destroy()` 遍历 `LIVE` 槽位释放键，再释放 `slots` 和 `m`。

**结论：`fakeroot.c` 的堆所有权管理是正确的**，没有发现 A/B/G 类缺陷。
（这也是为什么 `-fanalyzer` 在这里一句话都没报 —— 它确实没问题。）


内核的错误区间是 `[-4095, -1]`，`-4096` 不是错误。边界**正确**
（这是 `IS_ERR_VALUE` 宏的精确展开）。

### S12 —— `syscall_guard.c` 的 `path_arg_index()` 中 8 个**正确**条目

`291/79/78/48/56/35/34` 全部 `return 1`（a1 是路径）、`221` 是 `return 0`（a0 是路径）。

### S13 —— `crash.c` 的信号处理器不用非异步信号安全函数

`crash.c` 全部输出走自写的 `cw_write`/`cw_puts`/`cw_hex`/`cw_dec`（只用 `write(2)`），

（`cw_dump_window`/`cw_dump_fp_chain` 会解引用任意地址 —— 这是**刻意的**设计

### S14 —— `preload.c` 中 `l2s_rt_patch_stat((struct stat *)buf, p)` 的 `stat64` 强转

9 处把 `struct stat64 *` 强转成 `struct stat *` 传给 `l2s_rt_patch_stat`。
本机实测（`/tmp/st.c`）：
```
sizeof(struct stat) = 128   sizeof(struct stat64) = 128
offsetof st_nlink: stat=20  stat64=20
offsetof st_mode : stat=16  stat64=16
```
aarch64 上 `struct stat` 与 `struct stat64` **布局完全相同**，该函数只读写
`st_nlink` / `st_mode` 两个字段，偏移一致。**安全。**
（可移植性上仍是隐患 —— 若将来支持 32 位平台需重新核对，但本平台无关。）

### S15 —— `preload.c` 的 `getpwuid` 静态返回（A 类重点核查）

`preload.c:3312-3347`：
```c
static char name_buf[32];
static char dir_buf[8] = "/root";
static char shell_buf[16] = "/bin/sh";
static struct passwd fake;
...
memcpy(name_buf, "root", 5);
fake.pw_name = name_buf; ... return &fake;
```
这是**返回 `static` 缓冲**，形式上命中 A 类。但：
1. `getpwuid(3)` 的**契约本身就是**"返回指向静态存储的指针，
   下次调用会覆写"（POSIX 明确如此），调用方不该保存它；
2. `name_buf` 的内容是常量 `"root"`，**每次调用写进去的字节完全相同**，
   即使被覆写也不会产生"读到别人的数据"；
3. `memcpy(name_buf, "root", 5)` 写 5 字节进 32 字节缓冲，界内。
**结论：不是缺陷。** 需要 `_r` 变体的调用方，本项目也提供了 `getpwuid_r`（`:3313`）。

### S16 —— `syscall_guard.c` 的 64 KiB `sg_pool` **尺寸**本身够用（但并发不安全，见 H3）

单线程下：`need = 4096`，池 64 KiB → 16 个槽位才回绕一次。
项目自己在 `:342-350` 用判决实验证明"8 槽会崩、64 KiB 够用"。
**尺寸结论成立**；H3 说的是**并发**这条正交的路径。

### S17 —— `proc.c` 的 `%.*s` 精度与 `px_cfg_str` 截断

`proc.c:1470-1476`：
```c
n = snprintf(out, outsz, "%.*s/%s", (int)dir_len, p, file);
if (n < 0 || (size_t)n >= outsz) return PX_ETOOLONG;
```
`dir_len` 来自 `(size_t)(end - p)`，即 `PATH` 里某一段的长度。
`PATH` 由 `getenv` 提供，实际不可能达到 `INT_MAX`，转 `int` 不会截断；
且 `snprintf` 返回值检查正确。`px_cfg_str`（`proc.c:1980-1999`）
用 `n >= cap → n = cap - 1` 后 `memcpy` + `dst[n] = '\0'`，界内。
**安全**（`px_cfg_str` 的"截断而不是失败"是刻意选择，注释已说明）。

### S18 —— `l2s.c` 的 `parse_l2s_name` 与 `out->orig_name` 边界

`l2s.c:437-439`：
```c
if (bodylen + 1 > sizeof(out->orig_name))   /* sizeof == L2S_NAME_MAX == 256 */
    return L2S_ENAMETOOLONG;
memcpy(out->orig_name, body, bodylen);
out->orig_name[bodylen] = '\0';
```
先判后拷，**安全**。`bodylen` 来自 `nlen - plen`（`nlen = strlen(name)`），
不可能下溢（前面已判 `nlen > plen`）。

### S19 —— `l2s.c` 的 `l2s_make_paths_ex` 的 `mid`/`final` 组装

`l2s.c:768-787`：每条 `strcpy`/`strcat` 之前都有显式长度检查
（`if (strlen(head) + strlen(base) + L2S_DIGITS + 1 > sizeof(mid)) return L2S_ENAMETOOLONG;`
以及 `final` 的同款检查）。`head` 由 `l2s_join` 产出（已保证 < `L2S_PATH_MAX`），
`base` 由 `l2s_split` 产出（已保证 < `L2S_NAME_MAX`）。**安全。**

### S20 —— `preload.c` 的 `ensure_real_functions()` 幂等 + 惰性

`if (!real_open) { ... 一次性 dlsym 全部 24 个指针 ... }`。
以 `real_open` 单个标志作为"整组已解析"的哨兵。
若 `dlsym(RTLD_NEXT, "open")` 返回 NULL，会**重复**尝试整组 —— 只是浪费，
不是缺陷；且后续每个钩子各自判空（见 §6-U2 的例外清单）。

### U1 —— 并发竞态的实际触发率未能实测
H3 的竞态我给出的是**确定性复刻**（`/tmp/pool2.c`），

`real_newfstatat64`(`:1180`)、`real_lstat`(`:1199`)、`real_lstat64`(`:1240`)、

其中 `real_newfstatat` / `real_newfstatat64` **显式判了**（`:1148-1151`、`:1173-1176`，

（`proc.c:2515-2520`）完全一致。

### U5 —— `livepatch.c` 的站点偏移与 `mprotect` 失败处理
`livepatch.c:79-82` 的站点表 `{0x855c4UL, "set_robust_list", 99}` /

所以换 glibc 版本最坏是"不生效"而非"打错位置"。**这一点是安全的。**
**待确认**：`mprotect(lo, hi-lo, PROT_READ|PROT_WRITE|PROT_EXEC)`（`:175`）
成功后**再也没有恢复原权限** —— 代码段永久保持可写。这不是内存安全缺陷

### U6 —— `l2s.c` / `l2s-runtime.c` 的 `L2S_PATH_MAX`(4096) vs `MAX_PATH_LEN`(8192)
`l2s` 层的所有缓冲是 4096（`L2S_PATH_MAX`），而 `preload.c` 的翻译缓冲是 8192

所以**不会**越界写。
**待确认**：是否存在一条路径，让 `preload.c` 把**超过 4096 字节**的
已翻译路径交给 l2s 层，从而让 l2s 静默返回 `ENAMETOOLONG` 而不是

- `_GNU_SOURCE redefined`。

**结论：`-fanalyzer` 对本次这批缺陷基本无效。**
原因是这些缺陷的形状不是"单函数内的 malloc/free 失衡或明显的越界"，
而是**跨调用生命周期**（H3：调用方在 `svc` 返回后仍持有指针）、
**跨编译单元**（H1：`fprintf` 的变参在 `stderr` 内部被消费）、
**并发**（H3）以及**语义/契约**（M1 的编号、M2 的 FORTIFY 语义）。
**唯一高效的手段仍是"逐个对照内核头文件 + 针对可疑点写判决实验"。**

对 H1，真正有效的工具是 **`-Wformat=2`**（`BUILD_RUNTIME.sh` 用 `-w` 把它关掉了，见 L6）；
对 H3，真正有效的是 **ThreadSanitizer**（本环境未验证是否可用）。
