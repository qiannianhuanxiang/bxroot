## ⭐ 高价值缺口（3 项）

1. **kill-on-exit 异常退出失效**（#97 语义细节）：容器 shell `exit_group`/被杀是最常见退出方式，此时账本清理不执行，孤儿留在宿主。
   验证：`bxroot sh -c 'sleep 300 & kill -9 $!'` 后 `ps` 查 sleep 是否残留。
   方向：launcher 侧 fork 常驻监督进程（pidfd/subreaper 等待 + 向 runtime 查询账本快照，如经环境变量传递的共享 fd），需重新评估进程拓扑成本。
2. **裸系统调用绕过 SIGSYS 防屏蔽**（#134/#332 引申）：sigsys.c 只拦 4 个 libc 符号；guest 直接 `syscall(SYS_rt_sigprocmask, SIG_BLOCK, {SIGSYS})`（如 Go 运行时风格代码）不被剔除，一旦屏蔽被 seccomp TRAP 的调用即整进程死（rc=159）。
   验证：按 test/probe_raw_syscall.c 模式写探针：raw 屏蔽 SIGSYS→触发被拦调用，期望存活。
   方向：在 syscall_guard.c 裸系统调用分流表加入 **135**(rt_sigprocmask)/**134**(rt_sigaction) 的集合剔除。

   > ★ 号码以 aarch64 `asm-generic/unistd.h` 为准：135 / 134 ★
   >
   > 本文档此处原先写的是 **175 / 14** —— 两个都是错的：
   > aarch64 上 175 是 `__NR_geteuid`、14 是 `__NR_removexattr`
   > （实测：`gcc -dM -E -include asm-generic/unistd.h - </dev/null`）。
   > **按原号码改会引入新缺陷**，且正是 commit `d85b22c`（2026-09-19）
   > 刚修掉的那一类：`sigsys.c` 里把 135 写成 175，于是"解除屏蔽"那句
   > 实际只查了一次 `geteuid`，返回 0 而从不报错，SIGSYS 屏蔽位原封不动
   > → 进程被 159 杀掉。裸 `syscall` 号没有类型检查、没有宏兜底，
   > 写错只会静默调用另一个语义无关的系统调用。
   >
   > 注意区分：`d85b22c` 修的是 **sigsys.c 内部**那句裸"解除屏蔽"的
   > 号码与 sigsetsize；本条缺口指的是**裸 `syscall()` 绕过 libc 符号
   > 防屏蔽**（`syscall_guard.c` 的 `syscall()` 分流表不处理 135/134），
   > 两者是不同的问题面，本项至今无任何代码落地。
3. **execve 失败原因诊断**（#402/#21）：补上游式 4 条原因提示 + `execveat` 遇 ENOSYS 时回退 `/proc/self/fd/%d` 或翻译路径 execve；验证：容器内 exec 缺解释器的脚本应给出可定位提示。
