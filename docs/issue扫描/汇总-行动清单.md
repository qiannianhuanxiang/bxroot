### 三个只有动手才会发现的约束（复核时实测得出）

- **#1 的隐藏约束**（动手时又发现并补上一条）：glibc 的 `readdir` 用
  **本地 bl** 直调 `getdents64`（`objdump -d libc.so.6`：
  `bcc90: bl bcb80 <getdents64>`，不经 PLT）。所以**只 hook `getdents64`
  符号抓不到 `readdir`** —— 必须同时 hook glibc 导出的 `readdir`/`readdir64`，
  并另在 `syscall_guard.c` 给裸 `syscall(61 /*getdents64*/)` 加结果缓冲改写
  （node/libuv 走裸 svc）。
  **★ 本轮修的时候实测发现还有第三条分支：`scandir` 也是本地 `bl` 调
  `readdir` 真身（`bl bcbf0 <readdir>`），所以 hook `readdir` 对 `scandir`
  同样无效** —— 给 readdir 挂钩子后跑 scandir，钩子命中 **0 次**（实测）。
  三条链各要自己接，四处钩子：`readdir`/`readdir64` + `scandir`/`scandir64`
  + `syscall_guard.c` 的 case 61。漏掉任一条 = 做出「看起来修了、
  pnpm 依然失败」的假修复。
- **#2 文档措辞不准确**：断链**只在非集中布局下成立**。实测两形态对照
  （真实 `l2s_rt_link`）：`l2s_dir=NULL`（散落布局）落盘的是**相对**
  target → 从父目录读 `ENOENT`；而 `l2s_dir=<rootfs>/.l2s`（launcher
  的默认生产路径，`launcher.c:1205-1218`）落盘是**绝对** target → 读得通。
  缺口仍在（`--link2symlink` 未开、直接经 bridge 跑、或显式清空
  `BXROOT_L2S_DIR` 时复现），但成因是「相对形态落盘」，不是普适的。
- **#6 的真实影响被「未接线」掩盖**：`patch_static_elf` **无任何调用者**
  （`main` 走 `execve + LD_PRELOAD` 回退），`BXROOT_STUB_LOADER` 只被
  launcher `setenv` 而运行时无消费者。所以「noexec 时静默失败」
  **今天不可达** —— 不是因为修好了，而是这条路径从未被走到。
  正确的顺序是**先接线，再修 /tmp**，否则修了也无人走到。

## 关键结构性结论

- **proot 的进程/信号痛点多属架构性免疫**：bxroot 无 tracer，launcher
  execve 直接落位，#146（信号退出码）、#11（daemon）、#60（作业控制）、
  #291/#292/#261（ptrace 仿真缺陷）天然不存在。
- **资源平台类**：#44（personality/JVM）、#213（ptrace TAB 补全）、
  #227（Heroku 禁 ptrace）等对 bxroot 结构性免疫或反成卖点。
- **官方 430 条中，l2s 相对路径断链无同类 issue** —— 这是 bxroot
  独有的缺陷面（来自 l2s 的磁盘形态设计），无上游解法可摘。
