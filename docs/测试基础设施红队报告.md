## 2. 发现详情

### 🔴 S1 — 告警门禁与真实构建的警告集不等价（实测漏 4 条）

**问题描述**

`test/RUN_WARN_GATE.sh:139` 的门禁命令是：

```sh
"$CC" $BASE -I"${PROC_DIR:-.}" $DEFS -fsyntax-only "$f"
```

`$BASE` 里**没有任何 `-O` 选项**，同时又加了 `-fsyntax-only`。而
`BUILD_RUNTIME.sh` 实际编译时用的是 `-O2`（失败后回退 `-O1`），且不做 `-fsyntax-only`。

两者差出**两类**警告：
1. `-O1/-O2` 才会跑的优化分析（`-Wmaybe-uninitialized`、`-Wuninitialized`、`-Wstringop-truncation`、`-Warray-bounds` …）
2. `-fsyntax-only` 会整个跳过的代码生成/字符串长度分析（`-Wformat-truncation`）

**复现命令**

```sh
cd /root/rt-tmp/clone2     # 干净源码快照
WARN="-Wall -Wextra -Wformat=2 -Wno-nonnull-compare -Wno-unused-parameter"
FLAGS="-shared -fPIC $WARN -D_GNU_SOURCE= -Isrc/l2s -Isrc/runtime -Isrc/proc -DFAKEROOT_PURE_LOGIC -DPX_PURE_LOGIC=0"

# 门禁的写法
gcc $FLAGS -fsyntax-only src/launcher/launcher.c 2>&1 | grep -c 'warning:'
# 真实构建的写法
gcc $FLAGS -O2 -c src/launcher/launcher.c -o /dev/null 2>&1 | grep -c 'warning:'
```

**原始输出**

```
编译单元                       门禁-O0 构建-O2
----------------------------------------------------------
src/runtime/preload.c                      0         0
src/runtime/syscall_guard.c                0         0
src/runtime/sigsys.c                       0         0
src/runtime/crash.c                        0         0
src/runtime/livepatch.c                    0         0
src/runtime/fakeroot.c                     0         0
src/l2s/l2s.c                              0         0
src/l2s/l2s-runtime.c                      0         0
src/launcher/launcher.c                    0         3   <<< 门禁漏检 3 条
src/bridge/bridge.c                        0         1   <<< 门禁漏检 1 条
src/proc/proc.c                            0         0
----------------------------------------------------------
合计                                       0         4
```

被漏掉的具体告警：

```
[src/launcher/launcher.c] launcher.c:212:56: warning: '%s' directive output may be truncated writing 20 bytes into a region of size between 0 and 4095 [-Wformat-truncation=]
[src/launcher/launcher.c] launcher.c:218:50: warning: '%s' directive output may be truncated writing 19 bytes into a region of size between 0 and 4095 [-Wformat-truncation=]
[src/launcher/launcher.c] launcher.c:219:46: warning: '%s' directive output may be truncated writing 24 bytes into a region of size between 0 and 4095 [-Wformat-truncation=]
[src/bridge/bridge.c]     bridge.c:62:5:  warning: '__builtin_strncpy' output may be truncated copying 107 bytes from a string of length 255 [-Wstringop-truncation]
```

进一步隔离出两个变量各自的贡献：

```
src/launcher/launcher.c
   -O0  : 3 条
   -O1  : 3 条
   -O2  : 3 条
   无-O : 0 条  ← 门禁实际用的写法（`-fsyntax-only` 且不给 -O）
src/bridge/bridge.c
   -O0  : 0 条
   -O1  : 0 条
   -O2  : 1 条
   无-O : 0 条  ← 门禁实际用的写法
```

**关键点：`launcher.c` 那 3 条属于"光加 `-O` 也没用、必须放弃 `-fsyntax-only` 才看得见"**——
`-O0/-O1/-O2` 的 `-c` 编译都能看到 3 条，唯独 `-fsyntax-only` 是 0 条。
也就是说门禁的**主要**盲区是 `-fsyntax-only`，**次要**盲区是缺 `-O`（`bridge.c` 那一条只在 `-O2` 出现）。

再看 `-O2` 在本容器的实际可行性：

```
make runtime 第 1 次: ❌ ICE=1 error=1
make runtime 第 2 次: ❌ ICE=1 error=1
make runtime 第 3 次: ❌ ICE=1 error=1
```

`-O2` 在本容器**必崩**，`BUILD_RUNTIME.sh` 每次都回退到 `-O1`。而 `-O1` 下 `launcher.c` 依然是 3 条告警：

```
🔴 src/launcher/launcher.c            3 条 (真实 -O1 构建)
```

**影响**

这不是理论风险，是**当场就在漏**：基线那一轮"✅ 零告警（检查了 11 个编译单元）"的
同一次运行里，`launcher.c` 实际有 3 条、`bridge.c` 实际有 1 条告警。
门禁给出的"0 条"是**假的**。这套东西的整个卖点就是"防止编译警告被静默"——
而它自己就在静默 4 条现存告警。

**修复建议**

1. **去掉 `-fsyntax-only`，改成真实编译到 `/dev/null`**：
   `"$CC" $BASE $OPT -I... $DEFS -c "$f" -o /dev/null`
2. **补上与构建脚本一致的 `-O`**。既然 `BUILD_RUNTIME.sh` 实际落在 `-O1`，门禁就用 `-O1`
   （也可 `-O1`/`-O2` 各跑一次取并集，但本容器 `-O2` 会 ICE，建议只钉 `-O1`）。
3. 加一条**元测试**：门禁跑完后断言"每个单元都真的被编译过"（现在只检查 `CHECKED -eq 0`，
   只要≥1 个文件存在就放行，见 S7）。

### 🔴 S2 — "D4 符号导出核对"永远不会让构建变红

**问题描述**

`BUILD_RUNTIME.sh:178-189` 是 RUN_ALL 第 9 项（"运行时构建"）唯一的实质内容，
注释和文档都把它当作能拦住"钩子静默失效"的构建期门禁。但代码是：

```sh
if [ -n "$MISSING" ]; then
    echo "   ⚠️  未导出的 D4 符号:$MISSING"
else
    echo "   ✅ D4 进程管理符号全部导出（含 waitpid/wait4/wait3/waitid）"
fi
exit 0        # ← 无论 MISSING 是否为空都 exit 0
```

**复现命令**

```sh
cd /root/rt-tmp/clone2
sed -i 's|^    execve execv execvp execvpe execl execlp execle execveat fexecve \\|&|' BUILD_RUNTIME.sh
# 在符号清单里塞一个绝不存在的符号
sed -i 's|fexecve \\|fexecve THIS_SYMBOL_DOES_NOT_EXIST_ZZZ \\|' BUILD_RUNTIME.sh
grep -n 'THIS_SYMBOL' BUILD_RUNTIME.sh
sh BUILD_RUNTIME.sh -O0; echo "退出码=$?"
```

**原始输出**

```
176:    execve execv execvp execvpe execl execlp execle execveat fexecve THIS_SYMBOL_DOES_NOT_EXIST_ZZZ \
   ✅ 链接成功（-O0，第 1 次尝试）
   产物: /root/rt-tmp/clone2/build/libbxroot-runtime.so
   导出符号（nm -D --defined-only）: 335
   ⚠️  未导出的 D4 符号: THIS_SYMBOL_DOES_NOT_EXIST_ZZZ
BUILD_RUNTIME.sh 退出码 = 0   ← 明明有缺失符号却报成功
```

于是 `run_step "运行时构建"` 记 **PASS**，汇总显示 `✅`。

**顺带纠正一处文档错误**：注释里说这是"D4 的 **19** 个符号"，实际清单有 **23** 个
（`fork vfork posix_spawn posix_spawnp kill killpg tgkill tkill system popen
execve execv execvp execvpe execl execlp execle execveat fexecve waitpid wait4 wait3 waitid`）。

**影响**

这一类缺陷正是文档自己点名要防的："LD_PRELOAD 靠动态符号表插入，符号漏导出 = 钩子静默失效，
而进程照样能跑 —— 这类缺陷只有构建期检查能拦住。" 结果这个"唯一的构建期检查"**不会失败**。
换句话说：`kill`、`wait4`、`execve` 这些钩子哪天从动态符号表里掉了，回归照样全绿。

**修复建议**

```sh
if [ -n "$MISSING" ]; then
    echo "   ❌ 未导出的 D4 符号:$MISSING"
    exit 1
fi
echo "   ✅ D4 进程管理符号全部导出（含 waitpid/wait4/wait3/waitid）"
exit 0
```

（`test/RUN_WAIT_TESTS.sh:70` 与 `RUN_ALL.sh` 的 `--quick` 复用分支都已经是 `exit 1`，
只有 `BUILD_RUNTIME.sh` 这一处是软的——而它恰恰是被回归当门禁用的那个。）

### 🔴 S3 — 第 5 项"系统调用参数位置"根本不测试它声称要测的代码

**问题描述**

`RUN_ALL.sh` 第 5 项的注释写着"防回归：symlinkat 的 a1 不是路径"，
`test/test_syscall_argpos.c` 的文件头也写明"本项目的 syscall_guard 里有一张表……
曾把 symlinkat(36) 错列成'a1 是路径'"。

但这一项的命令只编译**一个**文件：

```sh
run_step "系统调用参数位置" retry_gcc_run t-argpos \
    -std=c11 -O1 -Wall -Wextra test/test_syscall_argpos.c
```

`src/runtime/syscall_guard.c` **不在命令行里**。测试里 `syscall(36, ...)` 调到的是
**glibc 的 `syscall()`**，走的是内核；`path_arg_index()` 那张表压根没被链接进来。

**复现命令**

```sh
cd /root/rt-tmp/mk
# 把 path_arg_index() 整个改成「一律返回 1」——正是历史上 symlinkat 的错误语义
python3 - <<'PY'
p='src/runtime/syscall_guard.c'; s=open(p).read()
i=s.index('static int path_arg_index(long nr)')
j=s.index('{', i); d=0; k=j
while True:
    if s[k]=='{': d+=1
    elif s[k]=='}': d-=1
    if d==0: break
    k+=1
open(p,'w').write(s[:i]+'static int path_arg_index(long nr)\n{\n    (void)nr;\n    return 1;\n}'+s[k+1:])
PY

# 第 5 项的原命令
gcc -std=c11 -O1 -Wall -Wextra -o /tmp/arg test/test_syscall_argpos.c && /tmp/arg; echo "退出码=$?"

# 同一份被改坏的源码，门禁怎么说？
sh test/RUN_WARN_GATE.sh | grep -E 'syscall_guard|零告警'
```

**原始输出**

```

=== 系统调用参数位置契约 ===
  [ok]   symlinkat: a1 是 dirfd（不是路径）
  [ok]   symlinkat: 链接内容正确
  [ok]   openat: a1 是路径
  [ok]   faccessat: a1 是路径
----------------------------------------
cases:  4  (0 failed)
RESULT: PASS
→ 第 5 项退出码 = 0

########## 同一份缺陷，门禁怎么说？ ##########
✅ src/runtime/syscall_guard.c        0 条
✅ 零告警（检查了 11 个编译单元）
```

二进制的符号表里连 guard 的影子都没有：

```
$ nm -C /tmp/arg | grep -ci 'path_arg_index\|syscall_guard'
0
```

**影响**

这一项**测的是内核 ABI，不是项目代码**。把 `path_arg_index()` 改回历史缺陷形态
（`case 36: return 1`），第 5 项、门禁、以及整个回归**全部保持绿色**。
也就是说：**这套回归声称能防的那个具体缺陷，它防不住。**

> 注：我尝试构造"缺陷编译进 `.so` 后用 `LD_PRELOAD` 触发 `SIGSEGV`"的端到端反证，
> 但本容器外层 proot 会吞掉 `LD_PRELOAD`（实测：`LD_PRELOAD=libpre.so /bin/true`
> 的构造器没有输出），无法在本环境内复现 139。**未证实**。
> 不过"argpos 测试不链接 `syscall_guard.c`"是硬事实（编译命令 + `nm` 双重确认），
> 结论不依赖那个反证。

**修复建议**

把第 5 项改成真正的防回归：让测试**链接真实的 `syscall_guard.c`**，并断言
`path_arg_index(36)` 的返回值不是 1。当前 `path_arg_index` 是 `static`，需要：
1. 给它加一个测试钩子（例如在 `syscall_guard.h` 里导出 `int bxroot_path_arg_index(long nr);`），或
2. 直接在测试里 `#include "../src/runtime/syscall_guard.c"` 后断言其行为。

同时把断言从"内核接受 `syscall(36, tgt, AT_FDCWD, lnk)`"改成
"`bxroot_path_arg_index(36) != 1`"——**这才是那个缺陷的直接不变量**。

### 🟠 S4 — 测试脚本缺失被静默跳过，退出码仍为 0

**问题描述**

`run_step` 对"没有命令"的处理是记 `SKIP` + `return 0`，而末尾的判定只看 `FAIL`：

```sh
run_step() {
    name="$1"; shift
    if [ "$#" -eq 0 ]; then
        note SKIP "$name" "无命令"
        SKIP=$((SKIP + 1))
        printf '⏭️  %-26s 跳过\n' "$name"
        return 0            # ← 不计 FAIL
    fi
    ...
}

# 末尾
echo "  通过 $PASS / 失败 $FAIL"      # ← SKIP 连数字都不打印
if [ "$FAIL" -gt 0 ]; then exit 1; fi
echo "  ✅ 全部通过"
exit 0
```

而"没有命令"这条路径**唯一的触发方式**就是测试脚本文件不存在。四处守卫都是这个形状：

```sh
[ -f test/RUN_INTEGRATION.sh ] && run_step "l2s×fakeroot 协同" sh test/RUN_INTEGRATION.sh \
    || run_step "l2s×fakeroot 协同"
```

**复现命令**

```sh
cd /root/rt-tmp/mk
mv src/runtime/RUN_CRASH_TESTS.sh /root/rt-tmp/hidden-crash.sh   # 删掉第 6 项的脚本
sh test/RUN_ALL.sh --quick; echo "退出码 = $?"
```

**原始输出**

```
 回归汇总
======================================================
```

- 旧版（228 行）的 `[ ... ] && run_step A || run_step B` 写法曾被怀疑会误走 `B`。
  **实测不会**：因为 `run_step` 结尾是 `return 0`，永远非零不了，`||` 分支永不触发。
  但这也意味着这四处 `|| run_step "名字"` 是**纯装饰**——它们共同制造了
  "名字还在表里 ⇒ 这一项跑过了"的错觉。下面的实验直接证明这一点：

```
########## 场景 1: 测试脚本真实存在且通过 ##########      ← 无输出＝跑过了
########## 场景 2: 测试脚本被删除/改名（同一份代码）##########
SKIP  协同
########## 场景 3: 回答「run_step A 返回非零会不会误走 B」##########
run_step 的返回码 = 0  → 因为结尾有 return 0，永远不会触发 || 分支
########## 场景 4: 缺失的测试脚本对最终退出码的影响 ##########
PASS=1 FAIL=1 SKIP=1
最终退出码 = 1   ← 场景2 的缺失测试脚本只贡献了 SKIP，没进 FAIL
```

**影响**

- 只要有人 `git mv` / 改名 / 漏检出一个测试脚本，那一项就**永久消失且没人知道**。
  汇总表里那两行 `⏭️ 跳过` 会被当成"环境限制"，而退出码 0 会被 CI 当成绿灯。
- 与之呼应的是背景故事本身：`make test` 曾经指向一个**从来不存在**的 `full_test.sh`，
  这个坑被修好了；但**同构的坑（缺脚本 = 静默通过）在 `run_step` 里原样保留了下来**。

**修复建议**

1. 空命令一律算**失败**：
   ```sh
   if [ "$#" -eq 0 ]; then
       note FAIL "$name" "测试脚本缺失"
       FAIL=$((FAIL + 1)); return 0
   fi
   ```
   若确实需要"合法跳过"，就提供一个显式的 `skip_step <名字> <原因>`，并且**只有它**能产生 SKIP。
2. 汇总里打印 SKIP 数，并在有 SKIP 时给出**非零**退出码（或至少要求 `CI_STRICT=1` 时非零）。
3. 把"某个 `-f` 判断失败"与"脚本存在但返回 127（命令不存在）"区分开：
   后者现在的行为是对的（实测 `rc=127` → FAIL），但值得加一条注释固化。

### 🟡 S6 — 门禁的"一致性自检"可被绕过，其中 2 种它默许通过

**问题描述**

`RUN_WARN_GATE.sh:95-105` 声称"两处若不一致，本脚本结尾会检测"。实测它只能拦住一种写法。

**复现与原始输出**

**绕过方式 1（能被拦住）**——`CFLAGS` 行首加 `-w`：

```sh
sed -i 's|^CFLAGS="-shared -fPIC \$WARN -D_GNU_SOURCE="|CFLAGS="-shared -fPIC -w -D_GNU_SOURCE="|' BUILD_RUNTIME.sh
sh test/RUN_WARN_GATE.sh; echo "退出码=$?"
```
```
70:CFLAGS="-shared -fPIC -w -D_GNU_SOURCE="
❌ BUILD_RUNTIME.sh 又用回了 -w（全量静默），这会让门禁失去意义。
门禁退出码=1
```

**绕过方式 2（拦不住 ⚠️）**——把 `-w` 塞进 `WARN` 变量：

```sh
sed -i 's|^WARN="-Wall|WARN="-w -Wall|' BUILD_RUNTIME.sh
sh test/RUN_WARN_GATE.sh; echo "退出码=$?"
```
```
69:WARN="-w -Wall -Wextra -Wformat=2 -Wno-nonnull-compare -Wno-unused-parameter"
✅ 零告警（检查了 11 个编译单元）
门禁退出码=0        ← 构建脚本已经全量静默，门禁却说「零告警」
```

**绕过方式 3（拦不住 ⚠️⚠️）**——直接削弱**门禁自己**的警告集：

```sh
sed -i 's|^WARN="-Wall -Wextra -Wformat=2 -Wno-nonnull-compare -Wno-unused-parameter"|WARN="-w -Wno-nonnull-compare"|' test/RUN_WARN_GATE.sh
sh test/RUN_WARN_GATE.sh; echo "退出码=$?"
```
```
警告集 : -w -Wno-nonnull-compare
✅ 零告警（检查了 11 个编译单元）
门禁退出码 = 0      ← 自检完全没发现门禁自己已经变成 -w
```
**门禁把自己变成 `-w`，自检一声不吭。** 这正是背景故事里那个缺陷的形态，
被原封不动地在门禁自身重演了一遍。

**绕过方式 4（只警告不失败）**——去掉 `-Wno-nonnull-compare` 造成真实策略漂移：

```sh
sed -i 's|-Wno-nonnull-compare -Wno-unused-parameter|-Wno-unused-parameter|' BUILD_RUNTIME.sh
sh test/RUN_WARN_GATE.sh; echo "退出码=$?"
```
```
门禁与构建策略可能已漂移，请同步后重跑。
✅ 零告警（检查了 11 个编译单元）
门禁退出码 = 0      ← 只用 ⚠️ 提示，不失败
```

**影响**

"一致性自检"的**唯一**实质作用是正则匹配 `^\s*CFLAGS=.*\s-w\s` 这一行。
换一个变量、换一种引号、去掉 `-w` 只削弱一部分警告集——
全部静默通过。而且方式 3 说明这个自检**连自己都不检查**。

**修复建议**

1. 把警告集提成**单一真源**：新建 `test/warn-flags.sh`（或 `build/warn.mk`），
   `BUILD_RUNTIME.sh` 与 `RUN_WARN_GATE.sh` 都 `source` 它。**复制粘贴 + 正则比对
   本质上不是一致性保证**——这正是脚本注释里"这里刻意复制"的代价。
2. 自检改成**断言级**：
   ```sh
   case "$WARN" in *-w\ *|*-w) echo "❌ 门禁自身警告集含 -w"; exit 2 ;; esac
   case "$WARN" in *-Wall*|-Wextra*|-Wformat=2*) ;; *) echo "❌ 门禁警告集被削弱"; exit 2 ;; esac
   ```
3. 所有"漂移"提示一律 `exit 2`（环境/配置问题），不要只 `echo ⚠️`。

"把 `-w` 换成精确警告集"这个改动**本身不足以**让警告被看见——
它只是让警告**被打印出来**。真正让警告变红的唯一机制是 `RUN_WARN_GATE.sh`，
而那个门禁有 S1/S6/S7 三个洞。

也就是说：**这条链路上真正的门禁只有一道，且那道门禁是漏的。**
`BUILD_RUNTIME.sh` 里加不加精确警告集，对"能不能拦住新告警"几乎没有影响。

**修复建议**

在构建脚本的成功路径上加：

```sh
if grep -q 'warning:' "$LOG"; then
    echo "❌ 构建产生告警（本项目要求零告警）："
    grep 'warning:' "$LOG" | head -20
    rm -f "$TMP"; exit 1
fi
```

这样构建本身就自带门禁，不必依赖外部脚本能否跑、跑得对不对。

### 🔵 S11 — `make all` 在本容器必然失败

**问题描述**

交叉编译器**存在**（`/usr/bin/aarch64-linux-gnu-gcc-13`），所以不是环境缺工具的问题。
但 `make all` 里的 runtime 目标用 `-O2` 直接编译、**没有 ICE 重试**，
而本容器 `-O2` 必崩。

> 说明：本项**受并发影响**。审查期间别的 agent 正在改 `src/proc/proc.c`，
> 我观察到 `make all` 曾因 `proc.c` 真语法错误而失败（`invalid storage class for function 'px_self_pid'`）。
> 为了公平，下面全部结论都在**干净源码快照** `/root/rt-tmp/clone2` 上重测。

**复现命令 / 原始输出**

```sh
cd /root/rt-tmp/clone2 && rm -rf build && mkdir -p build
for t in build/libbxroot.so build/libbxroot-linker.so build/libbxroot-bridge.so \
         build/libbxroot-stub-loader.so build/libbxroot-runtime.so; do
  make "$t" && echo "$t ✅" || echo "$t ❌"
done
```
```
build/libbxroot.so                     ✅ 成功
build/libbxroot-linker.so              ✅ 成功
build/libbxroot-bridge.so              ✅ 成功
build/libbxroot-stub-loader.so         ✅ 成功
build/libbxroot-runtime.so             ❌ 失败  警告=18 错误=1 ICE=1

make runtime 第 1 次: ❌ ICE=1 error=1
make runtime 第 2 次: ❌ ICE=1 error=1
make runtime 第 3 次: ❌ ICE=1 error=1
```

**结论**：`make all` 失败的**唯一**原因是 `libbxroot-runtime.so` 目标撞上 gcc 13.3.0 的
间歇性 ICE（`src/proc/proc.c:1038:1: internal compiler error: Segmentation fault`），
且 `Makefile` 里**没有重试**。这属于**已记录的环境限制**（`BUILD_RUNTIME.sh` 头部注释
自己就写了这一点）。其余 4 个目标在干净源码下**全部构建成功**。
如实说明，不硬造结论。

**顺带发现**：`make all` 的 FAIL 是 `Error 2`，但 `make test` 里第 9 项走的是
`BUILD_RUNTIME.sh`（带 30 次重试 + 三级优化回退），**能成功**。
所以 `make all` 红、`make test` 的第 9 项绿 —— 两者对同一件事给出相反结论。

**修复建议**

`Makefile` 的 runtime 规则改为 `runtime: ; @sh ./BUILD_RUNTIME.sh` 的委托形式
（即让 `all` 复用带重试的构建脚本），而不是自己再写一份裸 `$(CC)` 命令。
现在 `Makefile` 第 83-86 行与 `BUILD_RUNTIME.sh:113` 是**两份彼此独立的编译命令**，
警告集/重试/优化回退全都不一致——这本身就是 S1/S7 的根源。

### 🔵 S13 — 测试产物散落 `/tmp` 且不清理

**实测残留**（`/tmp` 在本容器里间歇性可读，我抓到了这些）：

```
-rw------- /tmp/bxroot-all-19966.txt      ← 旧版 RUN_ALL 的结果文件，从未删除
-rw------- /tmp/bxroot-step-19966.log     ← run_step 的日志，从未删除

-rw------- /tmp/bxroot-l2s-cc.err
-rw------- /tmp/bxroot-runtime-cc.err
-rwx------ /tmp/bxroot-t-argpos
```

`/tmp/bxroot-all-19966.txt` 的内容证明它来自**别人**的一次运行：

```
PASS|编译告警门禁|✅ 零告警（检查了 11 个编译单元）
...
FAIL|wait 家族钩子|rc=1    先跑 ../BUILD_RUNTIME.sh
```

`/tmp/bxroot-step-19966.log` 甚至指向**另一个工作目录**：

```
== 构建 libbxroot-runtime.so ==
   proc.c     : /tmp/clean-verify2/src/proc/proc.c
```

**影响 + 一个必须给设计者的提醒**

新版 `RUN_ALL.sh` 的注释把"/tmp 不可写"当成"别的进程动了权限"的偶发事件。
**实测是我这边也复现了同样的现象**：

```
$ ls -la /tmp
d---------. 218 root root 53248 Sep 16 17:31 /tmp       ← 权限 000
$ touch /tmp/rt-probe-$$
touch: cannot touch '/tmp/rt-probe-25906': Permission denied
...
$ mkdir -p /tmp/rt-x && echo OK
mkdir OK                                                 ← 几十秒后又好了
```

真实原因是：**`/tmp` 是一个 tmpfs，被跨会话/跨 agent 共享，且已有 218 个目录项
（达到 `nr_inodes` 量级的压力），权限在运行中途确实会变。**
所以"把 `/tmp` 当私有工作区"这个假设在本项目里是**不安全**的。
新版做的 mktemp + 仓库内回退是**正确方向**，但：

- 三个下级脚本（`RUN_WAIT_TESTS.sh`、`RUN_CRASH_TESTS.sh`、`test/RUN_TESTS.sh`、
  `test/RUN_INTEGRATION.sh`、`src/proc/RUN_TESTS.sh`）**仍然硬编码 `/tmp`**：
  `OUT=/tmp/test_wait_hooks`、`LOG=/tmp/crash-cc.err`、`/tmp/fakeroot-cc.err`、
  `/tmp/proc-cc.err`、`/tmp/bxroot-runtime-cc.err`。
  RUN_ALL 自己改好了，但**子脚本没改**，所以整条链路依然会因 `/tmp` 不可写而失败。
- **更严重的是跨运行污染**：`OUT=/tmp/test_wait_hooks` 这种固定名意味着
  A 项目/其他 agent 的旧产物会被复用。上面 `/tmp/bxroot-step-19966.log` 指向
  `/tmp/clean-verify2/` 就是活证据。

**修复建议**

1. 让所有子脚本从环境变量取工作目录：`OUT="${BXROOT_TEST_OUT:-/tmp}/test_wait_hooks"`，
   由 `RUN_ALL.sh` 统一传 `WORK_DIR` 下去。
2. 固定名产物前面带 `$$` 或用 `mktemp -d`。
3. 跑完清理，别留 `bxroot-all-*.txt`。

### ⚪ S14 — 文档把历史缺陷归因于错误的开关

**复现命令 / 原始输出**

```sh
cat > /tmp/fdef.c <<'EOF'
#include <stdio.h>
void f(const char *a, const char *b, const char *c){ fprintf(stderr,"%s %s %s\n", a, b); (void)c; }
EOF
for W in "-w" "-Wall" "-Wextra" "-Wall -Wextra -Wformat=2"; do
  printf '%-26s : %s 条告警\n' "$W" "$(gcc -std=c11 $W -c /tmp/fdef.c -o /dev/null 2>&1 | grep -c 'warning:')"
done
```
```
-w                         : 0 条告警
-Wall                      : 1 条告警
-Wextra                    : 1 条告警
-Wall -Wextra -Wformat=2   : 1 条告警
```

**问题**：`RUN_WARN_GATE.sh` 与 `BUILD_RUNTIME.sh` 的注释都写
"编译期本可由 **-Wformat=2** 直接拦下"。实测**只需 `-Wall`**（`-Wformat`）就能拦下，
`-Wformat=2` 是冗余的（它额外开 `-Wformat-nonliteral` / `-Wformat-security` / `-Wformat-y2k`）。

**影响**：不影响功能，但会误导后续维护者以为"必须保住 `-Wformat=2`"，
而真正必需的是**别用 `-w`**。归因错了会导致防线建在错误的位置。
