# 方法论：怎么证明"路径翻译真的生效了"

> 本篇是一个**判别实验的设计**，起因是两件事撞在一起：
> ① 发现 `LD_PRELOAD` 在 proroot 容器内静默失效，导致若干测试是**假绿**；
> ② NSS 子代理报告"官方 runtime 在本容器里不做路径翻译"，
>    而这条指控若成立，会让**多个既有对照报告**的结论失效。
>
> 两份报告都需要一个能**判别真假**的实验，而不是"看起来对/不对"。

---

## 一、为什么"程序跑起来了"不能当判据

本项目已经栽过两次同类跟头：

| 场景 | 假象 | 真相 |
|---|---|---|
| `RUN_PATH_FORMS.sh` 用 `launcher + LD_PRELOAD` | 8/8 全绿 | 加载的是**外层 proroot**，与 bxroot 无关 |
| 修 `dlsym` 降级时裸跑探针 | "验证成功" | 探针**压根没加载 runtime**，测的是 libc 自己 |

两次都是"程序正常运行 + 输出正常"，但**被测对象根本没上场**。
所以判据必须取"**被测对象自己的痕迹**"，且要能**区分它和替代品**。

---

## 二、三种判据的强弱

### 弱：看日志

```sh
BXROOT_VERBOSE=1 … 2>&1 | grep '\[bxroot\]'
# [bxroot] proc: init inject=1 have_preload=1 rootfs=…
```

能证明"库被加载了"，**但不能证明它做了翻译** ——
一个只加载不干活的库同样会打这行日志。

### 中：看 maps

```sh
grep -o 'libbxroot-runtime' /proc/<pid>/maps
```

能证明"库在进程里"，**但仍不能证明翻译生效**。
（`RUN_FALLBACK.sh` 用的是这一档：它的目的是"确认不是测了个假的东西"，
这一档足够。）

### 强：**判别性输入** —— 让"翻译"与"不翻译"产生**不同输出**

这是本篇的重点。

---

## 三、判别实验的设计

### 3.1 核心思路

给被测程序一个**只有经过翻译才能看到的世界**：

```
容器视角               内核视角
/etc/hostname   ←→    $ROOTFS/etc/hostname     ← 同一 inode，无法区分
```

上面这种是**不能**用来判别的 —— 两个视角指向同一个文件，
"翻译了"和"没翻译"读到的内容**一样**。这正是我第一次尝试失败的原因：

```sh
# ❌ 无效的判别实验
echo "UNIQUE-MARKER" > /tmp/disctest/etc/hostname
# 然后拿默认 rootfs 去测 —— 读到的还是老内容，因为没换 rootfs
```

### 3.2 正确的做法：换 rootfs，让 guest 的 `/` 指向**别处**

```sh
RF=/data/data/com.dsh.client/files/linux/ubuntu

# ① 在 rootfs **内**建一个"假根"（容器视角建，两侧 inode 相同）
mkdir -p /tmp/disc3/etc /tmp/disc3/bin
echo "DISCRIMINATOR-ABC" > /tmp/disc3/etc/hostname    # ← 唯一标记
cp /tmp/catprobe /tmp/disc3/bin/

# ② 把 rootfs 指到这个假根
BXROOT_ROOTFS=$RF/tmp/disc3 \
"$L/libproroot-bridge.so" "$L/libproroot-linker.so" --argv0 catprobe \
  --preload "$RF/tmp/bxd2rt/rt.so" \
  "$RF/tmp/disc3/bin/catprobe"
```

探针做的事极小：`fopen("/etc/hostname")` + 打印内容。

**实测结果**：

```
容器视角:  DISCRIMINATOR-ABC
内核视角:  DISCRIMINATOR-ABC
bxroot:    HOSTNAME: DISCRIMINATOR-ABC        ← ★ 命中标记 ★
```

判据成立的理由：探针请求的是 `/etc/hostname`（**guest 视角的路径**），
而它拿到了假根里的内容。要做到这一点，runtime **必须**把
`/etc/hostname` 改写成了 `$RF/tmp/disc3/etc/hostname` ——
"没翻译"的进程只会读到容器自己的 `/etc/hostname`（`localhost.localdomain`）。

★ 关键点：**输出里出现了"只有翻译才能拿到"的字符串** ★
这不是相关性，是**因果**。

### 3.3 一个必须避开的坑

假根里**必须也有探针自己**（或至少探针能跑起来所需的依赖）。
我第一次把假根建在 `/tmp/disc2`（rootfs 外），结果：

```
bxroot:  （无输出）
官方:    proroot-ldso: failure rc=2
```

因为 `--preload` 与 guest exe 都只认**内核视角**路径，
而 `/tmp/disc2` 不在任何 rootfs 内 —— 库和程序都找不到。
**把假根建在真 rootfs 内部**（`$ROOTFS/tmp/xxx`）就同时满足两侧。

## 四、这个判别法用来查什么

### 4.1 核实"官方 runtime 不做路径翻译"的指控

NSS 子代理报告：把 `PROROOT_ROOTFS` 指向 hostname 唯一的 rootfs，
官方**仍读到容器的 `/etc/hostname`**，输出与"完全不加载 runtime"逐字相同；
并称已试过 `PROROOT_ROOTFS`/`PROROOT_BINDS`/`PROROOT_ESCAPE_FD`/
`PROROOT_CFG_FD`/换 app linker/直接 exec linker 六种构造，均无效。

**我这边复现到的是**：官方 runtime 用判别性 rootfs 时先报
`deps: cannot find libc.so.6 (needed by …/catprobe)` —— 也就是**假根缺依赖**，
根本没走到"翻译"那一步。所以：

| 结论 | 状态 |
|---|---|
| 官方 runtime 在本容器**不翻译路径** | ⚠️ **子代理的观察可能是对的，但我的复现卡在"假根依赖不全"，尚未独立确认** |
| 官方需要 launcher 传 fd 才工作 | ✅ 与官方 strings 里的 `missing PROROOT_CFG_FD or PROROOT_ESCAPE_FD` 一致 |

★ 正确的核实方式（待做）★ 假根里补齐 `libc.so.6`、`ld-linux` 等依赖
（或直接把真 rootfs **复制**一份、只改 `/etc/hostname`），再跑判别实验。
**"复制整份 rootfs 再改一个文件"是最干净的构造** —— 它排除了所有依赖问题，
唯一的自变量就是 hostname。

★ 这条待办已记入 `docs/已知限制与架构能力边界.md` 的待办区 ★
在核实之前，**不要**基于"官方不翻译"这个前提去否定既有对照报告。

### 4.2 核实 bxroot 的每一条路径能力

同一个套路可以逐条钉住：
- bind mount 是否生效（bind 一个内容不同的目录，看能否读到标记）
- `-w`（工作目录）是否生效（在假根里放 `pwd` 探针）
- fakeroot 是否生效（探针打印 `getuid()`）
- l2s 是否生效（探针做 `link()` 后看 `st_nlink`）

判据统一为"**输出里出现只有该能力生效才会出现的字符串/数值**"。

## 五、固化成规则

1. **任何"runtime 生效了吗"的问题，禁止用"程序跑起来了"回答。**
2. **能用判别性输入时，优先用它** —— 它比日志和 maps 都强，
   因为它排除了"加载了但没干活"。
3. **判别性输入的设计要求**：让"生效"与"不生效"产生**不同且可预期**的输出，
   而不是"都正常"。做不到就先承认做不到，别用弱判据冒充强判据。
4. **构造失败 ≠ 结论成立**。本次官方侧的复现卡在依赖缺失 ——
   这既不能证明也不能否定"官方不翻译"，只能记"未确认"。
   ★ 把"没测出来"当成"证明了反面"是本项目反复警惕的错误 ★
