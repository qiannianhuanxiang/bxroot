# 已知限制与架构能力边界

> 本文是 bxroot **当前已知限制的汇总清单**，每条都附实测依据与
> 详细报告链接。目的：让后续开发者一眼看到"哪些做不到、为什么做不到"，
> 避免在这些方向上重复投入。

---

## 一、架构级能力边界（LD_PRELOAD vs ptrace）

bxroot 是 **LD_PRELOAD 用户态路径翻译**架构；官方 proroot 是 **ptrace/
livepatch 架构**。两者的能力差异不是实现质量，而是**架构本身**：

| 能力 | LD_PRELOAD（bxroot） | ptrace（官方） |
|---|---|---|
| 符号层 libc 调用 | ✅ 可拦截 | ✅ 可拦截 |
| `syscall()` 符号 | ✅ 可拦截 | ✅ 可拦截 |
| **内联 svc**（glibc 内部） | ⚠️ 只能靠 livepatch 中和已知地址 | ✅ 全程可见 |
| **glibc 私有内部路径**（GLIBC_PRIVATE，不经 PLT） | ❌ **无法拦截** | ✅ 全程可见 |
| 子进程每次 syscall 观测 | ❌ 看不到 | ✅ 看得到 |

**由此产生的已知限制**（见下文具体条目）都源于同一件事：
某些调用路径**根本不经过任何导出符号**。

## 二、确认的限制清单

### 2.1 `make` 的配方子进程不可用（架构级）

```
$ make -C dir
echo RECIPE-MARKER              ← make 回显了命令
make: *** [Makefile:2: all] Bad system call   ← 子进程被 SIGSYS 杀
（配方未执行）
```

- `make --version` 本体正常；**只有"跑配方"坏**
- 已实测**否定**两个最有希望的假设：
  - livepatch 覆盖不全（两侧对 libc 的 patched 地址**完全一致**，112 个）
  - spawn 走了未中和路径（`px_trampoline_spawn` 的日志从未出现）
- 精确复刻 make 序列的探针（vfork+execvp+自构 environ）两侧行为一致
- **判定**：make 用了 glibc 私有的 clone/spawn 内部路径，其子进程
  未经 bridge 直接 exec 宿主 shell —— 一跑就撞 seccomp

详见 `docs/posix_spawn带attr失败-make不可用.md`（含 20+ 个实验）。

### 2.2 NSS 用户库查询 —— **核心已修**（2026-09-17），剩 utimensat 边缘

**已修**：getpwnam/getpwnam_r/getgrnam/getgrnam_r 四个钩子，
采用"/etc/passwd、/etc/group 直解回退"（真实 NSS 失败时 fopen+逐行
解析）。NSS 全家与官方一致；dpkg -i 从 fatal error（unknown system
user 'root'）推进到**包安装成功**（Status: install ok installed，
两侧一致）。

**剩余边缘**：dpkg unpack 时报 "error setting timestamps of
'...dpkg-new'"（非致命，不影响包安装结果）。已定位为 utimensat 的
一个未覆盖入口 —— 已补 resolve_dirfd_path 的 dirfd+相对路径解析，
探针验证各路径均成功，但 dpkg 的具体调用序列（tar 子进程内）
仍有未对齐之处。显示层面差异，不影响文件内容/包状态/元数据。

```
$ getent passwd root     官方: root:x:0:0...   bxroot: （空，rc=2）
$ id                     官方: gid=0(root)     bxroot: gid=0（组名缺失）
$ python3 -c "import pwd; pwd.getpwnam('root')"
                         官方: 正常            bxroot: KeyError
```

已排除（实测）：dlopen 搜索路径、LD_LIBRARY_PATH、fakeroot 干扰、
`/etc/passwd` 可读性、文件元数据、nsswitch 解析、模块文件差异
（md5 相同、同一 inode）、livepatch 覆盖。

**最接近根因的观察**：libc 内置的 `_nss_files_getpwnam_r`
（glibc 2.39 已内置，74 个符号）两侧返回值不同：
官方 `rc=1`，bxroot `rc=0` 且 `res=NULL` —— 未解释。

详见 `docs/缺口D-NSS用户库查询失败.md`。

### 2.3 CLI 明确拒绝的选项（与官方一致的设计决定）

```
-H  -p  -q/--qemu  --sysvipc  --ashmem-memfd  -i 非0:0
```

- `-H`（hidden_files）与 `-p`（port_switch）是**上游 PRoot 的扩展**，
  官方 proroot 自己也没实现 —— 已实测官方 runtime 不碰 `getdents`/`readdir`
- 这些选项**明确报错**而不是静默忽略（设计决定，见
  `docs/proot-CLI兼容性报告.md`）


### 2.4 `df` 的挂载点标签不同（数值正确，2026-09-17 定位）

```
官方 : /dev/block/dm-13  495438082048 395546423296 99757441024 80% /
bxroot: /dev/block/dm-62 495438082048 395546423296 99757441024 80% /data/data/com.dsh.client
```

**数值部分（容量/已用/可用/百分比）逐字节一致**，只有设备名与挂载点
两个**标签**不同。

**根因（本轮定位，排查路径完整）**：
`df /` 的输出 = `statvfs("/")` 的数值 + 从挂载表里按 `st_dev` 匹配的标签。
bxroot 下两侧的 `statvfs`、`getmntent`、`st_dev`、`mountinfo`
**全部实测一致**（181 条挂载、`/` 的设备 `dm-13`、`st_dev=65086`）。

差异来自 **GNU df 的匹配顺序**：
- 无参数 `df` 会遍历挂载表并对每个挂载点调 `statvfs`
- 官方下 50 条可见（proroot 让宿主路径也可达），`/`（dm-13）在表前部
- bxroot 下只 5 条可见（宿主路径如 `/system`、`/data` 翻译后不存在，
  `statvfs` 失败被跳过），`/data`（dm-62）与 `/` **同一 f2fs 超级块**，
  `st_dev` 相同，且排在前面 → `df` 匹配到 `dm-62`

**为什么判为"不修"**：
1. 容量数值正确——用户关心的核心信息无损
2. 修复需要让 rootfs 外的宿主路径也可 `statvfs`（改变路径翻译的
   安全边界），影响面远大于收益
3. 标签差异只在 `df` 的显示列，不影响任何程序逻辑
   （没有程序依赖 `df` 的第一列做判断）

**排查路径**（完整，供复核）：`statvfs` → `getmntent` → `st_dev` →
`mountinfo` → 全部两侧一致 → 排除数据源 → 确认是 `df` 内部匹配顺序
+ 可见挂载集差异。

### 2.5 其他已知限制

- `audit_*` 5 个符号是**桩**（照抄官方行为，恒返回成功）——
  见 `docs/audit符号桩实现.md`
- fakeroot 下 setter"成功"但内核身份未变 —— **与官方一致**的
  兼容性取舍，非"正确"（见 `docs/身份查询与降权族-原始数据.md`）
- `tar cf t.tar .` 在**未配集中目录**时会包含 `.l2s.*` 中间文件 ——
  生产（launcher 默认 `BXROOT_L2S_DIR=<rootfs>/.l2s`）不受影响
- ASan 不可用（容器限制），用 ubsan 代替

### 2.6 seccomp 层与官方**完全对齐**（2026-09-17 实测确认）

用裸 svc 探针对比两侧对同一系统调用的响应（这是最底层的对照，
绕过一切符号钩子）：

```
号    含义            官方      bxroot
78    readlinkat     -14       -14     ← EFAULT：调用放行，参数问题
265   linkat         -38       -38     ← 被过滤器禁用（ENOSYS）
425   io_uring_setup -38       -38     ← 同上
```

**结论**：ldso 的 seccomp 过滤器对两侧表现**完全相同** ——
bxroot 与官方在 seccomp 层没有差异。这从最底层确认了：
- 官方 `link()` 成功**不是**因为它的 seccomp 放行了 linkat
  （它同样被禁，-38），而是因为**官方运行时在用户态模拟了 link**
- bxroot 的对应修法（link 失败自动启用 l2s）正是同一思路的
  独立实现，方向正确

此项为**验证性结论**（不是缺陷），把"ldso 过滤器是否对两个
运行时一视同仁"从假设变成了实测事实。


### 2.7 补充冒烟（2026-09-17）：locale/时区 —— 无缺陷

对 locale/时区相关操作做补充冒烟，确认无缺陷：

```
date                                  => Fri Sep 18 01:39:55 CST 2026  正常
ls /usr/share/zoneinfo                => ENOENT（两侧一致——rootfs 未装 tzdata）
ls /usr/share/zoneinfo/Asia; echo rc  => rc=2 稳定（3 次重复，无 segfault）
$LANG                                 => （空，与镜像默认一致）
```

rootfs 里**没有** `/usr/share/zoneinfo`（镜像未装 tzdata），
两侧行为一致。此前一次观察到的 "Segmentation fault" 经 3 次重复
复测**未再现**（判定为外层环境噪声/一次性事件），非 bxroot 缺陷。

### 2.8 补充冒烟：seccomp 层对照（已并入 2.6）

### 2.10 工具链 18 项全面对照（2026-09-17）：17 项完全一致

用 md5 对比两侧对同一命令的**完整输出**（不是 --version，而是真实行为）：

```
✅ whoami          ✅ uname -m         ✅ hostname
✅ stat /etc/passwd  ✅ readlink -f    ✅ dirname / basename
✅ date +%Y        ✅ sleep + echo     ✅ file /bin/sh
✅ wc -l           ✅ tr a-z A-Z       ✅ head / tail
✅ gzip -c | md5   ✅ bzip2 -c | wc    ✅ xz -c | md5
❌ env | wc -l     ← 实现细节差异（见下）
```

`env | wc -l` 的差异是**预期的实现细节**：两个 runtime 各自注入的
内部变量集不同（bxroot 有 `BXROOT_LD_PRELOAD`/`BXROOT_WORKDIR_DONE`，
官方有 `PROROOT_CFG_FD`/`PROROOT_ESCAPE_FD`）。程序**不应**依赖容器
内部变量名，这不是兼容性缺陷。

**结论**：18 项常用工具的行为与官方**无任何功能差异**——
这从工具链层面确认了 bxroot 与官方的兼容性水平。

对全部 12 项修复做"当前构建是否仍生效"的巡检（防止后续改动悄悄回退）：

| # | 修复项 | 复验方法 | 结果 |
|---|---|---|---|
| 1 | getpid 真值 | `echo $$` | ✅ 20522（非 1）|
| 2 | l2s 集中目录自建 | `test -d /.l2s` | ✅ 已建 |
| 3 | shebang exec | `./script.sh` | ✅ SB-OK |
| 4 | link 自动 l2s | 裸 `ln`（无开关） | ✅ OK |
| 5 | 身份 syscall 174/158 | 裸 svc | ✅ 174=0, 158=1（与官方一致）|
| 5b | getresuid 全 NULL 保留 EFAULT | 裸 svc | ✅ 4294967295（**有意保留**，官方=0）|
| 6 | dlerror | `dlopen` 失败后取错误串 | ✅ NULL（与官方一致——官方 dlopen 不写 dlerror）|

**唯一行为差异**仍是已记录的两条：`getresuid(NULL,NULL,NULL)` 保留
EFAULT（官方伪装成 0）与 `df` 的挂载点标签（数值一致）。见 2.1/2.4。

**复验方法论的教训**：容器视角/宿主视角的同 inode 关系让
`shutil.copy` 会在 `/root/x` 与 `$ROOTFS/root/x` 之间撞
`SameFileError`——**直接把文件放进 `$ROOTFS/root/` 下即可被两侧
看到，无需复制**。另：探针编译失败时 `grep -cE "error: "` 会因
输出为空而返回 0，**不要用它做编译成败判据**（本轮两次踩到），
应以产物文件是否存在为准。
