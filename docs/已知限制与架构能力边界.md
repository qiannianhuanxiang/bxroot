# 已知限制与架构能力边界

> 本文是 bxroot **当前已知限制的汇总清单**，每条都附实测依据与
> 详细报告链接。目的：让后续开发者一眼看到"哪些做不到、为什么做不到"，
> 避免在这些方向上重复投入。

## 一、架构级能力边界（LD_PRELOAD vs ptrace）

bxroot 是 **LD_PRELOAD 用户态路径翻译**架构；官方 proroot 是 **ptrace/
livepatch 架构**。两者的能力差异不是实现质量，而是**架构本身**：

| 能力 | LD_PRELOAD（bxroot） | ptrace（官方） |
|---|---|---|
| 符号层 libc 调用 | ✅ 可拦截 | ✅ 可拦截 |
| `syscall()` 符号 | ✅ 可拦截 | ✅ 可拦截 |
| **内联 svc**（glibc 内部） | ⚠️ 只能靠 livepatch 中和已知地址；路径类仅 openat 走 relay | ✅ 全程可见 |
| **内联 svc**（主程序 / 非 libc 的 .so，`mov x8,#号` 形态） | ✅ 构造期扫描改写（2026-10-31，见 2.14） | ✅ 全程可见 |
| **内联 svc**（号来自寄存器，如 Go `syscall.Syscall6`） | ⚠️ 仅 ULX 静态映像，需开启：`BXROOT_SVC_ALL=1`（改写）/ `BXROOT_SECCOMP_FALLBACK=1`（陷阱兜底），见 §2.17 | ✅ 全程可见 |
| **glibc 私有内部路径**（GLIBC_PRIVATE，不经 PLT） | ❌ **无法拦截** | ✅ 全程可见 |
| 子进程每次 syscall 观测 | ❌ 看不到 | ✅ 看得到 |

**由此产生的已知限制**（见下文具体条目）都源于同一件事：
某些调用路径**根本不经过任何导出符号**。

### 2.4 `df` 的挂载点标签不同（数值正确，2026-09-17 定位）

```
官方 : /dev/block/dm-13  495438082048 395546423296 99757441024 80% /
bxroot: /dev/block/dm-62 495438082048 395546423296 99757441024 80% /data/data/com.dsh.client
```

**数值部分（容量/已用/可用/百分比）逐字节一致**，只有设备名与挂载点
两个**标签**不同。

**根因（本轮定位，排查路径完整）**：
`df /` 的输出 = `statvfs("/")` 的数值 + 从挂载表里按 `st_dev` 匹配的标签。
bxroot 下两侧的 `statvfs`、`getmntent`、`st_dev`、`mountinfo`
**全部实测一致**（181 条挂载、`/` 的设备 `dm-13`、`st_dev=65086`）。

差异来自 **GNU df 的匹配顺序**：
- 无参数 `df` 会遍历挂载表并对每个挂载点调 `statvfs`
- 官方下 50 条可见（proroot 让宿主路径也可达），`/`（dm-13）在表前部
- bxroot 下只 5 条可见（宿主路径如 `/system`、`/data` 翻译后不存在，
  `statvfs` 失败被跳过），`/data`（dm-62）与 `/` **同一 f2fs 超级块**，
  `st_dev` 相同，且排在前面 → `df` 匹配到 `dm-62`

**为什么判为"不修"**：
1. 容量数值正确——用户关心的核心信息无损
2. 修复需要让 rootfs 外的宿主路径也可 `statvfs`（改变路径翻译的
   安全边界），影响面远大于收益
3. 标签差异只在 `df` 的显示列，不影响任何程序逻辑
   （没有程序依赖 `df` 的第一列做判断）

**排查路径**（完整，供复核）：`statvfs` → `getmntent` → `st_dev` →
`mountinfo` → 全部两侧一致 → 排除数据源 → 确认是 `df` 内部匹配顺序
+ 可见挂载集差异。

### 2.6 seccomp 层与官方**完全对齐**（2026-09-17 实测确认）

用裸 svc 探针对比两侧对同一系统调用的响应（这是最底层的对照，
绕过一切符号钩子）：

```
号    含义            官方      bxroot
78    readlinkat     -14       -14     ← EFAULT：调用放行，参数问题
265   linkat         -38       -38     ← 被过滤器禁用（ENOSYS）
425   io_uring_setup -38       -38     ← 同上
```

**结论**：ldso 的 seccomp 过滤器对两侧表现**完全相同** ——
bxroot 与官方在 seccomp 层没有差异。这从最底层确认了：
- 官方 `link()` 成功**不是**因为它的 seccomp 放行了 linkat
  （它同样被禁，-38），而是因为**官方运行时在用户态模拟了 link**
- bxroot 的对应修法（link 失败自动启用 l2s）正是同一思路的
  独立实现，方向正确

此项为**验证性结论**（不是缺陷），把"ldso 过滤器是否对两个
运行时一视同仁"从假设变成了实测事实。

### 2.12 多线程并发（2026-09-18 分级评估）

评估报告 8.7 指出全项目 26+ 个 static 可变全局无锁。逐项评估后**分级**
处理，而非一律加锁：

| 域 | 结构 | 性质 | 处置 |
|---|---|---|---|
| fakeroot 账本 | `g_fakeroot.by_path/by_inode` | **读-改-写并发**（realloc + 计数递增 + 键所有权转移） | ✅ **已加自旋锁**（见下） |
| l2s | `g_ops` / `g_enabled` | **只写一次、之后只读**（构造函数单线程发布） | 保持原样（不可变发布，非竞态） |
| preload 配置 | `g_config.*` | 初始化后只读 | 保持原样 |
| crash handler | `g_in_handler` | `volatile sig_atomic_t`，信号语义 | 保持原样 |

**fakeroot 账本（唯一的真实竞态）**：并发压测（8 线程 × 400 键，
`test/t_concur.c`）在无锁版**稳定复现堆破坏**：
`double free or corruption`、`malloc(): unaligned tcache chunk`。
根因是 `fr_map_compact`（整表 realloc）与 `fr_map_probe`（按 cap 取模
遍历）并发放行 —— node worker / pnpm 并发 IO 的真实路径。

修法：加自旋锁（`__atomic` CAS + `yield`），选择自旋而非 `pthread_mutex`
是为保住本库零 libc 依赖（`-nostartfiles` 构建）。锁可重入
（`_Thread_local` 持锁深度），因账本内部有嵌套调用链
（`fr_record_both → fr_map_update → put`）。

回归：`test/RUN_CONCUR.sh` 两阶段（小容量压重哈希查堆破坏；大容量
关淘汰查丢更新），已挂入 `RUN_ALL`。加锁后恒 PASS，无锁版阶段 A 崩溃。

**未做的**：`l2s`/`preload` 的静态全局按上表判定为不可变发布，未加锁。
若将来出现"运行期可变的共享全局"，需重新评估。

### 2.13 容器内 `LD_PRELOAD` / `BXROOT_ROOTFS` 无法清除（设计，2026-10-31 补文档与告警）

**现象**：容器内 `env -u LD_PRELOAD`、`env -i`、`LD_PRELOAD=`、`BXROOT_NO_AUTORUN=1`
四种写法，子进程里 `LD_PRELOAD` 都还在；`export BXROOT_ROOTFS=<别的路径>`
（甚至不存在的路径）后，子进程看到的仍是原 rootfs。

**原因**：每个 exec 出口（execve/execvp/posix_spawn/system/popen）都经
`px_runtime_build_env` → `px_build_forced`，以 `PX_ENV_SET` 把本进程的
`LD_PRELOAD` / `BXROOT_ROOTFS` / `PROROOT_ROOTFS` 写进子进程 envp，覆盖调用方给的值
（`src/proc/proc.c` 的 `px_build_forced`）；进程内 setenv/putenv/unsetenv/clearenv
钩子也会立即恢复这几项（`preload.c` 的 `FR_CRITICAL_ENV`）。

**为什么不加"不注入"逃生开关**：在 Android 上，rootfs 里的 ELF 不能被内核直接执行
（app 数据目录禁 exec），必须经 ULX / static_exec。一个不带 runtime 的子进程要么
EACCES，要么按宿主路径解析——`/bin/echo` 会落到 `/system/bin/echo`（Android
toybox），**进程已逃出容器**，测到的也不是"无 bxroot 的同一棵树"。所以容器内
**不存在**干净基线，开关只会制造看似可用的假对照。

**正确做法**：
- 要对照"翻译 vs 不翻译"：用**同一份源码的静态 / 动态两种编译形态**，或在容器外跑。
- 要用别的 rootfs：嵌套启动 launcher，`libbxroot.so -r <rootfs> <cmd>`
  （launcher 会 setenv 新的 `BXROOT_ROOTFS`）。
- 容器内显式给出不同的 `BXROOT_ROOTFS` 时，runtime 现在会往 stderr 打**一行**告警
  （每进程一次，行为不变）。

**`BXROOT_NO_AUTORUN=1` 不是隔离开关**：它只让构造函数提前返回。`LD_PRELOAD` 仍在、
库仍被加载、导出符号的钩子仍然生效，只是配置没初始化——进程处在半初始化状态。
它只供"把 preload.c 静态编进单元探针"的源码级测试用，不要拿它做基线。

**另：`BXROOT_ENTER` 不是开关**，是 `libbxroot-enter.so` 的宿主路径（native session v3），
`BXROOT_ENTER=1` 没有任何作用。

### 2.14 内联 svc 的路径翻译（2026-10-31）

两个容易读混的概念：

| 写法 | 经过的入口 | bxroot |
|---|---|---|
| `syscall(291, …)` | libc 导出的 `syscall` **函数** | ✅ `syscall_guard.c` 拦截 |
| `mov x8,#291 ; svc #0` | **一条指令**，不经任何符号 | 视映像而定，见下 |

README 里"libuv 用 `syscall(291,…)` 所以必须接管 `syscall()`"说的是前者。

按映像分：

| 映像 | 路径类内联 svc |
|---|---|
| 静态程序（gcc -static、musl 静态） | ✅ `static_exec` 装载时改写（含 execve/execveat，2026-10-31） |
| 动态程序的**主程序与非 libc 的 .so** | ✅ runtime 构造函数里 `bxroot_inline_svc_scan` 改写（2026-10-31 新增） |
| `libc.so.6` 内部 | ⚠️ 只有 openat 走 relay；其余由符号钩子覆盖。**刻意不全改**：runtime 自己的钩子会有意用宿主路径调 libc（host-world 等），全改会把这些路径误翻进 rootfs |
| `ld-linux*`、`libbxroot*`、外层 `libproroot*` | 不改（加载器 / 本项目与外层组件，裸 svc 是有意为之） |

**动态映像改写的识别与边界**（与静态程序同一套 `sx_scan`）：
- 只认 `mov x8,#立即数` 后 12 条内跟 `svc #0`，中途遇到改写 x8 或任何分支即放弃；
  号必须在路径类 / getcwd / readlinkat / execve 集合里；
- 先只读计数，0 命中的映像不改任何内存属性；有命中才把该段临时改写，改完复位 r-x；
- veneer 池放在该段 ±128 MB 内，够不着的站点跳过（fail-open）；
- 单段超过 64 MB 不扫（大映像如 node 本身走 libc）；
- `BXROOT_NO_INLINE_SVC=1` 关闭。

**仍覆盖不到**：
- 系统调用号来自寄存器的通用包装（Go 的 `syscall.Syscall6`、部分 JIT）——指令形态里
  没有立即数，无法静态判定号；
- 构造函数之后才 `dlopen` 进来的库。

**实测**（容器内模拟真机：runtime 在 rootfs 外，非默认 rootfs）：同一个内联 svc 探针

| | 修前 | 修后 |
|---|---|---|
| 内联 openat("/etc/marker") | -2 (ENOENT) | fd，读到 rootfs 内容 |
| 内联 newfstatat | -2 | 0，inode 与 libc stat 一致 |
| 内联 getcwd | 宿主路径 | guest 路径 |

bash / ls / python3 / git / node 在新版下命中 0 段、行为与耗时不变。

### 2.16 原生调用接入发行版（2026-11-01）

第一～三版原生调用（`bx-host` / `BXROOT_AUTO_HOST` / `BXROOT_REENTRY`）此前只在
源码里，发行 tarball 与 DSHA APK 都**没带** `bx-host` 和 `libbxroot-enter.so`，所以
在 DSHA 里用不了。本轮接入时又查出两个缺陷：

- **未提交的 raw svc 改法让分类器读错文件**。`host-world.c` / `bx-host.c` 曾把
  `svc` 包进 `stp/ldp` 压栈。在外层装载器会改写 svc 站点的进程里，
  `RUN_HOST_DISPATCH` 从基线 23 项失败变成 56 项（`real classifier reads bionic
  fixture` 等）。改成 x1..x5 用 `"+r"` 读写声明、不在 asm 里动 sp 之后，失败集合
  与 HEAD 逐项相同。`session.c` 的压栈版有单独的 A/B 证据，保留不动。
- **`bx-host` 自己的 execve 被 static_exec 改写回 exec 钩子**。`bx-host` 没有
  PT_INTERP，在 guest 里由 static_exec 进程内装载；它的 `mov x8,#221; svc` 被改写
  进 runtime 的 exec 钩子，钩子按 guest 程序处理，给 bionic 程序注入 glibc 的
  `LD_PRELOAD`：
  `CANNOT LINK EXECUTABLE "getprop": library "libc.so.6" not found`。
  仅当 `BXROOT_AUTO_HOST=1` 时钩子会再分流回宿主，所以以前只有开了自动分流才
  “碰巧”能用。现在 execve 号先放进 volatile 变量再 `mov x8, xN`，扫描器只认
  movz 立即数，不改写这个站点；其它 svc（openat 等）照常翻译。

同环境实测（外层 proroot 容器，bridge+linker 装载 runtime，`/system` 与 `/apex` bind）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `bx-host getprop ro.product.model`（AUTO_HOST=0） | CANNOT LINK … libc.so.6 | `V2352A` rc=0 |
| `bx-host /system/bin/sh -c '…; exit 7'` | 同上 | 输出正确，rc=7，`LD_PRELOAD` 为空 |
| `bx-host /usr/bin/true` | — | 拒绝，rc=126 |
| AUTO_HOST=1：`getprop` / `/system/bin/getprop` / `toybox uname -m` | — | `V2352A` / `16` / `aarch64` |
| AUTO_HOST=0：`getprop` | — | command not found（默认行为不变） |
| 原生 sh → `linker64 $BXROOT_ENTER -- /usr/bin/printf` | — | `back-to-guest`，rc=0 |
| 原生 sh → 回入 guest bash `exit 5` | — | 读到 Ubuntu os-release，rc=5 |
| 回入口经 ULX 装载链（与 APK 同） | — | 同上通过 |

回归（同环境对照 HEAD）：HOST_EXEC / HOST_WORLD(77) / NATIVE_SESSION(18 cases) /
ENTER_ELF 通过；HOST_DISPATCH 23、HOST_SESSION 33 项失败与 HEAD 逐项一致（外层
proroot 环境）；HOST_ENTER 失败 100 项，HEAD 为 109 项；D4 915 checks 通过。

接入后又查出三处，均已修：

- **跳板没保存 x18**。static_exec / 内联 svc 跳板保存 x1..x17、NZCV、q0..q31，漏了
  x18。内核跨 svc 保留 x18，GCC（非 Android 目标）也把它当普通临时寄存器用；跳板里
  的 C 代码改写 x18 后回到站点，程序拿到的就是垃圾。实测 `bx-host` 把
  `BXROOT_SESSION_FD` 的值指针放在 x18 里跨 getcwd，回来变成 `0x5` → SIGSEGV
  （只在设了会话 fd 时出现）。现在两个跳板都保存/恢复 x18（帧内 #168 空位），
  `bx-host` 另以 `-ffixed-x18` 编译。
- **会话记录的 runtime 取错**。`native-session.c` 先信 `PROROOT_LIB_PATH`；外层是
  proroot 时它指向 `libproroot-runtime.so`，回入的 guest 跑在别家 runtime 下，自动
  分流失效。改为先用 dladdr 取本库实际路径。
- **会话装载链取错**。同理先信 `PROROOT_TRAMPOLINE_PATH`，会回落到对方的 vendor
  linker，它只接受自家 runtime（`DSHA_PROROOT_PRELOAD_ENTRY_UNAVAILABLE
  stage=ARGV_PRELOAD_VENDOR`）。改为先用 launcher 设的 `BXROOT_ULX_*`。

验收脚本 `test/device/run-native-calls.sh`（容器内模拟 DSHA 启动方式：单文件 bind
提供 `bx-host`、AUTO_HOST + REENTRY 全开）：**pass=21 fail=0 skip=1**，跳过项是
`pm list packages`（App UID 无权限，属 Android 正常拒绝）。覆盖 python
`subprocess` / node `execFileSync` 调 `getprop`、原生 sh 回入 guest、rc 透传、
`--to-host` 路径转换和 guest→host→guest→host 四层链。

注意：本容器里 guest 程序位于 App data，内核不许直接 exec，所以模拟时装载链要指向
可执行的 nativeLibraryDir 程序。DSHA APK 里 ULX 本来就在 nativeLibraryDir，满足这一点。

会话建立失败时，runtime 现在只警告一次，并把 `BXROOT_REENTRY` 降为 0 写回环境，
子进程不再每条命令重复刷同一警告；guest→host 单向调用不依赖会话，照常可用。

**边界不变**：身份仍是 App UID；`pm`、`dumpsys` 等是否可用由 Android 的 UID /
SELinux / Binder 权限决定。没有 Termux companion、没有跨 App 代执行。以上不是
真机 DSHA 验收，真机结果以 `test/device/run-native-calls.sh` 的输出为准。

## 附二：验收硬判据 —— guest 的 stderr 必须干净

**背景**：一次中间构建残留了 14 处调试 `fprintf(stderr, "[dbg] …")`，
分布在 `stat`/`open`/链接展开的热路径上。后果有二：

1. 所有 guest 程序的 stderr 被污染（一次 `make` 产生 ~1.4 MB 噪音）；
2. 疑似引发 `ar` 的 `malloc(): invalid size` 段错误
   （见 `docs/调查-ar段错误无法复现.md`）——**高频、重入式的分配**。

**因此把下面两条加为验收硬判据**（任何一轮验收都应先跑）：

```sh
cd /root/bxroot
# ① 二进制里不能有调试标记
strings build/libbxroot-runtime.so | grep -cE '\[dbg\]|LOOPDBG|STATDBG|OPENDBG'   # 必须为 0

# ② 一条普通命令的 stderr 必须是空的
./tools/bxroot-run -- /bin/echo x 2>&1 >/dev/null | wc -l                          # 必须为 0
```

② 的意义不只是"它不吵"：**stderr 非空本身就是"钩子里有额外 I/O"的证据**，
而钩子里的 I/O 会带来重入式分配风险。

**当前状态**：两条均满足（源码与二进制都已确认无调试残留）。

## 2.17 seccomp 兜底层（静态映像，默认关闭）

源码 `src/runtime/seccomp_fallback.c`（被 `static_exec.c` 包含）。`BXROOT_SECCOMP_FALLBACK=1`
（按**目标** envp 判定）时，`px_static_exec` 跳进映像前叠加一层自己的 seccomp 过滤器：路径类
系统调用 + `rt_sigaction`/`rt_sigprocmask`，且 `instruction_pointer ∈ [映像 lo, hi)` 才
`SECCOMP_RET_TRAP|0x0bb1`，其余 ALLOW。runtime、veneer、跳板、bionic 都在范围外，所以经改写的
站点不进陷阱，只有改写漏掉的 svc（号来自寄存器、运行期生成的代码）才进。

- SIGSYS 处理器：`si_errno==0x0bb1` → 切回 runtime TLS 调 `px_static_dispatch`；其它 seccomp
  陷阱（Android 外层过滤器）→ 原 `sx_early_sigsys`；kill 来的 → guest 影子处理器。
- guest 在范围内改 SIGSYS 只进影子槽；`sa_mask` 和 `rt_sigprocmask` 新集合剔除 SIGSYS
  （后者直接改 `uc_sigmask`：处理器里真调会被 `rt_sigreturn` 覆盖，单测实测过）。
- 代价（真机探针）：过滤器每个 syscall 约 +90 ns，陷阱约 9–20 µs；容器单测：陷阱 openat+close
  约 3.2–3.7 µs。只能兜底，主路径仍是改写。

验证（容器，aarch64）：`test/test_seccomp_fallback.c` A–I 全过（翻译、范围外不翻译、非陷阱号
不进陷阱、影子 SIGSYS、mask 剔除、kill 转发、fork 继承、过滤器下 execve 动态程序）；
`test/test_seccomp_fallback_e2e.c` 经真实 `px_static_exec` 装 `test/data/sfb_guest.S`：关闭时
`/bxtest/hello` ENOENT，开启时翻译成功。完整 `BUILD_RUNTIME.sh` 可链接。

未验证、所以默认关闭：
- 真机上继承过滤器的**原生**子进程（bionic 代码若恰好映射进 `[lo, hi)` 并发路径类调用，没有
  处理器 → SIGSYS 杀进程）。经验上 ET_EXEC 静态程序在 `0x400000` 附近，Android 原生映射在
  `0x5x…/0x7x…`，但这不是保证。
- 真 Go 二进制（gsignal 栈、SIGURG 抢占与陷阱的交互）。
- guest 自己调 `seccomp()`/`prctl(PR_SET_SECCOMP)` 不拦；每次静态→静态 exec 叠加一层过滤器
  （约 51 条指令，内核总上限 32768 条）。

## 2.18 Termux 路径兼容（默认开启）

专为 Termux 写的脚本常把前缀写死（shebang `#!/data/data/com.termux/files/usr/bin/bash`、
`$PREFIX/etc/...`、`~` 展开成 `/data/data/com.termux/files/home`）。`translate_path` 先用
`src/runtime/termux_compat.h` 把 Termux 布局改写成 Ubuntu 布局，再走常规翻译（bind、rootfs
前缀、`..` 夹紧照旧）：

| Termux 路径 | guest 路径 |
|---|---|
| `$PREFIX/tmp` / `etc` / `var` | `/tmp` / `/etc` / `/var` |
| `$PREFIX`（bin/lib/share/include…） | `/usr` |
| `/data/data/com.termux/files/home` | `/root` |

`$PREFIX` 认 `/data/data/com.termux/files/usr` 与 `/data/user/0/com.termux/files/usr`。
rootfs 本身在 `com.termux` 之下（bxroot 跑在真 Termux 里）时自动关闭；`BXROOT_NO_TERMUX_COMPAT=1`
显式关闭。不设 `PREFIX` / `TERMUX_VERSION`，避免通用脚本误走 Termux 专用分支。

边界：只解决路径；`pkg` 包名、Termux 的 bionic 二进制、Termux:X11/Boot/Widget 等配套 App 不在范围内。
runtime 增加约 520 字节。验证：`test/probe_termux_compat.c`（纯函数 38 项）、
`test/RUN_TERMUX_COMPAT.sh`（真实 runtime 8 项；旧 runtime 只过 opt-out 一项）；`RUN_DEVSHM`、
`RUN_ESCAPE`、`RUN_FUZZ_PATH`、`RUN_ALT_ROOTFS` 新旧 runtime 失败项完全一致（本容器既有环境失败）。
