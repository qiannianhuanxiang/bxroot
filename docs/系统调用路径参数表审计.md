## 2. ★ 三种干扰源：为什么"实测"在本环境要格外小心 ★

这是本审计最重要的方法论收获。**本容器不是一台干净的内核**，
同一个裸 `svc` 的结果可能来自三个完全不同的地方：

```
       客户 raw svc
            │
            ▼
   ┌────────────────────┐
   │ ① seccomp 过滤器   │  proroot 装的，对 ~214 个编号直接返回 ENOSYS
   │  (SECCOMP_RET_TRAP)│
   └────────┬───────────┘
            │ 未被拦
            ▼
   ┌────────────────────┐
   │ ② proroot SIGSYS   │  对另一批编号**仿真**，errno 由 proroot 给出
   │    仿真层          │  不再经过内核的路径解析
   └────────┬───────────┘
            │ 未被仿真
            ▼
   ┌────────────────────┐
   │ ③ 真·内核          │  只有走到这里，errno 才真正来自内核
   └────────────────────┘
```

### 2.1 干扰源 ①：seccomp 伪造的 ENOSYS

**【实测】** 全零参数扫描 0..441，得到 **214 个**返回 ENOSYS 的编号。
其中包括：

```
39 umount2   40 mount   51 chroot   180 mq_open   181 mq_unlink
264 name_to_handle_at   265 open_by_handle_at   273 finit_module
428 open_tree  429 move_mount  430 fsopen  431 fsconfig  433 fspick
437 openat2    439 faccessat2  442 mount_setattr  452 fchmodat2
```

这些编号在 `asm-generic/unistd.h` 里**确定存在**，其中 `mount`/`chroot`
是 Linux 1.x 就有的调用。**所以这里的 ENOSYS 只可能由 seccomp 伪造。**

**【实测】编号上限的独立判定**（扫描 400..500，全零参数）：

```
最后一个被派发的号 = 441
442 起全部 ENOSYS（442..461 全在内）
```

内核在派发前用 `nr >= __NR_syscalls` 挡掉越界号，所以 **441 就是本内核的
编号上限**，与 aarch64 asm-generic 编号表完全吻合（`clone3`=435、
`pidfd_getfd`=438、`faccessat2`=439 都在上限内且非 ENOSYS）。

> **推论：≤441 的任何 ENOSYS 都是策略产物，不代表内核没有该调用。**

### 2.2 干扰源 ②：proroot 的 SIGSYS 仿真层

**【实测】** proroot 用 `SECCOMP_RET_TRAP` 把一批调用拦下来，在自己的
处理器里仿真，再把结果写回。判定手段是读 proroot 自己写的日志
（`PROROOT_SIGSYS_LOG_HOST_PATH` 指向的文件，内容形如
`[proroot-hook] SIGSYS trapped syscall=439 pc=... pid=...`）。

实测**被仿真**的编号：

```
39 40 51 180 181 264 265 428 429 430 431 433 437 439 442 452 457 458
```

**为什么这对本审计是致命的**：被仿真的调用**不经过内核的路径解析**，
于是"伪指针 → EFAULT"这条核心判据完全不成立。`faccessat2` 就是活例
（**【实测】**）：

| 调用 | 实测结果 | 若按内核判据解读 |
|---|---|---|
| `439(AT_FDCWD, "/tmp", 0, 0)` | `0`（成功） | 合理 |
| `439(AT_FDCWD, 999999, 0, 0)` | `EPERM` | ❌ 内核应给 EFAULT |
| `439(999999, "/tmp", 0, 0)` | `0` | ❌ 内核应给 EBADF |
| `439(999999, "rel", 0, 0)` | `EPERM` | ❌ 内核应给 EBADF |
| `48(999999, "rel", 0, 0)` 对照 `faccessat` | **`EBADF`** | ✅ 这才是内核行为 |

**结论：若照搬"伪指针应 EFAULT"的判据，会得出"439 的 a1 不是路径"这个
错误结论**，进而把一个正确的表项误判为缺陷。本测试加了仿真层探测后，
把所有被仿真的编号一律标为"未实测"，只给【文档】级结论。

### 2.3 干扰源 ③：libc 与 raw 的路径命名空间不同

**【实测】** 本容器里 proroot 的路径重定向**只作用于 libc 层**：

```
libc  open("/tmp/x", O_CREAT)      → 真建在 <rootfs>/tmp/x
raw   openat(AT_FDCWD, "/tmp/x")   → 看的是**宿主**的 /tmp
```

实测对照：

| 操作 | 结果 |
|---|---|
| `libc stat("/tmp/mixtest2")` | `0`（成功，libc 侧可见） |
| `raw statx("/tmp/mixtest2")` | `-1 ENOENT`（**raw 侧看不见**） |
| `raw getcwd()` | `/data/data/com.dsh.client/files/linux/ubuntu/tmp/<cwd>`（宿主真实路径） |
| `raw statx("/tmp")` | `0`（宿主 /tmp 存在，与 libc 的 /tmp **不是同一个**） |

**这是本测试第一版出现满屏假 FAIL 的根因**：夹具用 libc 的 `mkdir`/`open`
创建，探针却用 raw `svc` 去查 —— 探针永远 ENOENT，看起来像"参数位置错了"。

**修法**：沙箱**全部用 raw svc 创建**（`raw_mkdir`/`raw_create`/`raw_symlink`），
并挂在 `raw getcwd()` 返回的宿主路径下；子进程用 **raw `chdir(49)`** 进入
沙箱（libc 的 `chdir` 会被 proroot 换掉，对 raw 侧无效）。

### 2.4 附带发现：本环境不允许硬链接

**【实测】** 沙箱所在目录**禁止创建硬链接**（哪怕用 libc 的 `link()` 也
`EACCES`）。所以"成功建出硬链接"**不能**作为 `linkat` 的判据。
改用四寄存器三态判决（伪指针→EFAULT、伪 fd→EBADF），两条都发生在建链
之前，因此在本环境完全可用。

### 2.5 附带发现：renameat 类调用有破坏性副作用

**【实测】** `renameat`/`renameat2` 会**真的把源改名走**。第一版让它们与
`linkat` 共用夹具 `rel_f1`，于是 `run_measure` 跑完 38/276 之后 `rel_f1`
已不存在，后续所有用到它的实验全部 ENOENT —— 表现为"参数位置错"，
实则是夹具被前一个实验吃掉了。已改为**专用源名 + 每次在子进程里重建**。

### 3.2 ★★ `case 260`：审计期间发现的致命错误（现已被并行修改者修复）★★

审计**开始时**的表里有 `case 260: return 1;`，注释写的是 `linkat`。
**这是错的，而且是会主动制造故障的那一类错。**

**aarch64 上 260 是 `wait4`，`linkat` 实际是 37。**（**【文档】**
`asm-generic/unistd.h`：`__NR_wait4 260`、`__NR_linkat 37`）

**【实测】** 四重独立证据：

| # | 实验 | 实测结果 | 排除了什么 |
|---|---|---|---|
| ① | `260(-1, NULL, WNOHANG, NULL)` | `ECHILD` | 只有 wait 家族在无子进程时返回 ECHILD |
| ② | `260(pid, <只读地址>, 0, NULL)` | `EFAULT` | a1 是**只写输出缓冲**；路径型调用此处会**成功读**该串 |
| ③ | `260(pid, &ws, 0, NULL)` + `_exit(42)` 子进程 | 返回子 pid，子进程内读到 `ws=0x2a00` → `WIFEXITED=1, WEXITSTATUS=42` | 只有 wait 家族会写 `wstatus` |
| ④ | 把 linkat 的参数布局原样丢给 260 | `ECHILD` | 若 260 是 linkat，`AT_FDCWD` 会被当 dirfd 并正常执行 |

#### 危害机制（**【实测】复现**）

这不是"少翻译一条"，而是**静默数据错写**：

```
① 表返回 1  →  guard 把 a1 当 `const char *` 读首字节
② wait4 的 a1 是 `int *wstatus`（**输出**缓冲）
③ 被信号 N 终止的子进程 wstatus == N；N=47 时 wstatus == 0x2f
   首字节 = 0x2f = '/'  →  looks_like_guest_abs_path() 返回真
④ guard 把 a1 **替换成自己的翻译缓冲**，内核把退出状态写进缓冲
⑤ 调用方的 wstatus 永远保持原值  →  **静默数据错写**
```

**【实测】** 扫描信号 1..63，**只有信号 47** 使 `wstatus` 首字节等于 `0x2f`；
实验 C2 用哨兵 `0x5A5A5A5A` 预置缓冲，确认该通道成立。

> 故障只在信号号恰好让首字节变成 `'/'` 时出现 —— **极难排查**。
> 这正是"猜参数位置比不翻译更危险"的第二个实例：
> 第一个是崩溃（symlinkat），第二个是**静默数据错写**。

**现状**：并行修改者已删除 `case 260` 并把 `linkat` 正确列为 37。
本审计**实测确认**该修复正确。

## 8. 本次审计发现的测试夹具陷阱（留给后来者）

审计过程中本测试自身踩了 6 个坑，全部记录在测试文件注释里。
**它们同时也是理解本环境的钥匙** —— 任何在本容器里做 raw syscall 实验的人都会遇到：

| # | 陷阱 | 症状 | 正解 |
|---|---|---|---|
| 1 | **路径串放在 `baseline_for()` 的栈帧里** | `run_call` 在 `pipe()` 后才 `fork()`，子进程解引用到已被覆盖的栈内存 → 伪指针探针得 ENOENT 而非 EFAULT，满屏假 FAIL + proroot SIGSEGV 报告 | 路径串改用**静态**缓冲（`g_s_f1` 等） |

| 3 | **夹具用 libc 建、探针用 raw 查** | 两套路径命名空间 → 探针永远 ENOENT | 夹具也走 **raw svc**（§2.3） |
| 4 | **`wait4` 的探针带了 setup** | setup 把 a0 覆盖成真 pid，探针失效 → 误判"a0 是路径" | 非路径型判据对 260 **不带 setup** |
| 5 | **renameat 吃掉共享夹具** | 改名有破坏性副作用，后续实验全 ENOENT | 专用源名 + 每次在子进程里重建（§2.5） |
| 6 | **以为 proroot 只转发不仿真** | 439 的 errno 来自仿真层，按内核判据会得出**相反结论** | 先做仿真层探测（§2.2） |
