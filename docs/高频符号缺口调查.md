## 0. 先纠正三条前提

### 0.1 `$ROOTFS/root` 就是 `/root` 本身（同一 inode）

```
/root           dev=65086 ino=5995611
ROOTFS/root     dev=65086 ino=5995611   → 同一 inode = True
```

所以"落地目录必须在 ROOTFS 内"这条要求，用 `/root/mmapprobe/` 就**自动满足**。
但也要注意反面：**我往 `/root/mmapprobe/` 里写东西，等于直接改动 rootfs 里
的文件**；收尾时我只删自己的探针目录。

### 0.2 官方 runtime 只认 `PROROOT_`（已核实）

```
$ strings -a work/parity/off/libproroot-runtime.so | grep -c BXROOT

$ strings -a work/parity/off/libproroot-runtime.so | grep -oE 'PROROOT_[A-Z0-9_]+' | sort -u | wc -l
```

给官方传 `BXROOT_*` 时它**一个都不读**，那侧跑的是默认配置 —— 不是对照实验。

bxroot 侧 `BXROOT_ROOTFS/BXROOT_TMP_DIR`，两侧同一套
`bridge + linker + --argv0 + --preload` 命令（脚本见 §6.1）。

## 1. 核心问题：官方为什么导出这些 libc 符号？

### 1.1 结论：是 `--preload` 的**选择性符号抢占**，不是"全量抄袭 libc"，也不是"碰巧带进来"

**证据1（实测）：这 7 个符号的 PLT 槽全部指向官方 runtime。**

探针 `callprobe.c` 真调用这 7 个函数各一次，然后解析**自己的
`.rela.plt`** 拿 GOT 槽地址、读槽值 —— 这是"普通 PLT 调用到底跳到哪"的
直接证据（不经过任何 `dlsym`，所以不受我们自己的 `dlsym` 钩子影响）：

```
主程序基址 = 0x7108c6e000

mmap             [rela.plt] 槽 +0x1ff40  -> .../libproroot-runtime.so+0x1a84c
mmap64           [rela.plt] 槽 +0x1ff98  -> .../libproroot-runtime.so+0x1a8f0
dl_iterate_phdr  [rela.plt] 槽 +0x1ff50  -> .../libproroot-runtime.so+0x22fec
dlerror          [rela.plt] 槽 +0x1fec0  -> .../libproroot-runtime.so+0x22fa0
pthread_create   [rela.plt] 槽 +0x1ff68  -> .../libproroot-runtime.so+0x104b0
pclose           [rela.plt] 槽 +0x1ff80  -> .../libproroot-runtime.so+0x27da0
sem_wait         [rela.plt] 槽 +0x1fed0  -> .../libproroot-runtime.so+0x23900
getpid           (该程序没有它的 PLT/GOT 槽 —— 未调用)
malloc           [rela.plt] 槽 +0x1ff08  -> .../libc.so.6+0x96490      ← 对照
```

槽里的偏移量与 `nm -D` 给出的符号地址**逐位吻合**
（`mmap`=0x1a84c、`sem_wait`=0x23900 …），所以这些槽确实由 runtime 提供。
**`malloc` 仍指向 libc** —— 说明抢占是"按下标挑选"的。

**证据2：官方**只**抢占了它实现的那一部分，绝非"插在 libc 前面就什么都得提供"。**

```
$ nm -D --defined-only 官方runtime | grep 这些常用 libc 符号
malloc        未导出 → 走 libc       memcpy    未导出 → 走 libc
calloc        未导出 → 走 libc       memmove   未导出 → 走 libc
free          未导出 → 走 libc       memset    未导出 → 走 libc
realloc       未导出 → 走 libc       strlen    未导出 → 走 libc
printf        未导出 → 走 libc       getpid    未导出 → 走 libc
exit          未导出 → 走 libc       write     未导出 → 走 libc
abort         未导出 → 走 libc       read      未导出 → 走 libc
pthread_mutex_lock 未导出 → 走 libc
close         导出       fopen     导出
```

这条**直接否掉了"必须全量提供 libc 符号否则解析失败"的猜想**：
官方自己就没提供 `malloc`，而程序照样跑。

**证据3：官方头文件级别的结构也印证"抢占 + 从 libc 解析"混用。**

```
$ readelf -d 官方runtime | grep NEEDED
 (NEEDED)  Shared library: [libc.so.6]
 (SONAME)  Library soname: [libproroot-runtime.so]
$ nm -D -u 官方runtime | wc -l     # 未定义符号
   大量 @GLIBC_2.17 / @GLIBC_2.34 / @GLIBC_2.38
```

它**依赖 libc**，只把自己实现的那部分"盖"在 libc 上面。

**证据4（对照实验，最硬）：把官方 runtime 换个文件名，抢占立刻消失且进程崩溃。**

```
B: 官方内容 + 非官方名字 libmisnamed-runtime.so
   → dl_iterate_phdr 回调 5 次（成功）
   → [proroot] SIGSEGV pc=0x726a1e19b4 lr=0x726a1e1978 fault=0x1fe30 code=1
     x0 =0x000000000001fe30 x1 =0x000000000001fe30 ...   ← 访问 0x1fe30（未映射）
```

**证据5（反向对照）：把 bxroot 内容改成官方文件名，抢占**也没有**发生。**

```
A: bxroot 内容 + 官方名字 libproroot-runtime.so
   主程序基址 = 0x781eed8000
   mmap             [rela.plt] 槽 +0x1ff40  -> .../libc.so.6+0xe7320   ← 仍是 libc
   ...
   （另有 CANNOT LINK EXECUTABLE "sh": library "libc.so.6" not found）
```

A 与 B 合起来说明：**决定"是否被当作 runtime 来抢占"的既不是文件名、
也不是 SONAME 字符串本身**，而是官方 loader 对"通过 `--preload` 加载的
那个对象"的记账。具体判据（按路径？按 inode？按 `PROROOT_LIB_PATH`？）
**我没有找到**，列在 §5 未确定项。

我**不加任何 bridge/`--preload`**，直接跑一个刚编译的探针（`env -i ./symprobe`，
连环境变量都清空），结果：

```
SYM mmap               ptr=0x7cc52a284c  .../libaroot-runtime.so+0x1a84c
```

**我没能定位注入点**（已排除 ld.so.preload / env / 改造 ld.so），列在 §5。
这不影响本报告任何结论，但对**后续所有 agent 的测试方法论有影响**：

> ⚠️ **在本工作区里，任何"裸跑"的程序都已经被官方 runtime 抢占。**
> 要拿 bxroot 的真实行为，**必须**走 `bridge + linker + --preload` 那条路；
> 想拿"没有 runtime"的基线，我实测**做不到**（不加 `--preload` 时
> `sigsys: trap on syscall nr not on allow-list, terminating` 直接终止）。

### 2.1 `mmap`（官方 @0x1a84c）

**官方反汇编（全文关键指令）：**

```asm
000000000001a84c <mmap@@Base>:
   1a84c: stp  x29, x30, [sp, #-96]!
   1a854: add  x6, sp, #0x5c              ; x6 = &fallback_flag（栈上，已置 0）
   1a85c: sxtw x20, w2                    ; prot 符号扩展（32→64）
   1a860: mov  x2, x20
   1a868: sxtw x21, w3                    ; flags
   1a86c: sxtw x22, w4                    ; fd
   1a88c: str  wzr, [sp, #92]             ; fallback_flag = 0
   1a890: bl   6110 <proroot_drm_mmap@plt>   ★ 先问 DRM 层
   1a894: ldr  w1, [sp, #92]                 ; 读回 flag
   1a898: cbz  w1, 1a8cc                     ; flag==0 → 走真实 mmap
   ... (flag!=0 的返回/errno 处理)
   1a8cc: mov  x6, x25
   1a8d0: mov  x5, x22
   1a8d4: mov  x4, x21
   1a8d8: mov  x3, x20
   1a8dc: mov  x2, x24
   1a8e0: mov  x1, x23
   1a8e4: mov  x0, #0xde                  ; #222 = __NR_mmap
   1a8e8: bl   8740 <clearenv@@Base+0xe0>  ; 裸 syscall(222, ...)
   1a8ec: b    1a89c
```

**`proroot_drm_mmap` 本体（@0x17180，可判定语义）：**

```asm
0000000000017180 <proroot_drm_mmap@@Base>:
   17180: cbz  x6, 172ac            ; 无 out 参数 → 返回 -14 (EFAULT)
   1719c: str  wzr, [x6]            ; *out_flag = 0
   171a0: tbz  w3, #5, 171b8        ; ★ flags bit5 == MAP_ANONYMOUS(0x20) → 跳过 DRM
   171a4: mov  x0, #0x0             ;   匿名映射：返回 0，flag 保持 0
   171a8: ... ret
   171cc: bl   10d08                ; 按 fd 查 DRM 句柄表
   171e0: mov  w0, #0x1
   171e4: str  w0, [x19]            ; ★ *out_flag = 1 → 告诉 mmap "我接管了"
   1723c: ldr  x0, [x5, #56]        ; 查 BO 的 size
   17248: sub  x0, x0, x6
   1724c: cmp  x0, x24
   17250: b.cc 172a0                ; 越界 → -22 (EINVAL)
   17268: ldrsw x5, [x5, #8]        ; 取 BO 的 offset
   17270: mov  x0, #0xde            ; 222
   1727c: b    8740                 ; 裸 mmap 到 BO 的 offset 上
```

**分类：`(a) 真实现`** —— 但**只对非匿名映射**。

- `tbz w3, #5` 是关键：`MAP_ANONYMOUS = 0x20 = bit5`。匿名 mmap
  **根本不进 DRM 逻辑**，直接落到 `syscall(222)`。
- 对 DRM 缓冲区，它还会改写 offset，把 mmap 映射到 BO 的真实位置。

**是不是真需要 hook？** 对**本容器**：**不需要**。

**实测（`mmprobe.c`，双侧 5 项全过）：**

```
=== 官方 ===                        === bxroot ===
1 匿名 mmap      -> 0x7050197000 OK  1 匿名 mmap      -> 0x75021cf000 OK
2 文件 mmap      -> 0x7050165000 OK  2 文件 mmap      -> 0x75021ce000 OK
3 mmap64 匿名    -> 0x7050156000 OK  3 mmap64 匿名    -> 0x75021bf000 OK
4 MAP_FIXED      -> 0x7050197000 OK  4 MAP_FIXED      -> 0x75021cf000 OK
5 64MB           -> 0x704a000000 OK  5 64MB           -> 0x74fc600000 OK
5  首尾可写 OK                       5  首尾可写 OK
MMAP-DONE                            MMAP-DONE
```

**为什么 bxroot 不导出也没事（有证据）：**

1. 匿名/文件/`MAP_FIXED`/64MB 全部走 `syscall(222)`，**与 libc 的 `mmap` 等价**；
2. 容器的 DRM 场景**不存在**：
   - `<ROOTFS>/dev/dri` **不存在**；
   - rootfs 里**没有** `libgbm*` / `libdrm*`；
   - `node` 对 `drm|gbm|seat` 的动态引用数 = **0**；
   - 官方把 DRM 那一整套作为**内部 API** 导出（97 个 `proroot_/gbm_/drm_/link2symlink_/fake_id0_/libseat_` 符号），
     而 rootfs 程序对这 97 个的引用数是 **0**（符合你给的统计）。

**结论：`mmap` / `mmap64` = 不必补（对本容器/DSHA 用途）。**
**但**要留下判据：一旦出现"用 DRM/GBM 的程序"（比如跑 Wayland/X、`kmscube`、
Chromium 的 ozone-drm 后端），**必须补**，而且是补**整套 DRM**
（`proroot_drm_mmap` + `gbm_*` + `drmGetDevice*` + `libseat_*`），
只补一个 `mmap` 壳子没有意义。**这是范围外的工程，不建议现在做。**

> 修正一处口径：你给的 `mmap64`=36 引用，我实测 `mmap64` 的符号地址是
> **0x1a8f0**，其函数体与 `mmap` **逐字节同构**（同样 `bl proroot_drm_mmap`、
> 同样 `syscall(222)`），所以两者结论一致。

### 2.2 `dl_iterate_phdr`（官方 @0x22fec）★ **实测有真实缺陷** ★

**官方反汇编（全文）：**

```asm
0000000000022fec <dl_iterate_phdr@@Base>:
   22ff8: adrp x21, b1000
   22ffc: add  x21, x21, #0xf68        ; x21 = &缓存槽
   2300c: ldr  x2, [x21, #8]           ; 读缓存
   23010: cbz  x2, 2304c               ; 空 → 去解析
   23014: mov  x1, x20                 ; data
   23018: mov  x0, x19                 ; callback
   2301c: blr  x2                      ; ★ 调"真正的 dl_iterate_phdr"
   23020: cbnz w0, 2303c               ; 非 0 → 直接返回
   23024: ...
   23038: b    5b50 <ldso_service_dl_iterate_phdr@plt>   ★ 再调 linker 服务
   2303c: ... ret
   ; ---- 解析路径 ----
   2304c: adrp x1, 36000
   23054: add  x1, x1, #0xc80          ; "dl_iterate_phdr"（我已从 .rodata 读出）
   23058: bl   5fb0 <dlsym@plt>        ; dlsym(-1, "dl_iterate_phdr")
   2305c: str  x0, [x21, #8]           ; 填缓存
   23064: cbnz x0, 23014               ; 成功 → 回上面调用
   2307c: b    5b50 <ldso_service_dl_iterate_phdr@plt>
```

`.rodata@0x36c80` 实测内容：`b'dl_iterate_phdr\x00dladdr\x00...'` —— **印证**
"先 `dlsym("dl_iterate_phdr")`，失败再走 linker 服务"。

**分类：`(b) 薄转发（带静态缓存 + 双路兜底）`。**

**为什么它不需要 hook？** 注意 `dlsym(-1, "dl_iterate_phdr")` 拿到的是
**libc 的** `dl_iterate_phdr` —— 也就是说即便在官方 runtime 上，
实际干活的仍是 libc 的 loader 状态。官方只是**多兜了一层**
`ldso_service_dl_iterate_phdr`（proroot loader 的**私有模块视图**）。

**实测（`phdrprobe.c`）—— 这里是真差异：**

```
=== 官方 ===                                   === bxroot ===
dl_iterate_phdr:                               dl_iterate_phdr:
   phdr[0] name=.../phdrprobe base=... phnum=9    phdr[0] name=.../phdrprobe base=... phnum=9
   phdr[1] name=.../phdrprobe base=... phnum=9 共 1 个模块      ← ★
   phdr[2] name=.../liboff-runtime.so ...
   phdr[3] name=.../libc.so.6 ...
   phdr[4] name=.../ld-linux-aarch64.so.1 ...
   共 5 个模块
dladdr(&main) -> 1 fname=.../phdrprobe         dladdr(&main) -> 1 fname=.../phdrprobe
                 fbase=0x725dab5000                            fbase=0x7a22de6000
```

> 注：官方侧 `phdr[0]` 与 `phdr[1]` 重复，是因为它**先 `bl` libc 的
> `dl_iterate_phdr`、再 `b` linker 服务**，两遍回调拼在一起 —— 上表
> "5 个模块"里已含这个重复。这一点在 `PROROOT_*` 默认配置下就复现，
> 与本报告结论无关，但**本身像是官方的一个小瑕疵**，列在 §5。

**bxroot 只看到 1 个模块（主程序自己），看不到 libc / runtime / ld.so。**

**结论：`dl_iterate_phdr` = 必须补。** 但**不能只做"薄转发 libc"** ——
理由见 §2.3（同一个陷阱）。正确修法必须同时接上
`ldso_service_dl_iterate_phdr`（bxroot 的 linker **已经**导出这三个

|---|---|---|
| 1) 初始 `dlerror()` | `NULL` | `NULL` ✅ |
| 2) 失败的 `dlsym` 后 | `undefined symbol: bxroot_definitely_no_such_symbol_42` | **`NULL`** ❌ |
| 3) 再读一次（应已清除） | `NULL` | `NULL` ✅ |
| 4) 成功的 `dlsym` 后 | `NULL` | `NULL` ✅ |

**根因（bxroot 源码注释自己就写明了，实测现已兑现）：**

`src/runtime/preload.c`（`dlsym` 实现，第 3732 行附近）注释说：

> 本轮**只导出 `dlsym`** …… 客户程序（node + N-API 模块）的失败点
> 只有 dlsym 一处，实测已闭合；`dlerror` 为 TLS 错误码语义，
> 自己实现要先复刻 `__libc_dlerror_result` 的布局；**做错比不做更糟**。

**调用方拿不到错误原因，真故障被静默吞掉。**

更糟的是 **bxroot 内部自己就依赖它**：

- `src/proc/proc.c:3049` —— `PX_LOG("proc: dlsym(%s) 失败: %s", name, dlerror());`

即：**bxroot 专门写了"失败必须留痕"的诊断代码，而这段代码现在永远打印不出原因。**

**★ 修法警告（我实测了两种"薄转发"，两种都崩）★**

我自己写了两个垫片验证"直接转发给 libc 够不够"：

这正是 bxroot 源码里那段警告的**实测复现**（它说"实测

注意 `base=0x0` 说明我的自检垫片没能从 `dl_iterate_phdr` 拿到自身基址

**结论：`dlerror` = 必须补，且必须与 `dlsym` 同源实现。**
建议修法（两条路，二选一，**都要先做自递归防护**）：

- **路 A（推荐，与官方同构）**：在 bxroot 自己的 `dlsym` 里，

- **路 B（若坚持转发）**：必须先把"解析结果是否落在本库地址范围内"
  判准（用 `/proc/self/maps` 或 linker 的
  `ldso_service_find_object_by_addr`），命中自己就返回 `NULL`，
  再转发给 libc。**我已实测：不做这个判准 100% 崩。**

> ## ⚠️ 2026-09-17 更正：本节的三条**机理**结论已被实测推翻
>
> 缺陷本身与结论（必须补）**成立**，修复也已完成
> （见 `docs/pthread_create栈哨兵修复.md`）。但下面的**机理描述是错的**，
> 后人若照它去找一个不存在的"哨兵 bug"会白费功夫。逐条更正：
>
> **1. 「溢出哨兵」不存在 —— `addr+region==0` 是 glibc 的常态。**
> `pthread_attr_getstack`（libc@0x82f20）实际只做：
> ```
> addr   = [attr+24] - [attr+32];
> region = [attr+32];
> ```
> 字段布局实测为 `+16=guardsize, +24=stackaddr, +32=stacksize`。
> 只设 `stacksize` 时 `stackaddr` 为 0，于是
> `addr = 0 - size`，`addr + region = -size + size ≡ 0`。
> **这是恒等式，不是加载器塞进去的东西。** 用纯 glibc 在本机复现：
> ```
> $ ./stackattr
> 只设 size=135168:  addr=0xfffffffffffdf000 region=135168
>   addr+region = 0x0
>   addr == -size ? 是                 ← ★ 恒等式
> 设显式栈区    :  addr=0x7587b72018 region=1048576  和=0x7587c72018
> ```
> 决定性证据：两侧 attr 的**原始 64 字节逐字节相同**，原生环境读到的
> 值也一模一样 —— attr 相同而结果不同，足以否掉"哨兵"假设。
>
> **2. 官方 `b.eq 105f4` 是【进入修正】而非【跳过】。**
> 分支目标 `105f4 → 1064c → 10650` 正是
> `sysconf` / `csel(256K)` / `setstacksize` 那段修正代码；
> `!b.eq` 路径也汇入同一段。把 `b.eq` 读反了，才会得出
> "命中后提前 return 直通、没走到修正段"。
>
> **3. 根因是 glibc 的栈下限，与加载器无关。**
> 用 `dlopen("libc.so.6")` 绕过一切钩子直调：**139264 以下
> （128K/135168/136192/137216/138240）原生、官方、bxroot 三侧完全一致
> 地返回 EINVAL**。真实下界 = `PTHREAD_STACK_MIN(128K) + guard(4K)` 对齐
> = **139264**。官方只是把 <256K 的请求抬到 256K，让调用方碰不到下界。
>
> **真实差距是**：官方给栈下限，bxroot 不给。这解释了
> "135168 档 rc=0 随后 SIGSEGV" —— 用 `pthread_getattr_np` 读回**真实**
> 栈才发现：bxroot 真的只给了 135168。
>
> **修法上的两处更正**（下面的代码骨架有两处会引入新缺陷）：
> - **判据 `addr != NULL` 是错的**：只要设过 `stacksize`，`addr` 必非空，
>   于是 `!sentinel && region != 0` 永不成立 → 每次都替换 attr。
>   应改用 `region != 0 && addr + region != 0`。
> - **必须 `memcpy` 复制，不能用 `pthread_attr_init`**：`init` 会把
>   guardsize 重置为 4096，而官方是逐字节复制故**保留**。
>   实测 guardsize=16384 时：官方 16384 / init 写法 4096 / 正确实现 16384。
>   这正是"为了修边缘情况而破坏正常路径"。
>
> 以下原文保留，但请以上面的更正为准。

**这条推翻了 bxroot 源码注释里"已回退、无法靠复刻官方钩子关闭"的判断**
（`src/runtime/preload.c` 约 4874 行的长注释）。那条注释的第 1 点
（"不带任何 bxroot 代码时同样发生 → 是 loader 缺陷"）**我无法复核**：
本工作区**裸跑任何程序都会被官方 runtime 抢占**（§1.2），
所以我造不出"无 runtime"的基线。它的第 2 点（照抄官方判据不生效）
**我完全复现了**，见上面第 2 步。

**建议修法（关键在"不要照抄官方的跳过判据"）：**

```c
int pthread_create(pthread_t *t, const pthread_attr_t *a,
                   void *(*fn)(void *), void *arg)
{
    /* 懒解析真实现，语义 = dlsym(RTLD_NEXT)，注意 §2.3 的自递归防护 */
    if (!a) return real(t, a, fn, arg);

    size_t size = 0, region = 0; void *addr = NULL;
    pthread_attr_getstacksize(a, &size);
    pthread_attr_getstack(a, &addr, &region);

    /* ★ 判据：addr+region==0 说明 proroot loader 塞了溢出哨兵 ——
       这正是官方会"跳过"的情形，但恰恰是**最需要修**的情形 */
    int sentinel = (addr != NULL && (uintptr_t)addr + region == 0);
    if (!sentinel && region != 0) return real(t, a, fn, arg);  /* 真显式栈区，别动 */

    long psm = sysconf(_SC_THREAD_STACK_MIN);
    size_t want = (size_t)psm * 2; if (want < 262144) want = 262144;
    if (size >= want && !sentinel) return real(t, a, fn, arg);

    /* ★ 必须造"全新 attr"：沿用原 attr 会把哨兵 addr 一起带过去 */
    pthread_attr_t clean;
    pthread_attr_init(&clean);
    if (pthread_attr_setstacksize(&clean, want) != 0) {
        pthread_attr_destroy(&clean);
        return real(t, a, fn, arg);        /* 失败则保守直通 */
    }
    int rc = real(t, &clean, fn, arg);
    pthread_attr_destroy(&clean);
    return rc;
}
```

**必须注意的边界（我实测到的）：**
- `256K` 档位在我的探针里原本**也崩**，强制修法后正常；
  说明"丢弃哨兵"这一步是必需的，不是可选优化。
- 官方在解析不到真实现时返回 **EAGAIN(11)**（`mov w23, #0xb`），
  不是 `ENOSYS` —— 复刻时保持这个语义更安全。

### 2.5 `pclose`（官方 @0x27da0）★ **实测有真实缺陷，但根因不在它** ★

**官方反汇编（关键片段）：**

```asm
0000000000027da0 <pclose@@Base>:
   27da0: stp  x29, x30, [sp, #-64]!
   27db0: mov  x22, x0
   27db4: adrp x21, b2000
   27db8: bl   5b10 <fileno@plt>            ; ★ fd = fileno(stream)
   27dbc: add  x19, x21, #0x140              ; ★ 全局表（.bss）

   27dc4: add  x0, x19, #0x8

   27e10: bl   61f0 <pthread_mutex_unlock@plt>
   27e14: mov  x0, x22
   27e18: bl   5b60 <fclose@plt>
   27e20: str  wzr, [sp, #60]

   27e40: bl   6200 <waitpid@plt>

   27e48: ldr  w0, [sp, #60]

   27e5c: ...
   27e70: bl   6180 <__errno_location@plt>

   27e80: mov  w0, #0xffffffff
```

**分类：`(a) 真实现。`**
**它必须 hook，因为官方把 `popen` 也一起自研了** —— 两者共用一张
**256 项的全局表**（`fd → pid`）。官方 `popen`（@0x27b50）自己在
`pipe2` + `fork` + `execve("/bin/sh","sh","-c",cmd)` 之后：

```asm
   27c3c: adrp x23, b2000
   27c40: add  x19, x23, #0x140
   27c44: add  x0, x19, #0x8
   27c48: bl   61d0 <pthread_mutex_lock@plt>
   27c4c: add  x1, x19, #0x44
   27c64: ldr  w3, [x1]
   27c6c: cbnz w3, 27c58                     ; 找空槽
   27c80: str  w22, [x0, x2]                 ; 存 fd
   27c84: str  w21, [x1, #4]                 ; ★ 存 pid
   27c90: bl   61f0 <pthread_mutex_unlock@plt>
```

**调用同一个 `popen` 后调 `pclose` 是自洽的**（都走官方实现）。
**但"混搭"就会坏** —— 而这正是 bxroot 的现状。

**实测（`pcprobe.c`）：**

```
=== 官方 ===                                === bxroot ===
读到: HELLO_FROM_CHILD                       CANNOT LINK EXECUTABLE "sh": library "libc.so.6" not found:
pclose -> 1792 (WEXITSTATUS=7)                 needed by .../libbx-runtime.so in namespace (default)
第二次 popen/pclose -> 0                     pclose -> 256 (WEXITSTATUS=1)
                                             第二次 popen/pclose -> 256
```

**根因（我逐步隔离出来的，与 `pclose` 无关）：**

1. bxroot **确实导出了 `popen`**（@0x1de00），但它是一层**薄转发**：

   ```asm
   000000000001dc60 <popen>:                 ; 注意：符号名 popen，但函数体在 system 段附近
      1dc80: ldr  x2, [x19, #360]           ; 缓存的真 popen
      1dc94: mov  x1, x21
      1dc98: mov  x0, x20
      1dcac: br   x16                        ; ★ 纯转发
      1dcb0: adrp x22, 1f000
      1dcb4: add  x22, x22, #0x8b8           ; "popen"（我实测读出 b'popen'）
      1dcc0: bl   66c0 <dlsym@plt>            ; dlsym(-1, "popen")
   ```
   源码侧对应 `src/proc/proc.c:4189 FILE *popen(...)`，注释明确写着
   **"这里明确不接管，只记录为不覆盖项"**。

2. bxroot 在构造函数里 **`setenv("LD_PRELOAD", <本库的容器绝对路径>, 1)`**
   （`src/proc/proc.c` 的 `px_cfg_merge_preload`，约 2454 行），
   意图是让 `system`/`popen` 的子进程也带上钩子。我读到的实际环境：

   ```
   ##### 官方 #####                          ##### bxroot #####
   LD_PRELOAD = (未设置)                      LD_PRELOAD = /data/data/.../ubuntu/usr/lib/aarch64-linux-gnu/mmprobe/libbx-runtime.so
   ```

3. **那个路径在"子进程的视角"里不存在。** 子进程是宿主世界的 `/bin/sh`
   （glibc 的 `popen` 硬编码 `/bin/sh`，bxroot 的注释自己也指出了这一点），
   它按**宿主视角**解析 `/data/data/com.dsh.client/files/linux/ubuntu/...`
   → 前缀 `/data/data/com.dsh.client/files/linux` 只在**容器视角**成立
   → `CANNOT LINK EXECUTABLE "sh": library "libc.so.6" not found`。

4. **决定性对照**：bxroot 的 `system()` 是**真接管**的
   （`px_system_via_guest` → `posix_spawn` 容器内 `<rootfs>/bin/sh`），
   它**同样**受 `setenv(LD_PRELOAD)` 影响，**也一起坏了**：

   ```
   ##### 官方 #####                              ##### bxroot #####
   SYS-CHILD-OK                                   CANNOT LINK EXECUTABLE "sh": ...
   system() -> 0  WEXITSTATUS=0                   system() -> 256  WEXITSTATUS=1
   popen()  读到 "POPEN-CHILD-OK"  pclose -> 0    popen()  读到 "(读不到)"  pclose -> 256
   ```

   注意 bxroot 的 `system` 已经用的是**容器内 shell**，却仍然报
   `library "libc.so.6" not found` —— 说明**坏的是 `LD_PRELOAD` 这条
   环境变量的值，不是 shell 的路径**。

   > 补充：我确认过这个 `LD_PRELOAD` 值**本身**是可用的
   > （`env LD_PRELOAD=<同一个路径> /bin/echo HELLO` → `HELLO_FROM_BX`，
   > rc=0）。坏的是**继承给子进程时的视角错配**。

**结论：**
- **`pclose` 单独补上 = 不解决问题。** 我没有实测"只补 pclose"这一格
  （因为 `popen` 已经是 bxroot 的薄转发，混搭的原表查找问题被更前置的
  exec 失败掩盖了）。**所以我对"pclose 是否也需要补"给不出实测判据**
  —— 列在 §5。
- **真正该修的是 `LD_PRELOAD` 的注入值**：应当注入**宿主视角路径**
  （即 `/data/app/.../lib/...` 那种），或干脆不要在 `environ` 里放
  容器路径；否则 `system`/`popen`/任何 `exec` 出来的子进程全部起不来。

### 2.6 `sem_wait`（官方 @0x23900）

**官方反汇编（全文）：**

```asm
0000000000023900 <sem_wait@@Base>:
   23900: stp  x29, x30, [sp, #-32]!
   2390c: adrp x20, b1000
   23910: mov  x19, x0
   23914: ldr  x1, [x20, #4008]          ; 缓存的真 sem_wait
   23918: cbz  x1, 23930                 ; 空 → 解析
   2391c: mov  x0, x19
   23920: mov  x16, x1
   23924: ldp  x19, x20, [sp], #16
   23928: ldp  x29, x30, [sp], #32
   2392c: br   x16                        ; ★ 纯转发
   ; ---- 解析路径 ----
   23930: adrp x1, 36000
   23938: mov  x0, #0xffffffffffffffff     ; -1 = RTLD_NEXT
   2393c: add  x1, x1, #0xd80             ; "sem_wait"（.rodata@0x36d80 实测 b'sem_wait'）
   23940: bl   5fb0 <dlsym@plt>
   23944: str  x0, [x20, #4008]
   23948: cbnz x0, 2391c
   2394c: bl   6180 <__errno_location@plt>
   23954: mov  w2, #0x26                  ; ★ 38 = ENOSYS
   23958: mov  w0, #0xffffffff
   2395c: str  w2, [x1]
```

**分类：`(b) 薄转发（带缓存）`** —— 没有任何实质逻辑，
`dlsym(RTLD_NEXT,"sem_wait")` 拿到 libc 的 `sem_wait` 后 `br x16` 直通。

**注意：官方 `sem_*` 家族只导出了 `sem_wait` 一个**，没有
`sem_post`/`sem_trywait`/`sem_timedwait`：

```
$ nm -D --defined-only 官方runtime | grep ' T sem'
0000000000023900 T sem_wait
$ nm -D --defined-only bxroot-runtime | grep ' T sem'
（无）
```

这说明官方**不是**"为了解决某个 sem 问题"而导出它；更像某处代码
（可能是某个静态库里的同步工具）引用了 `sem_wait`，被"抢占表"顺带收进来了。

**实测（`sem2.c` / `sem3.c`）—— 无差异：**

```
=== 官方 sem2 ===                              === bxroot sem2 ===
[sem2] 已初始化 value=1，调用 sem_wait...       [sem2] 已初始化 value=1，调用 sem_wait...
[sem2] sem_wait -> 0 errno=1 (Operation not permitted)   [sem2] sem_wait -> 0 errno=0 (Success)
SEM-OK                                         SEM-OK
```

`errno` 的差别是**成功路径上 errno 的残留值**（POSIX 允许，不属于契约），
两边都不该被依赖。

**阻塞路径（`sem3.c`，这才是 `sem_wait` 唯一有意义的语义）：**

```
=== 官方 ===                                === bxroot ===
[sem3] value=0，sem_wait 将阻塞...           [sem3] value=0，sem_wait 将阻塞...
[w] 即将 sem_post                            [w] 即将 sem_post
[sem3] sem_wait -> 0 errno=0，阻塞 152.9 ms   [sem3] sem_wait -> 0 errno=0，阻塞 150.2 ms
SEM-BLOCK-OK 153ms                           SEM-BLOCK-OK 150ms
```

**结论：`sem_wait` = 不必补。**
判据：官方实现是**纯转发**（`br x16`），转发目标是 `dlsym(RTLD_NEXT,"sem_wait")`
= **libc 的同一个函数**；bxroot 不导出时，程序**直接**解析到 libc 的
`sem_wait` —— **落点是同一个函数**，功能上完全等价（实测阻塞/唤醒/超时
三条路径一致）。这是"不必补"的**充要判据**：
**当官方实现等价于"不 hook"时，bxroot 不导出即可。**

## 3. 汇总表

| 符号 | 官方地址 | 官方实现分类 | 官方实现**是否等价于"不 hook"** | bxroot 现状 | **实测是否有真实差异** | **结论** |
|---|---|---|---|---|---|---|
| `mmap` | 0x1a84c | (a) 真实现（DRM 查表，非匿名映射） | 否（有实质逻辑） | 未导出，走 libc | 无（匿名/文件/MAP_FIXED/64MB 全过） | **不必补**（本容器无 DRM 场景） |
| `mmap64` | 0x1a8f0 | (a) 真实现（与 mmap 同构） | 否 | 未导出，走 libc | 无 | **不必补**（同上） |
| `dl_iterate_phdr` | 0x22fec | (b) 薄转发（缓存 + linker 服务兜底） | **否**（兜底那层是私有的） | 未导出，走 libc | **有：模块视图 5 → 1** | **必须补**（且要与 dlsym 同源） |
| `dlerror` | 0x22fa0 | (a) 真实现（TLS，读一次即清） | **否**（与官方自研 dlsym 配套） | 未导出，走 libc | **有：错误串恒为 NULL** | **必须补**（勿裸转发，见 §2.3） |
| `pthread_create` | 0x104b0 | (a) 真实现（栈下限修正） | **否** | 未导出，走 libc | **有：EINVAL + SIGSEGV** | **必须补**（勿照抄官方跳过判据） |
| `pclose` | 0x27da0 | (a) 真实现（fd→pid 全局表） | **否**（与官方 popen 配套） | 未导出，走 libc | **有，但根因是 LD_PRELOAD** | **不能只补它**；先修 `LD_PRELOAD` 注入值，再评估（见 §5） |
| `sem_wait` | 0x23900 | (b) 薄转发（纯 `br x16`） | **是**（转发给 libc 自己） | 未导出，走 libc | 无 | **不必补** |

**一句话判据（给后续 agent 复用）：**
> 官方导出一个 libc 符号，**不等于**它需要被 hook。
> 判据是：**官方实现是否等价于"程序直接解析到 libc"**。
> - 等价（纯转发给 libc 自己，如 `sem_wait`）→ **不必补**；
> - 不等价（有实质逻辑，或配套了官方自己的另一个自研实现）→ **必须补**。
>
> `mmap` 是第三种情况：**实现不等价，但触发条件在本环境不存在** →
> 当前**不必补**，但要写明"什么条件下必须补"。

## 4. 关于"是不是 `--preload` 抢占导致必须提供"这个核心问题

**不是"必须提供全部 libc 符号"，而是"官方主动挑了一部分来抢占"。** 证据见 §1.1：

1. 这 7 个符号的 PLT 槽**确实**被官方 runtime 占（GOT 槽实测，§1.1 证据1）；
2. 但 `malloc`/`printf`/`memcpy`/`getpid`/… **没被占**，程序照样从 libc 解析
   （§1.1 证据2）—— 所以不存在"不做全量就解析失败"；
3. 官方 runtime **自己依赖 libc**（`DT_NEEDED: libc.so.6` + 大量
   `@GLIBC_2.17/2.34/2.38` 未定义符号，§1.1 证据3）；
4. 换个文件名，抢占就没了、进程就崩（§1.1 证据4）；
   换成 bxroot 的内容用官方名，抢占也没发生（§1.1 证据5）。

**所以 bxroot 要不要补，只取决于"官方那部分实现是否与 libc 等价"**
（§3 的判据），而不取决于"抢占"这个机制本身。

## 5. 我**不确定**的地方（不假装确定）

1. **官方 loader 判定"谁是 runtime"的确切规则 —— 没找到。**
   我排除了：文件名（证据4/5）、SONAME 字符串（两侧都叫/都不叫都不影响）、
   `DT_NEEDED`、`PT_INTERP`（标准 glibc ld.so，md5 干净）、
   `/etc/ld.so.preload`（不存在）、环境变量（`env -i` 也一样）。
   **但 `PROROOT_LIB_PATH` 的值恰好是官方 runtime 的宿主路径**
   （实测在环境里），**这是最可疑的线索，我没有验证**。
   → 若后续要研究，建议从 `PROROOT_LIB_PATH` + bridge 的 EXEC trampoline 入手。

2. **本工作区的注入点没定位（§1.2）。**
   裸跑程序就被官方 runtime 抢占，但我找不到注入者。
   这直接导致我**无法复核** bxroot 源码注释里"不带任何 bxroot 代码时
   pthread 问题同样发生 → 是 loader 缺陷"那一句。
   我**只能**确认"照抄官方判据无效"这一半。

3. **`pclose` 单独补是否有用 —— 没有实测判据。**
   因为 `popen` 子进程在 bxroot 下**根本 exec 不起来**（`LD_PRELOAD` 视角
   错配），更前置的故障把"表查找混搭"问题完全掩盖了。
   要判定这一点，得先把 `LD_PRELOAD` 修好，再重跑 `pcprobe.c`。
   （但在修好之前，**补 `pclose` 不会有任何可观测收益**，这一点是确定的。）

4. **`dl_iterate_phdr` 的官方实现在默认配置下就会重复回调主程序**
   （实测 `phdr[0]` 与 `phdr[1]` 同 name 同 base，见 §2.2）。
   我不确定这是"官方有意为之（两遍视图）"还是**官方的 bug**。
   如果 bxroot 要"逐位对齐官方"，需要先定性这一条；我倾向认为它是 bug，
   但**没有证据**。

5. **`dlerror` 若走"路 A"（自研 TLS 状态），格式串要不要逐字对齐官方？**
   官方有两条：`undefined symbol: %s` 与
   `ldso_runtime dlsym: symbol '%s' not found`（对应不同失败分支，
   我读到代码里 `stp` 了两个指针、用 `csel` 选，但没完全还原选择条件）。
   我**建议**照抄 `undefined symbol: %s`（更常见、更 glibc 风格），
   但**没有证据**说明哪条在哪个分支用。

6. **引用数统计的真实口径（§0.3）。** 我给了 4 种口径都与你给的数不符，
   且发现 `raw.tsv` 有并发丢行。**我无法确定你那批数的来源**，
   所以无法判定"谁对谁错"。

7. **`mmap` 在本环境的 DRM 路径完全没被执行到**（无 `/dev/dri`、无
   libdrm/libgbm）。所以我对 `proroot_drm_mmap` 的语义判断
   （`tbz w3,#5` = MAP_ANONYMOUS 跳过）是**从反汇编读出来的**，
   没有动态验证。它足够支撑"当前不必补"的结论，但**不足以**支撑
   "补 DRM 时该怎么写"。

### 6.3 三个环境陷阱（我踩过了）

1. **`mkdir`/`ls`/`cp` 在 `$ROOTFS` 里会"成功但看不见"。**
   `mkdir -p "$ROOTFS/usr/lib/.../mmprobe"` 返回 **rc=0**，
   紧接着 `ls` 报 No such file；而 `python3 -c "os.makedirs(...)"` 一切正常。
   → **在 ROOTFS 内建目录/复制文件一律用 Python**，不要用 shell 工具。
2. **`/tmp` 会被间歇性清空**（我遇到 `$ROOTFS/tmp/mmstage` 建完即消失）。
   → 用 `/root/mmapprobe/`（它**就是** `$ROOTFS/root/mmapprobe/`，满足
   "落地目录必须在 ROOTFS 内"的要求）。
3. **`--preload` 不支持冒号列表**：
   `--preload a.so:b.so` → `deps: failed to preload a.so:b.so`。
   要测"bxroot + 垫片"，**把垫片直接编进同一个 .so**（§6.2 的做法），
   或走 `LD_PRELOAD`。
