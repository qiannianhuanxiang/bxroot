# 身份伪造：官方在裸 syscall 层也伪造，bxroot 只在符号层

> 这份记录来自 audit 符号任务的**副产品**（子代理 142a864e 首先发现，
> 我独立复现并做了更细的分层测量）。它**与 audit 无关**，是一个独立的能力缺口。

---

## 一、实测数据

探针同时读三个层次：`/proc/self/status`（内核真值）、libc 符号、裸 syscall。

```c
/* 关键三行 */
open("/proc/self/status"); ... strstr(b, "Uid:");
printf("libc : getuid=%d ...", getuid(), ...);
printf("raw  : getuid=%ld ...", syscall(174), ...);   /* aarch64: 174=getuid */
```

两侧都用 `fakeroot` 打开（官方 `PROROOT_*` / bxroot `BXROOT_FAKEROOT=1`）：

```
##### 官方 libproroot-runtime.so #####
status: Uid:  10655  10655  10655  10655
libc : getuid=0 geteuid=0 getgid=0 getegid=0
raw  : getuid=0 geteuid=0 getgid=0 getegid=0        ← ★ 裸 syscall 也是 0

##### bxroot libbxroot-runtime.so #####
status: Uid:  10655  10655  10655  10655
libc : getuid=0 geteuid=0 getgid=0 getegid=0
raw  : getuid=10655 geteuid=10655 getgid=10655 getegid=10655   ← ★ 泄露真值
```

整理成表：

| 层次 | 官方 | bxroot |
|---|---|---|
| `/proc/self/status` | 10655（内核真值，都不改） | 10655 |
| libc 符号 `getuid()` | **0** | **0** ✅ 一致 |
| **裸 `syscall(174)`** | **0** | **10655** ❌ **不一致** |

## 二、官方是怎么做到的

反汇编官方 `getuid`（`objdump -d --start-address=0x22840`）：

```asm
getuid:
    ... 读一个配置标志 ...
    cbnz  w0, 2289c          ; 标志非零 → 走另一分支
    mov   x0, #0xae          ; 174 = getuid
    bl    syscall@plt        ; ← 未启用时**真的发 syscall**
    ...
2289c:
    mov   x0..x6, #0         ; 全零
    mov   x0, #0xae          ; 174
    bl    0x8740             ; ← ★ 走内部的特权 syscall 转发层 ★
```

关键在 `0x2289c` 那个分支：它**不直接返回常量**，而是把 `syscall(174)`
转发到内部那层（`0x8740`，即本项目文档里反复出现的"特权 syscall 转发"）。

**这说明官方伪造的不是"返回值"，而是"这次系统调用的结果"** ——
所以连裸 `syscall(174)` 都被改写成 0。

bxroot 的实现（`src/runtime/preload.c`）：

```c
uid_t getuid(void) {
    ensure_real_functions();
    if (g_config.fakeroot) return 0;      /* 纯符号层伪装 */
    return real_getuid();
}
```

只在**符号层**动手，且 `src/runtime/syscall_guard.c` 的参数表里
**完全没有 174/175/176/177 这几条**（实测 grep 无命中），
`src/runtime/sigsys.c` 也没有对应处理。所以绕过 libc 直接 `syscall(174)`
的客户程序（静态链接的 Go/Rust 程序、部分安全检查代码）会看到真实 uid。

## 二·补：身份族的缺口不止 getuid —— 还有降权族

上表只测了"读身份"。真正卡住程序的是**降权**那一半。
探针（`/root/myverify/sgprobe.c`，同时走 libc 与裸 syscall）：

```
##### 官方 libproroot-runtime.so（fakeroot 开启）#####
getuid=0 raw_getuid=0
setgroups(0,NULL)   rc=0 errno=0
raw syscall(159)    rc=0 errno=0        ← ★ 裸 syscall 也是 0
setgid(999)         rc=0 errno=0

##### bxroot libbxroot-runtime.so（BXROOT_FAKEROOT=1）#####
getuid=0 raw_getuid=10655               ← ★ 泄露真值
setgroups(0,NULL)   rc=-1 errno=38 (ENOSYS)
raw syscall(159)    rc=-1 errno=38      ← ★ 同样失败
setgid(999)         rc=-1 errno=38
```

（aarch64 上 `159 = setgroups`、`144 = setgid`。）

**注意 `raw syscall(159)` 官方返回 0** —— 这一条把机制问题钉死了，见下节。

## 二·补二：机制是"用户态模拟"，不是"更宽的 seccomp 过滤器"

这一条对修法影响很大，子代理 142a864e 做了判定，我复核了它的论据：

**排除"官方装了更宽的 seccomp 过滤器"：**
1. seccomp BPF 的动作只有 `ALLOW / ERRNO / KILL / TRAP / LOG`，
   **没有能力伪造"成功返回 0"** —— 它最多让调用返回某个 errno。
2. 而本进程 `CapEff=0` + `CapBnd=0`（实测 `/proc/self/status`），
   内核在这种情况下对 `setgroups` **必然**返回 EPERM。
   既然官方拿到的是 0，那这个 0 **不可能是内核给的**。
3. 对照项 `io_uring_setup(425)` 在**官方侧同样命中 SIGSYS** ——
   说明官方并没有整体放宽过滤器。

**所以：官方的 0 来自用户态接管。** 但"接管发生在哪一层"**尚未坐实**：
内联 `svc #0` 绕过了所有 libc 钩子（LD_PRELOAD 不可能拦住内联 svc），
却仍返回 0，这一点用"hook libc 符号"解释不通。
唯一能同时解释「内联 svc 成功 + 观测者自己的 SIGSYS 处理器不命中」的机制是
**`SECCOMP_RET_TRAP` + 官方在 SIGSYS 处理器里改写 `x0` 并跳过该 svc**。

> **这一条我没有直接证据**（要坐实需抓官方 `sigaction` 调用、
> 或反汇编它的过滤器 BPF）。**故不下定论**，只记录为最可能的机制。

**对修法的硬结论**：`BXROOT_FAKEROOT=1` 让 `getuid()` 返回 0 之后，
`chage` **仍然**报 `failed to drop privileges (Function not implemented)` ——
因为 glibc 的降权路径会**无条件**调 `setgroups`，与 `getuid()` 取值无关。
**所以只补假身份不够**，`setgroups` / `setgid` / `setresgid` 族也必须"能成功"。


## 三、真实后果（子代理实测，我已复核其证据链）

链式后果出现在需要"判断自己是不是 root"的程序上：

```
官方  : getuid()=0 → 认为已是 root → 跳过 drop privileges → chage -l root 正常输出
bxroot: getuid()=0（符号层）但 raw 层是 10655
        → 某些程序用 raw syscall 自检 → 判定需要降权
        → 走 PAM 的 drop privileges
        → setgroups/setgid 被 proroot-ldso 的 seccomp 过滤器拒绝（SIGSYS，si_syscall=159）
        → chage: failed to drop privileges (Function not implemented)
```

子代理用 SIGSYS 处理器测到 `setgroups` 确实触发 `SIGSYS (si_syscall=159)`，
而**官方同一调用不触发** —— 因为官方根本没走到那一步（它自检为 root，提前跳过）。

> 注意这里有两层原因叠加，**不要混为一谈**：
> 1. bxroot 的假身份在 raw syscall 层不生效 → 程序自检结果与官方不同
> 2. seccomp 过滤器是否放行 `setgroups`（`docs/trampoline特权exec实现.md` §5.1
>    已把 seccomp 允许列表列为**未定位项**）
>
> 究竟"官方装了更宽的过滤器"还是"官方压根没走到 syscall"，
> **目前证据只支持后者** —— 但这一点尚未被直接证伪，列为待查。

## 四、状态

**未修**。这是一个独立于 audit 的能力缺口，需要单独评估：

- 修法方向：在 `syscall_guard.c` 的参数表里补 174-177（以及可能的
  `getresuid` 家族），按 `g_config.fakeroot` 返回伪造值。
- 风险：`syscall_guard.c` 是本项目最"高危"的文件之一 —— 它有明确记录
  的两次事故（`case 36` 把 dirfd 当路径、`case 260` 把 `wait4` 当成
  `linkat` 写坏 `wstatus`）。**动它必须有独立测试覆盖**。
- 另有一个前置问题：官方用的是"特权 syscall 转发层"，bxroot 用的是
  "参数表 + 裸 svc"，两者机制不同 —— 补之前要先确认 bxroot 这套
  能否表达"改写返回值"。

  **这一条我已经查了，答案是能**（好消息，工作量比预想小）：

  ```c
  /* src/runtime/syscall_guard.c:109-130 */
  static long raw_syscall6(long nr, long a0, ...)
  {
      register long x0 __asm__("x0") = a0;
      ...
      __asm__ __volatile__("svc #0"
          : "+r"(x0)                       /* ← x0 是读写操作数 */
          : "r"(x8), ...);
      if (x0 < 0 && x0 > -4096) { errno = (int)(-x0); return -1; }
      return x0;                            /* ← 返回值就是 x0 */
  }
  ```

  `x0` 声明为 `"+r"`（读写），且函数最终 `return x0` —— 所以
  **在 `syscall()` 钩子拿到结果之后改写它，是现成可做的**，
  不需要动内联汇编，也不需要另起一套转发层。

  **更好的是：这个文件里已经有"结果改写"的先例了** ——
  `syscall_guard.c:766-800` 的 statx 分支就是在 `raw_syscall6()`
  返回**之后**去 patch `statxbuf` 的（`l2s_rt_patch_statx_buf`）。
  那段的注释还专门解释了"翻译那一半生效了、伪装那一半从未发生"
  这个坑（node/libuv 绕开 libc 走 `syscall(291)`）。

  **身份伪造是同一个坑的另一个实例**：路径翻译有裸 syscall 覆盖，
  身份伪装没有。补法照抄 statx 那段即可 —— 在
  `long ret = raw_syscall6(...)` 之后按 `number` 分派，
  `174..177` 时把 `ret` 换成伪造值（失败路径不动）。

  **所以缺的不是机制，是那张表里没有 174-177 这几条。**
