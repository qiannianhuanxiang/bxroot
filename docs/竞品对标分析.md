# bxroot 竞品对标分析报告

> 目的：把 bxroot（开源"无 root 容器运行时"，LD_PRELOAD 路径翻译路线）与同类项目横向对标，判断它在**功能 / 易用性 / 稳定性 / 安全性**上还缺什么、有什么值得借鉴的设计。
>
> 方法：结论尽量基于可核验的一手资料（官方 manual / README / 官方文档），来源 URL 见文末与正文行内链接。凡是我**推测**而非查证的，都会显式标注「（推测）」。
>
> 覆盖对象：`proot` · `proot-distro` · `fakechroot` · `fakeroot` / `pseudo`(Yocto) · `bubblewrap` · `bxroot`。
>
> 生成日期：2025 年。

---

## 0. 一句话背景与坐标

bxroot 走的是 **纯 LD_PRELOAD 路径翻译 + 无 ptrace** 路线：拦截 libc 调用，把 guest 视角路径 `/etc/x` 翻译成宿主 `<rootfs>/etc/x`，并叠加 fakeroot（伪 root 身份 + 属主账本）、link2symlink（硬链接模拟）、seccomp SIGSYS 兼容层、glibc livepatch、/dev/shm 模拟、只读 bind、任意 uid:gid 映射。

同类里可以按"拦截机制"分成三派：

| 派系 | 拦截机制 | 代表 | 在 Android app 沙箱可用？ |
|---|---|---|---|
| ptrace 派 | 每个 syscall 停两次，内核态改参数 | proot、proot-distro（底层就是 proot）、fakeroot-ng | ✓（不需 root，只需 ptrace 自身进程） |
| LD_PRELOAD 派 | 替换 libc 函数，用户态改路径/属主 | fakechroot、fakeroot、pseudo、**bxroot** | ✓（不需任何特权） |
| user namespace 派 | 内核 unshare 出新 namespace | bubblewrap、rootlesskit、unshare | ✗（见 §5，Android app 沙箱基本禁用） |

这三派的分野是本报告所有对比的基础。

## 2. bxroot 的差异化优势（它做对了、同类没有或更弱的）

1. **无 ptrace 的路径翻译，同时保留 chroot 语义** —— proot 的官方 manual 明确它"technically relies on `ptrace`"（[proot manual](https://proot-me.github.io/)），而 ptrace 每个 syscall 要陷入内核两次，是社区公认的性能瓶颈。fakechroot 虽然也走 LD_PRELOAD，但**只做 chroot、不做 fakeroot**（[fakechroot README](https://github.com/dex4er/fakechroot)：只"replaces some libc functions ... simulate the effect of being called with root"，属主/身份要靠外挂 fakeroot）。bxroot 把 **路径翻译 + fakeroot + link2symlink** 三件事合进一个 LD_PRELOAD 运行时，是 proot 的能力面 + LD_PRELOAD 的低开销，这个组合同类里少见。

2. **面向 Android app 私有目录 + seccomp SIGSYS 兼容层** —— 这是纯 LD_PRELOAD 方案在 Android 上最难的部分。Android app 沙箱会 seccomp-TRAP 掉 `set_robust_list`/`rseq` 等 syscall，fakechroot / fakeroot / pseudo 这些桌面/构建向工具**根本没处理过这种场景**（它们假设跑在正常 Linux 上）。bxroot 用信号处理器 + libc 内联 svc 站点 livepatch 去中和，属于把 LD_PRELOAD 路线真正"啃"到 Android app 沙箱可用的工程投入。

3. **glibc 版本自适应 livepatch** —— fakeroot 的 manual 自己承认一个致命限制：「Every command executed within fakeroot needs to be linked to the **same version of the C library** as fakeroot itself」（[fakeroot(1)](https://manpages.debian.org/bookworm/fakeroot/fakeroot.1.en.html)）。bxroot 做 glibc 版本自适应 livepatch，正好是在攻这个同类公认的脆点。

4. **不依赖 user namespace** —— 见 §5，这让它在 Android app 沙箱里能跑，而 bubblewrap 这类"更现代"的方案跑不了。这不是缺点而是路线正确性的印证。

## 3. bxroot 缺失或较弱的功能（对标差距）

按「功能 > 易用性 > 稳定性 > 安全性」优先级排序。每条给出「同类怎么做 / bxroot 可否借鉴 / 实现难度」。

### A. 易用性（最可能决定 bxroot 能否被用起来 —— 重点）

**A1. 多发行版管理与一键登录（差距最大）**
- 同类怎么做：`proot-distro` 提供完整生命周期命令：`install / login / remove / reset / backup / restore / list / rename`，甚至 `search`、`build`（从 Dockerfile 构建）、直接从 **Docker Hub / OCI registry 拉发行版**（`proot-distro install ubuntu:24.04`），还有 `ps` / `kill` 管理后台 session、`--detach` 守护化、`--shared-home/--shared-tmp/--shared-x11` 这类贴心 bind 开关（[proot-distro README](https://github.com/termux/proot-distro)）。
- bxroot 现状：核心是运行时，"发行版管理层"薄（推测）。用户拿到 bxroot 后从"哪弄 rootfs、怎么装第二个发行版、怎么备份"这些问题没有开箱答案，就会流失。
- 可否借鉴：**强烈建议**。这是 proot-distro 相对裸 proot 的全部价值来源，也是 bxroot 目前最容易被比下去的地方。
- 实现难度：中。管理层是纯脚本/CLI 工程，不碰核心拦截逻辑。可先做 `install/login/list/remove/backup/restore` 六个命令 + 一份 rootfs 源清单。

**A2. DNS / 网络的零配置化（重点挖到的实际短板）**
- 同类怎么做：`proot-distro` 在装完发行版后**自动做三件 fixup**：把 `/etc/resolv.conf` 写成 Google DNS（8.8.8.8 / 8.8.4.4）、给 `/etc/hosts` 填 localhost 映射、把宿主 Android 用户注册进 `/etc/passwd` 等（[proot-distro README §"After all layers are applied"](https://github.com/termux/proot-distro)）。裸 proot 则要用户自己 `-b ~/hosts:/etc/hosts`（[proot manual 示例](https://proot-me.github.io/)）。
- bxroot 现状：（推测）需要用户手动 bind resolv.conf，否则 guest 里 DNS 解析失败——这是新手最常见的"装完 apt update 不通"翻车点。
- 可否借鉴：**强烈建议**。这是低成本高回报的易用性补丁。
- 实现难度：低。安装/首次登录时写默认 `/etc/resolv.conf` + `/etc/hosts` 即可；进阶可跟随宿主 DNS。

**A3. 特权端口重映射 / 端口协调**
- 同类怎么做：proot 有 `-p in:out`（端口映射）和 `-n`（netcoop 自动分配空闲端口）；proot-distro 有 `-P` 把 1–1023 特权端口自动 +2000（22→2022）（[proot manual](https://proot-me.github.io/) / [proot-distro README](https://github.com/termux/proot-distro)）。因为非 root 进程绑不了 <1024 端口。
- bxroot 现状：（推测）未见端口重映射。
- 可否借鉴：可选。sshd/nginx 等想在容器里跑就需要。
- 实现难度：中。需要拦截 bind/connect 改端口，bxroot 已有 libc 拦截框架，增量不大。

### B. 功能

**B1. 跨架构执行（QEMU user-mode）**
- 同类怎么做：proot `-q qemu-*` + mixed-mode（host/guest 程序混跑，host rootfs 挂 `/host-rootfs`）；proot-distro `--emulator`（QEMU/Blink）能装并跑 x86 发行版（[proot manual](https://proot-me.github.io/)）。
- bxroot 现状：（推测）无。arm64 上想跑 amd64 二进制做不到。
- 可否借鉴：中优先。LD_PRELOAD 路线要 mixed-mode 会比 ptrace 难（QEMU 本身也要被翻译）。
- 实现难度：高。可作为长期路线，不建议短期投入。

**B2. `-b host:guest!` 不解引用绑定、`--kernel-release` 伪造内核版本**
- 同类怎么做：proot 的 `-b ...!`（强制不 dereference 目标软链）解决 `/bin/sh→dash` 这类覆盖；`-k`/proot-distro `--kernel STRING` 伪造 `uname -r` 避免"kernel too old"（[proot manual](https://proot-me.github.io/)）。
- bxroot 现状（已核源码）：`--kernel-release` **已实现** —— `launcher.c` 有 `-k/--kernel-release`，经 `BXROOT_KERNEL_RELEASE` 传给运行时 uname 钩子，这条差距不存在。bind 的 `!` 不解引用语义未见，待确认。
- 可否借鉴：`!` 语义看 bxroot bind 是否已处理软链覆盖，值得补齐。
- 实现难度：低。

### C. 稳定性

**C1. fakeroot 属主账本持久化（重点挖到的实际短板）**
- 同类怎么做：这是 **pseudo（Yocto）最核心的设计**。Yocto 官方文档写得很直白：pseudo 用 **SQLite 3 数据库** 记录 fake 的属主/权限，存到 `${WORKDIR}/pseudo/files.db`，「Storing the database in a file as opposed to in memory gives **persistence between tasks and builds**, which is not accomplished using fakeroot」（[Yocto 概念手册 §3.7](https://docs.yoctoproject.org/overview-manual/concepts.html)）。fakeroot 自己只能靠 `-s save-file` / `-i load-file` 手动导出导入（[fakeroot(1)](https://manpages.debian.org/bookworm/fakeroot/fakeroot.1.en.html)），而且官方警告 save-file"会泄露 uid 信息、且用同一文件同时 -i/-s 会 corrupt"。
- bxroot 现状：fakeroot 账本是**进程内的，退出即丢**。后果：这次会话里 `chown root:root` 出来的属主，下次登录看不到；`apt install` 装完的文件属主在重启后错乱，dpkg 的一致性检查可能报错。这是长期稳定性隐患。
- 可否借鉴：**强烈建议**，直接学 pseudo 的持久化 DB 路线。
- 实现难度：中。可用 SQLite 或轻量 KV 存 `(guest_path 或 inode) → uid:gid:mode`；难点是 rename/unlink 时同步更新账本、以及 inode 复用问题（pseudo 用路径 + inode 双重键，可参考）。建议第一版做"每 rootfs 一个 db 文件"。

**C2. LD_PRELOAD 路线的经典脆点：open() 语义、libc 版本耦合**
- 同类怎么做：fakeroot manual 坦白它**故意不 wrap open()**，因为 open() 被 libc 内部大量调用，wrap 了会产生调用环甚至段错误（libtricks 的教训）；也因此有"same libc version"硬约束（[fakeroot(1)](https://manpages.debian.org/bookworm/fakeroot/fakeroot.1.en.html)）。
- bxroot 现状：bxroot 拦得比 fakeroot 多（路径翻译必须 wrap open/openat），所以**更容易踩到这些环**。glibc livepatch 是对的方向，但需要持续跟 glibc 版本。
- 可否借鉴：把 fakeroot/libtricks 的历史教训当测试用例——针对 stat→open 互调、静态链接程序（LD_PRELOAD 对静态链接二进制无效！）建回归测试。
- 实现难度：低（建测试）～ 中（处理静态链接程序：只能靠 fallback 提示，或像 proot 那样 ptrace 兜底——但那就违背无 ptrace 初衷）。
- ⚠ **静态链接二进制是 LD_PRELOAD 路线的根本盲区**：静态程序不经动态链接器，preload 失效。proot（ptrace）没这问题。这是路线级取舍，建议在文档里显式声明。

### D. 安全性

**D1. 明确的隔离边界声明**
- 同类怎么做：bubblewrap 文档反复强调"它不是 ready-made 安全边界，隔离程度完全取决于传入参数"，并用 `PR_SET_NO_NEW_PRIVS` 关掉 setuid（[bubblewrap README](https://github.com/containers/bubblewrap)）。proot 也从不宣称是安全沙箱。
- bxroot 现状：LD_PRELOAD 方案**天然不是安全边界**（guest 里的程序能读到 preload 库、能直接发裸 syscall 绕过翻译）。
- 可否借鉴：文档层面明确"bxroot 是兼容性/可用性工具，不是安全沙箱；不要用它跑不可信代码"。零代码成本，避免误用。
- 实现难度：低（写清楚即可）。

## 5. 附：为什么 Android app 沙箱下走 LD_PRELOAD / ptrace 而不是 user namespace

这段用来印证 bxroot 路线合理性。

- **bubblewrap / rootlesskit / unshare 全靠 user namespace**。bubblewrap README 明说"There is a feature ... called user namespaces which allows unprivileged users to use container features. Bubblewrap uses these to build the sandbox"，且已删除 setuid 回退模式（[bubblewrap README](https://github.com/containers/bubblewrap)）。
- **Android app 沙箱基本禁用 unprivileged user namespace**：普通 app 进程被 seccomp 策略限制、`clone(CLONE_NEWUSER)` 通常被拒，且 app 运行在 `no_new_privs` 语境下（这也是 bubblewrap 主动设置的位）。（部分为一手、部分为业界共识的推测：bubblewrap 依赖 userns 是查证事实；Android 具体禁用细节我未逐条抓到内核配置，标为推测。）
- 结论：userns 路线在 Android app 里走不通 → 剩下**ptrace（proot）**和**LD_PRELOAD（fakechroot/bxroot）**两条。bxroot 选 LD_PRELOAD，用性能换掉 ptrace 的双陷入开销，是这个约束下合理的工程取舍；代价是静态链接二进制盲区（§C2）。
