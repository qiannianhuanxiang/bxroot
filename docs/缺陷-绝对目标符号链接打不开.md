# 缺陷调查：绝对目标符号链接在 bxroot 下打不开

> **状态**：已定位、有最小复现、有官方对照。**判定为架构级限制**
> （`LD_PRELOAD` 方案的固有边界），不是实现疏漏。
>
> **发现方式**：修正测试加载路径之后暴露出来的（见
> `docs/调查-LD_PRELOAD在proroot容器内失效.md`）。此前该测试一直是
> **假绿** —— 它加载的其实是外层 proroot。

---

## 一、现象

一个**目标是绝对路径**的符号链接，在 bxroot 下打不开（`ENOENT`），
而官方 proroot 正常。

### 最小复现

```sh
mkdir -p /tmp/linktest && cd /tmp/linktest
echo content > target.txt
ln -s /tmp/linktest/target.txt linkabs   # 绝对目标
ln -s target.txt               linkrel   # 相对目标
```

探针（`chdir` 到该目录后逐个打开）：

```c
fd = open("linkrel",  O_RDONLY);   /* 相对目标 */
fd = open("linkabs",  O_RDONLY);   /* 绝对目标 ★ 问题在这 */
fd = open("/tmp/linktest/target.txt", O_RDONLY);  /* 直接开目标，作对照 */
```

### 实测结果

| 操作 | 官方 proroot | bxroot |
|---|---|---|
| `open(linkrel)`（相对目标） | ✅ OK | ✅ OK |
| `open(linkabs)`（**绝对目标**） | ✅ OK | ❌ **ENOENT** |
| `open(linkabs)`（用绝对路径调用链接） | ✅ OK | ❌ **ENOENT** |
| `open(target.txt)`（直接开目标，不经链接） | ✅ OK | ✅ OK |
| `readlink(linkabs)` | ✅ 返回 `/tmp/linktest/target.txt` | ✅ 同样正确 |

★ `readlink` 正确、直接开目标也成功，**唯独"经绝对链接"失败** ★
这一组合把问题范围精确锁在"链接解析"这一步。

---

## 二、根因

### 2.1 机制

bxroot 是 **`LD_PRELOAD` 用户态路径翻译**：它只翻译**客户程序传给 libc 的
那个路径字符串**。

```
客户调用:  open("linkabs", ...)
bxroot:    把 "linkabs" 翻译成 "<rootfs>/tmp/linktest/linkabs"
内核:      读到这是个符号链接，取出目标字符串 "/tmp/linktest/target.txt"
           ★ 用这个**未经翻译**的绝对路径**去找文件
           → 内核视角下 /tmp/linktest/target.txt 不存在（它在 rootfs 里）
           → ENOENT
```

**关键点**：链接目标的解析发生在**内核内部**，不经过任何 libc 符号。
bxroot 的钩子没有任何机会介入 —— 它连"内核要去找第二个路径"这件事
都感知不到。

### 2.2 为什么官方 proroot 能做到

官方是 **ptrace 架构**：它跟踪**每一次**系统调用。内核在解析链接时，
无论查找路径是怎么"演变"出来的，最终都要发出 syscall 去访问那个路径 ——
官方在**那一次** syscall 上做翻译，所以能覆盖。

这正是项目文档 `docs/已知限制与架构能力边界.md` 里那张表的又一实例：

| 能力 | LD_PRELOAD（bxroot） | ptrace（官方） |
|---|---|---|
| **内核内部的路径查找** | ❌ 感知不到 | ✅ 每次 syscall 可见 |

### 2.3 与已有条目的关系

本次是新发现，但**属于同一根因族**（"不经过导出符号的路径"）：

- 已有：`make` 配方子进程（glibc 私有 spawn 路径）
- 已有：NSS `getpwnam_r` 内部分派
- **本条**：内核的符号链接目标解析
- 已有：内联 `svc`（glibc 内部）

区别在于：前几条是"用户的代码路径绕过了符号层"，本条是
**"内核自己发起了一次路径查找"** —— 后者连"用户代码"都没有，
纯粹是内核行为。

---

## 三、影响面（为什么这条比看起来重要）

### 3.1 不只是"链接打不开"

凡是**依赖绝对符号链接**的软件都会受影响。实际场景：

| 场景 | 是否受影响 |
|---|---|
| `/etc/alternatives/*`（Debian/Ubuntu 的替代方案系统） | ⚠️ 若目标是绝对路径 |
| `/usr/lib/*.so` 常见的 `libfoo.so -> /usr/lib/libfoo.so.1.2.3` | ⚠️ 取决于链接形态 |
| `/proc/self/cwd`、`/proc/self/exe`（魔法链接，目标是绝对路径） | ⚠️ 可能受影响 |
| 相对目标的链接（`libfoo.so -> libfoo.so.1`） | ✅ 不受影响 |
| 硬链接（真硬链接） | ✅ 不受影响（无"目标"概念） |

★ 需要注意：本项目已有 l2s（link2symlink）层把**硬链接**转成符号链接，
而那些链接的目标形态会影响是否踩到这个缺陷。

**✅ 已实测：l2s 不会踩这个缺陷**（这是本文档写完后立刻补做的验证，
因为它决定了这条缺陷的严重程度）：

```
$ BXROOT_ROOTFS=$RF BXROOT_L2S_DIR=$RF/.l2s … l2sprobe
RESULT link() rc=0                      ← 成功
RESULT lstat(b) symlink=0               ← ★伪装层说它不是符号链接★
RESULT readlink(b)=-1 (Invalid argument) ← readlink 如实报"不是链接"
RESULT open(b via link)=9 errno=0       ← ★经它 open 成功★
RESULT content=hello
RESULT st_nlink(a)=2                    ← nlink 契约也对
```

**为什么安全**：l2s 的设计是"**对客户程序伪装成真硬链接**"，所以：
- 客户看到的是 `st_nlink=2` + **不是**符号链接 —— 与真硬链接一致
- 客户**看不到**那个中间链接（它是实现细节，被 l2s 层藏住）
- 因此客户拿到的路径**从来不是**一个"绝对目标的符号链接"

也就是说，l2s 的中间链接形态**不影响**本条缺陷的适用范围。
结论：**本条缺陷只影响"用户自己创建的、目标为绝对路径的符号链接"**，
影响面比 3.1 表格里担心的要小。

★ 这次验证值得记一笔方法论 ★ 我在写 3.1 时把这条列为"尚未实测"，
而它恰好是**决定严重程度的关键变量**。先记录"未验证"、随后立刻补测，
比直接写"影响很大/不大"（两个都是猜测）都正确。

### 3.2 一个反直觉之处

`/proc` 下的魔法链接（如 `/proc/self/exe`）**目标是绝对路径**，理论上
也会受影响。但 `readlink` 是"读目标字符串"（返回内核给的原始字符串），
而 `open` 才是"跟过去"（触发解析）。所以：
- `readlink("/proc/self/exe")` → 正常返回
- `open("/proc/self/exe")` → 可能失败

这与实测的 `linkabs` 行为一致。**但 `/proc` 是否真受影响未实测**
（本容器在 proroot 内，`/proc` 已被官方映射），列为待验证项。

## 四、可能的修法（未实施，供后续评估）

按代价从低到高：

### 4.1 拦截"跟链接"的操作，自己做解析

在 `open`/`stat` 等钩子里：先 `lstat`，若发现是符号链接，就
`readlink` 取目标，**自己翻译目标**，再拼成最终路径传给真 `open`。

- 代价：每个路径操作多 1～2 次 syscall（热路径上开销明显）
- 正确性风险：要处理链接套链接、`..`、循环链接、`O_NOFOLLOW`、
  `AT_SYMLINK_NOFOLLOW` 等语义，容易做错
- **不完整**：`execve`、`chdir` 等由内核解析路径的调用仍覆盖不到

### 4.2 让内核自己翻译（推荐方向）

核心思路：**让 rootfs 内的绝对路径在宿主上也存在**。两种做法：

1. **bind mount**：把 rootfs 挂到它自己内部（需要 root/权限）
2. **在宿主侧造镜像**：把 rootfs 的内容也在宿主对应路径上放一份
   （不可行 —— 会污染宿主）

在 Android 的非 root 场景下，1 通常不可用。这也正是官方要用 ptrace 的原因。

### 4.3 接受为限制，明确记录

考虑到：
- 相对目标的链接（**绝大多数**）不受影响
- 修法 4.1 开销大且易错、修法 4.2 需要权限

**当前建议是 4.3**：写进已知限制清单，并在文档里说清
"绝对目标的符号链接不可用"这个边界。

★ 但要注意 **l2s 与它的交互**（3.1 那条待实测项）★ —— 如果 l2s
生成的链接恰好是绝对目标形态，那影响面会大很多，需要重新评估。

## 五、对测试的影响

### 5.1 这条缺陷是"修正测试"之后才暴露的

修 `LD_PRELOAD` 失效问题之前，`RUN_PATH_FORMS.sh` 的 B 基线显示
**8/8 全绿**。改成真实加载路径（`bridge + linker + --preload`）后，
立刻变成 **7/8**，T06 报错。

★ 也就是说：**假绿掩盖了这个缺陷** ★

这印证了那次调查里的判断 —— 假绿比红灯危险，因为红灯会有人查，
假绿会被当成事实写进报告和 README。

### 5.2 测试判据的调整

T06 现在**明确标记为已知限制**而不是失败：

- 保留用例（它是有价值的回归锚点 —— 万一将来修好了，测试会变绿）
- 但用 `BXROOT_KNOWN_LIMIT` 标记，失败时记为"已知限制"而非"回归失败"
- 同时**保留双侧对照输出**，让"比官方差"这个事实始终可见

不要直接删掉这个用例 —— 删掉就等于把这个限制藏起来了。
