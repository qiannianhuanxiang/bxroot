# 真机（DSHA / Android）验证清单

> 目的：本开发容器有**两个不可绕过的验证盲区**——
> ① `LD_PRELOAD` 惰性（外层 proroot 自研 loader 劫持 execve，见
> `docs/调查-LD_PRELOAD在proroot容器内失效.md`）；② bridge 链 SIGILL。
> 因此一批修复只能做到"代码层正确 + 符号级/源码级单元验证"，
> **hook 的运行时行为必须在此清单逐项过一遍**才能闭环。
>
> 用法：真机（DSHA 容器）上按顺序执行，每项记录 PASS/FAIL 与实测输出。
> 全部 PASS 后本清单可归档为"已闭环"。

## 真机结果：Termux（2026-09-27，vivo V2352A / Android 16 / 6.1 内核，untrusted_app_27，Seccomp:2）

脚本：`test/device/run-termux.sh`（把 `bx/` 与 rootfs 放到 Termux 家目录，`sh run.sh`）。
这是**普通 app 域**、无外层 proroot 的 launcher + LD_PRELOAD 路径 —— 正是本容器的盲区 ①。

**结果：26 通过 / 0 失败**（E0 E1 E1b E2 E2b A2 A3 A3b A4 B1 B2 B2b B2c B2d B2e B2f B4 B6 B7 C1 C4 L1 S1 S2 S3 K1）。

### 真机才暴露、已修的缺陷

1. **所有 glibc 程序在 main 之前被 SIGSYS 杀死（rc=159）** —— app 域 seccomp 对
   `set_robust_list(99)` / `rseq(293)` 是 `RET_TRAP`，glibc 启动代码 / guest ld.so 的
   `__libc_early_init` 在 runtime 构造函数之前就发这两个调用。连纯静态 `puts("hello")`
   也被杀（判别力探针：无桩 rc=159 / 有桩打印 alive）。
   修：`src/ldr/early_sigsys.h`（入口 `bx_early_start` 先装 SIGSYS→ENOSYS 处理器）+
   `src/ldr/ulx.c`（`libbxroot-ulx.so`：同进程内装载 guest ld.so，避开 execve 对信号
   处置的重置）；launcher 与 runtime 的 exec 钩子在无外层 trampoline 时经 ulx。
2. **标准 glibc 下 runtime 的 `dladdr` 恒失败** → `px_detect_self_lib` 拿不到自身路径 →
   "envp 注入已禁用" → 子进程不带 runtime（guest 里 `sh -c /bin/echo` 报 not found）。
   修：无 ldso 服务时转发 libc 的 dladdr。
3. **shebang 脚本直跑落到宿主 `/system/bin/sh`**（bionic，被 glibc runtime 拖死：
   "CANNOT LINK EXECUTABLE"）。修：launcher 的 ulx 路径解析一层 `#!`。

### 真机部署注意

- Termux 的 `LD_PRELOAD=libtermux-exec-ld-preload.so`（bionic）必须 `unset`，否则 guest 的
  glibc ld.so 找不到 `libc.so`。
- guest 继承宿主 PATH（与 proot 同语义）；Termux 的 PATH 在 rootfs 里不存在，需自设。
- 宿主 cwd 不在 rootfs 内时，按上游语义打印 "can't chdir … falling back to /"；用 `-w /` 消除。
- rootfs 里的相对符号链接要按目录语义打包（本次包里 `usr/bin/sh -> usr/bin/dash` 打错过）。
- ~~残余：静态 guest 的**新线程**里 `set_robust_list` 仍会被杀（pthread_create 在 clone 前
  屏蔽了全部信号，处理器无法投递）；动态 guest 由 livepatch 中和该站点，不受影响。~~
  **已修（2026-09-28，容器内实测复现+修复）**：静态链接 guest 的 glibc 内联 svc 站点
  （`set_robust_list`(99)/`rseq`(293)）在**主可执行映像自己的 .text**，不在独立
  libc.so.6 段。原 livepatch 只扫 libc.so.6 段、且 `find_libc_base()==0` 时直接早退，
  对静态 guest 一条都补不到。修复：`src/runtime/livepatch.c` 新增 `find_main_exec_range()`
  ——当 maps 里没有独立 libc.so.6 r-x 段（静态链接特征）时，用"livepatch 代码自身地址"
  作锚点定位主映像 r-x 段，复用 `lp_scan_and_patch`（形态识别+逐字节校验 svc）补 99/293；
  并去掉 `g_base==0` 的早退（改为仅跳过依赖 libc 基址的版本精确表部分）。
  回归 `test/RUN_STATIC_THREAD.sh`（撤修复变红，已实测 `RESULT: FAIL`）。
  - 本容器实测细节：容器嵌套在外层 proroot 上，外层会把静态主映像里**紧凑形态**
    （mov x8,#99|#293 后≤2 条即 svc，含 glibc 真实 start_thread 站点 gap=2）预打成
    `mov x0,#0`，所以本容器里静态多线程"看起来也活"——那是外层的功劳，掩盖了 bxroot
    自身的空缺。判别力靠一个"外层会漏补"的间隔站点（mov x8,#99→栈 spill→svc）证明：
    修复前 `masked set_robust_list → DIED sig=31（SIGSYS）`，修复后存活。真机（Termux）
    没有外层 proroot，这些站点**全部**要中和方，本修复直接闭合该残余。
  - 存疑（诚实标注）：静态 guest 经外层/DSHA stub-loader 执行时，runtime.so **不会**被
    加载进该进程（实测 maps：静态 guest `libbxroot=0`、`libc.so.6=0`；动态 guest
    `libbxroot=2`、`libc.so.6=4`）。所以真机上"注入 runtime.so 的动态 guest"必经
    libc.so.6 分支、不触发主映像扫描；主映像扫描分支只在 **livepatch.c 被静态编入某
    可执行映像**时可达（当前即离线测试探针；将来若把 livepatch 接进 stub-loader 则真机
    也可达）。本修复对动态 guest 零影响（有 libc.so.6 段 → 走原分支），是纯增量兜底。
