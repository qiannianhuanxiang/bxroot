# 两处对照实验缺陷的更正

> 本文记录两次**看似成立、实则无效**的对照实验，以及它们各自被推翻的实证过程。
> 保留这份记录的原因是：这两次误判都**产出了看起来完整的结论**，
> 而如果不是去看了磁盘真相，它们会被当成事实写进文档。

---

## 更正一：`-L` 与 l2s 的关系（由子代理 674e56fb 报告，结论成立）

这一条不是错误，是**任务书前提有误**，记录在此以便对照。

任务书原本的验收标准②假定「官方默认 lstat 的 size 是错的，要靠 `-L` 修」。
子代理读 proot 源码后指出：`-L` 的实现（`fix_symlink_size_callback`）第一行就是

```c
if (!S_ISLNK(statl.st_mode)) return 0;   /* 不是符号链接 → 什么都不做 */
```

它对 **l2s 伪造出的链接**（已被改成 `S_IFREG`）是**空操作**。
而官方不传 `-L` 时 lstat 的 size **本来就是对的**。

**结论**：`-L` 与「l2s 的 size 缺陷」是两件独立的事。
按实测做——默认行为与官方一致（正确）+ `-L` 实现为独立的兼容开关。

## 更正二：`tar cf t.tar .` 含 `.l2s.*` —— **这是误判，不是缺陷**

### 最初的（错误）结论

子代理 674e56fb 在收工报告里写：

> **`tar cf t.tar .`（归档整个目录）仍会包含 `.l2s.*` 中间文件** —— 这是 l2s 模拟的固有代价，
> 修它需要隐藏目录项（proot 的 `-H` 扩展正是干这个的）。

我起初采信了这个结论，并据此认为「`-H` 未实现」是一个真实的功能缺口。
**这个结论是错的**，它有两次独立的实验缺陷。

### 缺陷 A：对照实验的环境变量前缀错了

我为了确认「官方是否也暴露 `.l2s.*`」，写了探针跑两侧，命令大意是：

```sh
BXROOT_ROOTFS=... BXROOT_LINK2SYMLINK=1 \
  "$APP_LIB/libproroot-bridge.so" "$APP_LIB/libproroot-linker.so" \
  --argv0 sh --preload "$ROOTFS$S/libproroot-runtime.so" "$ROOTFS/bin/sh" probe.sh
```

输出显示官方那侧 `ls -a` 只有 `a` `b`，**没有** `.l2s.*`。
我差点据此得出「官方默认就隐藏中间文件，bxroot 泄漏了」。

**但官方 runtime 根本不读 `BXROOT_*`**：

```sh
$ strings -a work/parity/off/libproroot-runtime.so | grep -oE 'PROROOT_[A-Z0-9_]+' | sort -u
PROROOT_ALLOW_UNSAFE_EXEC_FALLBACK
PROROOT_CACHE_TRACE
PROROOT_CFG_FD
...
（共 41 个，**全部是 `PROROOT_` 前缀**）

$ strings -a work/parity/off/libproroot-runtime.so | grep -c BXROOT
0
```

也就是说，我给官方那侧传的 `BXROOT_LINK2SYMLINK=1` **被完全忽略**，
官方那次**根本没启用 l2s**。

### 缺陷 B：只看容器视角，没看磁盘真相

用宿主视角检查官方那次留下的目录：

```sh
$ ls -la /data/data/com.dsh.client/files/linux/ubuntu/tmp/H1-13202
-rw-------. 2 root root 5 ... a        ← nlink=2
-rw-------. 2 root root 5 ... b        ← 真硬链接
```

宿主文件系统是 **f2fs，原生支持硬链接**：

```sh
$ stat -f -c '%T' /data/data/com.dsh.client/files/linux/ubuntu
f2fs
```

所以官方那次建的是**真硬链接**，压根没走 l2s —— 那个「官方不暴露中间文件」
的观察与 l2s 毫无关系，是**两种不同机制**的产物。

> **本项目的经典陷阱再次生效**：容器视角看到的 `ln a b` 成功，
> 不代表内核真的建了硬链接。只有宿主视角才能区分
> 「真硬链接」与「l2s 伪造的链接 + 中间文件」。

### 正确的对照实验

两侧各用**自己的**环境变量：

```sh
# bxroot 侧
BXROOT_ROOTFS="$ROOTFS" BXROOT_TMP_DIR="$ROOTFS$S/tmp" \
BXROOT_WORKDIR="/" BXROOT_FAKEROOT=1 BXROOT_LINK2SYMLINK=1 \
  ... --preload ".../libbxroot-runtime.so" ...

# 官方侧（PROROOT_ 前缀；且官方**没有** l2s 的开关）
PROROOT_ROOTFS="$ROOTFS" PROROOT_TMP_DIR="$ROOTFS$S/tmp" \
  ... --preload ".../libproroot-runtime.so" ...
```

### 真相：`BXROOT_L2S_DIR` 才是关键，而它已经实现且默认启用

proot 的 l2s 有一个**集中目录**布局，中间文件不放在客户文件旁边，
而是全部丢进一个单独目录：

```c
/* proot: src/extension/link2symlink/link2symlink.c:117 */
value = getenv("PROOT_L2S_DIR");
if (value == NULL || value[0] == '\0')
        return false;
...
strcpy(intermediate, l2s_directory);     /* 中间层放进集中目录 */
```

bxroot 的对应实现是 `BXROOT_L2S_DIR`，且 **launcher 默认就设好了**：

```c
/* src/launcher/launcher.c:990-1002 */
const char *l2s_dir = getenv("BXROOT_L2S_DIR");
setenv("BXROOT_LINK2SYMLINK", "1", 1);
if (!l2s_dir || !l2s_dir[0]) {
    static char fallback[4096];
    int n = snprintf(fallback, sizeof(fallback), "%s/.l2s",
                     cfg.rootfs ? cfg.rootfs : "");
    ...
}
```

**实测**（`BXROOT_L2S_DIR=$ROOTFS/.l2s`）：

```
--- ls -a ---
.
..
a
b                    ← 没有 .l2s.*

--- tar cf t.tar . ---
./
./a
./b                  ← 干净，与官方一致
```

宿主视角确认中间文件确实存在，只是在**另一个目录**里：

```sh
$ ls -la $ROOTFS/tmp/CD-*/
lrwxrwxrwx. 1 root root 60 ... a -> /.l2s/.l2s.a0001
lrwxrwxrwx. 1 root root 60 ... b -> /.l2s/.l2s.a0001
```

### 关于 `-H`

`-H`（hidden_files 扩展）与 l2s **没有联动关系**。proot 只在显式传 `-H` 时启用它：

```c
/* proot: src/cli/proot.c:328-332 */
static int handle_option_H(Tracee *tracee, ...)
{
        (void) initialize_extension(tracee, hidden_files_callback, NULL);
        return 0;
}
```

它的实现是硬编码前缀 `.proot`：

```c
/* proot: src/extension/hidden_files/hidden_files.c:16 */
#define HIDDEN_PREFIX ".proot"
```

—— 这个前缀之所以对 proot 的 l2s 有用，是因为 **proot 的 l2s 中间文件就叫 `.proot.l2s.*`**
（`link2symlink.c:31` 的 `#define PREFIX ".proot.l2s."`）。
它是一个「让 `tar`/`rm *` 这类通配操作不误伤中间文件」的**补丁**，
而不是 l2s 的必需品 —— 更不是唯一的解法。集中目录布局从根本上避免了这个问题。

**因此**：`-H` 仍未实现（CLI 兼容层会明确拒绝并提示），这是**如实的已知限制**，
但它**不是** `tar` 缺陷的成因，也不影响 `tar cf t.tar .` 的正确性。

### 补充证据：官方 proroot 自己也没有 `-H`

这一条把上面的结论钉死。检查官方 runtime 的导出符号表：

```sh
$ grep -cE '^(readdir|getdents)' work/parity/off/libproroot-runtime.so   # 用 nm -D 结果
0
$ nm -D work/parity/off/libproroot-runtime.so | grep -i dents
（无输出）
$ strings -a work/parity/off/libproroot-runtime.so | grep -iE 'getdents|dirent|hidden'
（无输出）
```

官方 runtime **完全不碰 `getdents` / `readdir`**，也没有任何隐藏文件的机制。
（它导出的 `opendir` 是纯路径翻译转发，与目录项过滤无关。）

`hidden_files` 是**上游 PRoot 的扩展**，官方 proroot 并未移植它 ——
这与官方也没移植 `-p`（port_switch）是同一类情况。
所以「bxroot 少了 `-H`」这个缺口，**官方同样有**，不构成与官方的行为差异。

CLI 层对此的处理是正确的（`src/launcher/launcher.c:467`）：**明确拒绝并解释**，
而不是静默忽略。实测：

```
$ sh test/RUN_CLI_COMPAT.sh
--- C) 明确拒绝（不可静默忽略）---
  ✅ -H                         明确拒绝
  ✅ -p                         明确拒绝
```

### 顺带发现：测试路径与生产路径不一致（真实缺陷，待修）

在核实上面这些时发现了一个**独立的问题**：

| | l2s 中间文件位置 | 来源 |
|---|---|---|
| **生产**（DSHA 经 launcher） | `<rootfs>/.l2s`（集中目录） | `launcher.c:999-1002` 默认设 `BXROOT_L2S_DIR` |
| **测试**（`RUN_L2S_E2E.sh`） | 客户文件旁边（散落） | 直接调 bridge，未设 `BXROOT_L2S_DIR` |

`test/RUN_L2S_E2E.sh:176-183` 的 `run_one()` 只设了 `BXROOT_ROOTFS` /
`BXROOT_TMP_DIR` / `BXROOT_WORKDIR` / `BXROOT_FAKEROOT` / `BXROOT_LINK2SYMLINK`，
**没有** `BXROOT_L2S_DIR`。

后果：测试脚本验证的是**散落布局**，而生产跑的是**集中目录布局**，
两者在目录可见性上表现不同（散落布局下客户 `ls -a` 会看到 `.l2s.*`，
集中目录布局下看不到）。

**这正是「测试通过但生产出问题」的一类典型来源** ——
测试覆盖的不是生产实际走的路径。修法：`run_one()` 补上
`BXROOT_L2S_DIR="$ROOTFS/.l2s"`，与 launcher 的默认值对齐。

### 修了之后立刻暴露第二个缺陷：集中目录不存在时 l2s **静默失效**

补上 `BXROOT_L2S_DIR` 后测试**当场变红**：

```
  bxroot: RESULT nlink=-1 islink=null size=-1 stsize=-1 reallink=true content=null err=ENOENT
  ❌ st_nlink 应为 2，实得 -1
```

探针连 `link()` 都没成功。查下去发现根因不在 l2s 逻辑，而在**目录不存在**：

```sh
$ ls -d $ROOTFS/.l2s
ls: cannot access '.../.l2s': No such file or directory
```

`l2s_make_paths_ex()` 只按 `l2s_dir` 拼路径，**不去建那个目录**；
真正落盘的那次 symlink/rename 撞上不存在的目录 → ENOENT。
而 `link()` 返回的失败**没有指向"目录不存在"**，表现成"l2s 本身坏了"。

`launcher.c:999` 会默认设 `BXROOT_L2S_DIR=<rootfs>/.l2s`，
**但 launcher 自己不建这个目录** —— 生产环境靠 DSHA 的 Java 侧
`l2s.mkdirs()`（`ContainerRuntime.java`）兜底。于是三条入口里：

| 入口 | 目录来源 | 结果 |
|---|---|---|
| 经 DSHA 启动 | Java 侧 `l2s.mkdirs()` | ✅ 正常 |
| 经 launcher 直启 | 无人创建 | ❌ **静默失效** |
| 测试脚本直调 bridge | 无人创建 | ❌ **静默失效** |

**修法**：在 `init_l2s()` 里自建目录（`SYS_mkdirat` + `EEXIST` 忽略）。
运行时是唯一知道 `l2s_dir` 会被真正用到的地方，由它保证目录存在最可靠。
建不出来时明确 `LOG()` 报错 —— 静默失效正是本缺陷最难查的地方。

顺带踩到一个平台差异：**aarch64 上没有 `mkdir` 系统调用**，只有 `mkdirat`
（`SYS_mkdir` 未定义，编译报 `did you mean 'SYS_mkdirat'?`）。
这是本项目「同一功能在不同路径上覆盖不全」模式的又一例。

**验证**（删掉目录后重跑，测试由红转绿）：

```
$ rm -rf $ROOTFS/.l2s
$ sh test/RUN_L2S_E2E.sh
  bxroot: RESULT nlink=2 islink=false size=5 stsize=5 reallink=true content="hello"
  官方  : RESULT nlink=2 islink=false size=5 stsize=5 reallink=true content="hello"
  ✅ 与官方一致
RESULT: PASS

$ ls -ld $ROOTFS/.l2s
drwx------. 2 root root 3452 ... /data/data/.../ubuntu/.l2s     ← 被运行时自建
```

全量回归仍然 **12/12**。

## 方法论教训

1. **两侧必须各用各的环境变量**。这个项目的对照实验极易失效——
   两个实现的前缀不同（`BXROOT_` vs `PROROOT_`），传错了**不会报错**，
   只会静默地跑另一套配置，而输出看起来完全正常。

2. **容器视角 ≠ 磁盘真相**。判断「内核到底建了什么」必须用宿主视角
   （`/proc/<pid>/root` 前缀，或直接看 `/data/data/...`）。
   本项目已有多处缺陷因此被误判，这次是反向的——因为没看磁盘，
   把「真硬链接」误认成了「隐藏了中间文件」。

3. **一个观察到的差异，要先问「两次跑的配置真的一样吗」**，
   再问「这个差异说明了什么」。这里的顺序反了，导致结论建立在无效对照上。

4. **项目已有的正确实现，可能就在手边**。`BXROOT_L2S_DIR` 早已实现、
   早已被 launcher 默认启用，只是测试脚本直接调 bridge 时绕过了 launcher，
   才暴露成「缺陷」。**测试路径与生产路径不一致**本身就是一类缺陷来源。
