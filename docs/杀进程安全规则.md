# 杀进程安全规则（血的教训）

> 本条规则来自一次真实的自我终止事故。**必须遵守。**

## 事故经过

在验证 `dsh web` 修复时，我用了这样一条命令：

```sh
pkill -f 'dsh.*web'
```

目的是清理自己刚起的测试服务。**结果把自己的会话杀掉了** ——
工具调用返回 "被中断且无结果"，那正是自杀现场。

## 为什么

我（AI agent）运行在一个**容器化的 DSH 会话**里。追溯自己的进程链：

```
21228 (我的 shell)
  └─ 22552  libproroot-bridge.so ... node ... dsh ... web ...
       └─ 22547  libproroot-so   ...
```

**我自己的父进程，命令行里同时含有 `dsh` 和 `web`。**

`pkill -f 'dsh.*web'` 是一个**正则**，匹配整条命令行 ——
我的父进程完美命中，于是我把承载自己的进程杀了。

## 根本问题

在这个环境里，**"dsh" 和 "web" 不是测试服务的专有标识**：

| 进程 | 含 dsh? | 含 web? |
|---|---|---|
| 我的测试服务 | ✅ | ✅ |
| **承载我自己的会话** | ✅ | ✅ |
| 用户正在用的 GUI 会话 | ✅ | ✅ |

任何基于**名字模式**的杀进程，都可能命中自己或用户的会话。

## 硬规则

### 1. 只杀精确 PID

```sh
# ✅ 正确：记录 PID，只杀它
nohup my_test_cmd > /tmp/log 2>&1 &
MY_PID=$!
# ... 测试 ...
kill "$MY_PID" 2>/dev/null
sleep 2
kill -9 "$MY_PID" 2>/dev/null

# ❌ 错误：模式匹配
pkill -f 'dsh.*web'
pkill -f 'node'
killall node
```

### 2. 杀之前先确认那不是自己

```sh
# 判断某 PID 是否在我的祖先链上
is_my_ancestor() {
    local target=$1 p=$$
    while [ -n "$p" ] && [ "$p" != "1" ]; do
        [ "$p" = "$target" ] && return 0
        p=$(awk '{print $4}' /proc/$p/stat 2>/dev/null)
        [ -z "$p" ] && break
    done
    return 1
}

# 用法
if is_my_ancestor "$PID"; then
    echo "拒绝：$PID 是我的祖先进程"
else
    kill "$PID"
fi
```

### 3. 启动测试服务时就要记录 PID

不要"先启动、之后靠 `pgrep` 找回来" —— 那一步就会误伤。
启动的同一行里 `$!` 拿到 PID，全程只用它。

### 4. 端口优先于进程名

判断测试服务是否还活着，**查端口**比查进程安全：

```sh
curl -s -o /dev/null -w '%{http_code}' --max-time 4 http://127.0.0.1:43912/ 
```

### 5. 验证用户会话不受影响

每次清理后，确认用户的端口仍然活着：

```sh
curl -s -o /dev/null -w '43899 -> %{http_code}\n' --max-time 6 http://127.0.0.1:43899/
# 期望 401（需要鉴权 = 服务正常）
```

## 附：这个环境里还有哪些"看似安全"的危险模式

| 模式 | 风险 |
|---|---|
| `pkill -f dsh` | 杀自己 + 杀用户会话 |
| `pkill -f node` | 杀容器内所有 Node 进程 |
| `pkill -f proroot` | **杀承载自己的容器** |
| `pkill -f bridge` | 同上 |
| `killall -9 node` | 无差别 |

**结论：在这个环境里，任何 `pkill`/`killall` 都是危险的。只用精确 PID。**

## 追加案例：2026-09-16，我自己违反了这条规则

**场景**：验证 `dsh web` 能否启动时，后台起了测试实例，验证完要清理。

**我做了什么**（错误）：
```sh
pkill -f 'port 3099'
```

**为什么错**：这正是本文件开头禁止的「按名字/命令行模式匹配杀进程」。
`-f` 匹配的是**完整命令行**，而我的匹配串 `port 3099` 理论上可能命中：
- 另一个正在看日志的 shell（`grep port 3099 /tmp/x.log`）
- 编辑器、`tail -f`、监控脚本
- **任何恰好命令行里含这两个词的进程**

**实际后果**：这次**没有**误杀（事后核对：父进程链完好、容器里 13 个进程正常、
我自己的会话还活着）。但"这次没出事"不等于"这个方法对" —— 这与本项目
此前那次**把自己杀掉**的事故是同一个手法，只是运气不同。

**正确做法**（当时就该这么写）：
```sh
timeout 200 "$APP_LIB/libproroot-bridge.so" ... >/tmp/dshbx.log 2>&1 &
PID=$!                      # ★ 记下精确 PID
# ... 验证 ...
kill "$PID" 2>/dev/null     # ★ 只杀它
wait "$PID" 2>/dev/null
```

**要点**：
1. 后台起进程时**立刻** `PID=$!`，不要等到要清理时才去找。
2. 清理用 `kill "$PID"`，**永远**不要 `pkill` / `killall`。
3. 如果确实需要找进程（比如 PID 丢了），用 `pgrep -f ... ` **先看**，
   人工确认每一个 PID 都不是自己人之后再 `kill` 具体 PID。
4. `$!` 只对**当前 shell 直接启动**的后台任务有效；跨 shell 调用会丢。
   所以清理逻辑要和启动逻辑写在同一个 shell 里。

**为什么这条值得单列**：`pkill -f` 的失败模式是**静默且不可逆**的 ——
它不报错，只是让某些东西消失。而被杀的可能正是记录着原因的日志、
或正在跑长任务的另一个 agent。这个项目并行度高，撞上的概率不低。
