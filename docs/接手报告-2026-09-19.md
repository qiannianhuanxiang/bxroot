## 一、已修复：测试侧缺陷（这些让回归不可信）

### 1.1 `RUN_L2S_E2E.sh` —— 探针传参视角错误（假红）

**症状**：`❌ bxroot 侧没有产出 RESULT 行（探针没跑起来？）`，
脚本据此判为"l2s 伪装未生效"，并把排查方向指向 l2s 功能。

**真因**：脚本直接 exec bridge 启动 guest node，把**宿主视角**路径
`$STAGE_LOAD/l2s_probe.js` 当 argv 传给 node，而 node（guest）会**再翻译一次**
→ 双重翻译 → 启动即
`Error: ENOENT: no such file or directory, lstat '/data/data/com.dsh.client'`。

**判据不是"统一用某种视角"，而是这个值由谁消费**：

| 参数 | 正确视角 | 消费方 |
|---|---|---|
| `--preload <path>` | **宿主** | exec 直达内核，不翻译 |
| `BXROOT_TMP_DIR` | **宿主** | launcher/runtime |
| guest 可执行文件路径（`$NODE`） | **宿主** | exec |
| **guest 的 argv（脚本/目标文件）** | **容器** | guest 自己会翻译 |

**修为**：`$STAGE_MKDIR/l2s_probe.js`（容器视角）。**结果**：`RESULT: PASS`
（`nlink=2 islink=false size=5 stsize=5 reallink=true`）—— 即 l2s 功能本来就是好的。

**顺带修**：原先 `... | grep '^RESULT' | head -1` 把探针的 stderr 全吃掉，
失败时只剩"没有 RESULT 行"，无从排查。现改为原始输出落盘 + `show_raw()` 打印末尾 15 行。

### 1.2 `probe_sigprocmask_num.c` —— 用被劫持的 libc 符号观测状态（假红）

**症状**：`❌ 175(=geteuid) 不能解除屏蔽 → 本钉能区分正确/错误号`
与 `❌ 装处理器后屏蔽位保持不变`。两条**负向**断言失败，共 3 通过 / 2 失败。

**真因**：外层 proroot 运行时**劫持 libc `sigprocmask`**，把 SIGSYS 从读回的掩码里
剔除。同一进程内两条观测路径互相矛盾（实测）：

```
libc sigprocmask(SIG_BLOCK, SIGSYS) → sigismember 读回 0     ← 被改过
裸 svc 135 读回同一掩码              → SIGSYS 位 = 1          ← 内核真相
/proc/self/status SigBlk             → 0000000040000000       ← 内核真相
```

**修为**：状态建立与读回一律走**裸 svc 135**（`KSET = sizeof(unsigned long)`）。
另加 **T0 观测路径自检**（"裸 svc 建立的状态必须能被裸 svc 读回"）——
没有这一步，下面那些"屏蔽位保持不变"的断言可能是恒假的，整项会失去判别力。

**结果**：6 通过 / 0 失败。

> **通用教训**：用被测机制本身去观测被测机制 → 假绿；
> 用同一环境里另一个被劫持的符号去观测 → 假红。本探针两个都不碰。

### 1.3 顺带修：`RUN_SIGSYS_NUM.sh` 的"源码-探针一致性"前置检查

探针头注声称"从被测源码里取号，避免漂移"，但实际把 135 **硬编码**在自己文件里 ——
而 `src/runtime/sigsys.c` 也各有一份 `#define SYS_RT_SIGPROCMASK`。两边是独立常量，
所以**真正的漂移场景恰好测不出来**：

```
若有人把 sigsys.c 改回 175（正是上一个提交 d85b22c 修的缺陷），
sigsys.c 那句裸调用会再次变成"查 euid"、SIGSYS 不被解除，
而探针**仍只测自己那份 135** → 照旧 PASS。
```

**修为**：从两边抽出实际号并比对。**已注入缺陷实测判别力**：把 `sigsys.c` 改回 175
→ `❌ 前置检查失败：源码 175 vs 探针 135`，rc=1（此前会静默 PASS）。
验证后已把源码**字节还原**。

### 1.4 `test_syscall_table_audit.c` —— 沙箱清理不完整，污染仓库根

**症状**：每次跑 `RUN_SYSCALL_TABLE_AUDIT.sh`，仓库根都留下一个**非空**的
`.bxroot-scg-audit-<pid>/`，而它**不在 `.gitignore` 里** → `git status` 一直显示，
`git add -A` 会把它提交进去（`.gitignore` 头注担心的正是这类产物）。

**真因**：`sb_purge()` 的清理清单与测试期间真实创建的文件**脱节**。
实测漏了三项：`d1/rel_g3`、`rel_rnsrc`（rename 用例）、`rel_f2`。

**修为**：补齐清单（加注释说明"新增相对名用例必须同时加进此清单"），
并加 `.gitignore` 的 `.bxroot-scg-audit-*` 兜底。**实测**：跑完无残留。

### 1.5 `RUN_DL_TESTS.sh` —— 硬编码过期 APK 路径 → 永远静默跳过（🔴 最严重）

**症状**：`RUN_ALL` 显示 `✅ dl 家族契约`，但**实际一条都没测**。

**真因**：硬编码的 APK 路径后缀已过期：

```sh
# 脚本里写的（过期）：
/data/app/~~IIMfcaE6bcH0NmTRD8KqpA==/com.dsh.client-7Lg5Zt8zAVL829axfo2lQQ==/lib/arm64
# 本机真实的（从 /proc/self/maps 探测）：
/data/app/~~Ina4eRxGmdHClt0y0DqsGg==/com.dsh.client-Bqbh8yjCugq4VmZdjRfkTg==/lib/arm64
```

APK 一重装，那个随机后缀就变。于是 `bridge_ok()` 恒失败 → 跳过，
而**跳过方式是 `exit 0`** → `RUN_ALL` 记 ✅。

**危害不止"少测一项"**：这是一个自述"只有真跑才测得到真实缺陷"的测试
（普通环境下 LD_PRELOAD 走的是另一条降级路径），它被跳过的时候恰恰最需要它。

**修为**：加 `detect_app_lib()`（与 `RUN_NSS_EDGE.sh:173` 等一致，从
`/proc/<pid>/maps` 反查）+ 所有跳过改 `exit 2`。**实测**：真实路径下 **11/11 全过**。

> 讽刺点：脚本自己的注释就写着"用文件属性做守卫会导致永远静默跳过"，
> 但它只解决了"怎么判断可用"，没解决"去哪儿找" —— 同一个坑换个入口又出现。

### 1.6 `RUN_WARN_GATE.sh` —— 漏检 2 个构建单元 + ICE 路径冒充通过

**(a) 覆盖面漏检（告警门禁的 `UNITS` 清单不含 `stub-loader.c` / `linker.c`）**

两者都是 `make` 真正编译、并随发行产出的组件，却整体不在门禁清单里。
实测 `stub-loader.c` 积累 **7 条告警**，含：

- **`-Wdangling-pointer`（真实 UB，活路径）**：`load_runtime()` 里
  `runtime_path` 指向块内局部数组 `path`，出块后 `dlopen`/`fprintf` 仍在用；
- `-Wformat-truncation` ×2、VLA 尺寸、未用变量等。

**这与门禁注释里描述的历史缺陷（`-fsyntax-only` 漏掉 3 条现存告警）是同一失效模式：
门禁的覆盖面本身没有判据。**

**(b) ICE 路径 `exit 0`**

`CHECKED` 在编译**前**自增（把未检查的单元也算进去），且 ICE 耗尽后仍
`✅ 零告警 / exit 0`。实测注入真告警 + 模拟 ICE：

```
① 正常：⚠️ bridge.c 2 条告警 ; ❌ 共 2 条 / rc=1
② 模拟 ICE：✅ 零告警（检查了 13 个编译单元）/ rc=0   ← 2 条告警凭空消失
```

**修为**：UNITS 补两项 + 加"覆盖面自检"（从 Makefile/BUILD_RUNTIME.sh 抽源文件列表
逐个核对，漏项即 `exit 1`）+ `CHECKED` 挪到编译成功后自增 + ICE 耗尽按 rc=2 上报。

**判别力已实测**：① 注入 2 条告警 → rc=1；② 模拟 ICE → rc=2 且"12 个已查、1 个未查"；
③ 从清单删一项 → `❌ 漏了构建里真实编译的源文件`。正常路径仍 `✅ 零告警（13 个单元）`。

**副产品**：修掉 `stub-loader.c` 后 `make` 输出**零告警**（此前有 8 条）。

### 1.7 `RUN_ALL.sh` —— 9 处裸 `if`：删掉测试脚本则该项**整体消失**

**症状**：删掉 4 个测试脚本后，汇总里那 4 行**凭空消失**（无 ⏭️、无提示），
`通过 13 / 失败 0 / ✅ 全部通过`。

**真因**：`if [ -f test/X.sh ]; then run_step ...; fi` 没有 `else`
→ 不调用 `run_step` → `run_step` 里"无命令则记 SKIP"的分支根本不执行
→ 三个计数器都不动 → 只看 `FAIL>0` 的汇总判为通过。

**修为**：给 21 个守卫块补 `else run_step "<同一名字>"`（走"无命令"分支记 SKIP）。
**实测**：删掉 4 个脚本后那 4 项**仍可见**（记 ⏭️ SKIP），不再消失。

### 1.8 `RUN_E2E.sh` —— 两个独立缺陷导致它**从未执行过**

**(a) `STAGE_MKDIR` 与 `STAGE_LOAD` 不是同一目录**

```sh
STAGE_MKDIR="${BXROOT_STAGE:-/tmp/bxroot-e2e-$$}"   # 带 $$
STAGE_LOAD="$ROOTFS/tmp/bxroot-e2e"                  # 固定名，不派生
```

两者永不相等 → 守卫必然失败 → 脚本**永远跑不到 exec**，且把自己造的 bug
打印成「创建 … 返回成功但 … 不存在（**proroot 双重翻译？**）」—— 把排查方向
引向了外层运行时（那里其实没问题：`/tmp` 与 `$ROOTFS/tmp` 实测同 inode）。

**修为**：`STAGE_LOAD` 由 `STAGE_MKDIR` 派生。

**(b) `RUN_ALL.sh` 的真机判据用容器视角路径**

`[ -d /data/data/com.dsh.client ]` 在干净真机容器里可能是假的 → `--e2e`
永远打印"跳过（需真机 rootfs）"。**更糟的是它会假真**：任何在 rootfs 内
产生 `data/data/com.dsh.client` 空目录的操作都会让它变 TRUE
（实测：把那个空壳移走，守卫立刻 TRUE→FALSE，而真 rootfs 一直都在）。

**修为**：改用宿主视角的 `$BXROOT_ROOTFS`。

**(c) 修完 (a)(b) 后立刻暴露第三个：`$DSH_JS` 传了宿主视角**

`DSH_JS` 是**给 guest node 的 argv**，node 会再翻译一次 → `ENOENT: lstat '/data'`。
实测对照（只改这一个参数）：

```
宿主视角 $ROOTFS/usr/local/lib/.../bin.js → ENOENT
容器视角 /usr/local/lib/.../bin.js        → 0.1.5-rc.2  ✅
```

**修为**：拆成 `DSH_JS_GUEST`（给 guest）与 `DSH_JS`（仅供脚本做存在性检查）。

**最终结果**：`端到端 dsh ✅ rc=0  0.1.5-rc.2` —— 该项**首次真正执行成功**。

### 1.9 `RUN_UPSTREAM_CLI.sh` —— 空断言：整体失效仍 35/35 PASS

**真因**："支持类"选项的判据是**否定式**的 —— 只看输出里**没有**
"未知选项/unknown option/unrecognized"就算"已识别"。实测：

```sh
# 一个"对任何输入都报错"的 launcher
int main(void){ printf("错误: 未实现\n"); return 1; }
$ sh test/RUN_UPSTREAM_CLI.sh
通过 35 / 失败 0   RESULT: PASS      ← 一个上游选项都不支持
```

即：它**抓不住"识别层整体失效"**（虽然确实能抓"漏掉某个别名"——
实测删掉 `-l` 别名可得 34/35 FAIL）。

**修为**：在逐选项对照**之前**加正向能力自检（launcher 必须能用上游语法
真跑通 `-r / -w / /bin/true`）。**实测**：不可用 launcher → `❌ 前置能力自检失败` rc=1；
真实 launcher → 仍 35/35 PASS。

### 1.10 文档错误：`bash` 脚本被教用 `sh` 调用

### P0-2. SIGSYS 裸 syscall 屏蔽绕过（→ rc=159）—— ✅ 已修（2026-09-19）

**影响**：guest 直接 `syscall(SYS_rt_sigprocmask, SIG_BLOCK, {SIGSYS})`
（Go 运行时风格）不被剔除，一旦被 seccomp TRAP 即整进程死。诊断成本极高。

**修复前状态**：`src/runtime/sigsys.c` 只挡 4 个 libc 符号
（`sigprocmask` / `pthread_sigmask` / `signal` / `sigaction`）；
`syscall_guard.c` 的裸 syscall 路径**不做任何剔除**。

**改动**（只动 `src/runtime/syscall_guard.c`）：

1. 新增判据 `sigsys_strip_raw(how, set, sigsetsize, out)`：
   只处理 `SIG_BLOCK` / `SIG_SETMASK`，清掉集合里的 SIGSYS 位，
   **改到本地副本**（不污染客户结构体）；`sigsetsize != 8` 时不动
   （那种调用内核自己会回 EINVAL）。判据抽成独立函数是为了可被源码级测试直接驱动。
2. 在 `syscall()` 里、`raw_syscall6` **之前**调用它（这是**入参**改写，
   方向与 statx / getdents64 的结果补丁相反）。

**★ 动手记录：第一版把参数下标写错了 ★**

`rt_sigprocmask` 的 ABI 是 `(how, set, oldset, sigsetsize)`：
`a0=how`、**`a1=set`**、`a2=oldset`（出参，客户常传 NULL）、`a3=sigsetsize`。
第一版写成了 `a2` 当集合指针 —— 于是条件恒假、**整段代码从未执行**，
而编译通过、符号导出、行为不变，探针原样报 `masked=1`。
裸系统调用没有类型检查，写错下标只会静默不生效。
（这正是它和 §1.3 里"源码-探针号一致性"同一类错误：**写错的值不会有任何提示**。）

**验证（三组对照 + 不误伤）**

| 场景 | 结果 |
|---|---|
| 无 bxroot（对照） | `masked=1`（未剔除） |
| 修复前 runtime（`d85b22c` 重编） | `masked=1` |
| 修复后 runtime | **`masked=0`**（已剔除）✅ |
| `SIG_BLOCK{SIGUSR1}` | 其它信号屏蔽照常生效 ✅ |
| `SIG_UNBLOCK{SIGSYS}` | 仍能解除（未被改坏）✅ |
| 调用后客户 `set` 结构体 | 仍含 SIGSYS（未被污染）✅ |
| `SIG_SETMASK{SIGSYS,SIGUSR2}` | SIGUSR2 生效、SIGSYS 被剔除 ✅ |

**回归钉（两层）**

- 源码级：`test/probe_raw_syscall.c` 新增组 6（13 条断言，判据直测 48 → 61）。
- 端到端：`test/test_id_syscall_guard.c` 新增"裸 syscall SIGSYS 剔除"一节
  （47 → 64 用例），用**内联 svc** 读回内核掩码 —— 因为本容器的 proroot
  会劫持 libc `sigprocmask` 造成假阴性。

判别力验证：漏掉 `how` 判定 → 两端各 1 处失败；原地改客户数据 → 1 处失败；
去掉 `sigsetsize` 门控 → 2 处失败；**把 `a1` 改回 `a2`（还原我犯过的错）→ 2 处失败**。

**顺带修掉一个既有缺陷：`RUN_ID_SYSCALL.sh` 是唯一没有 gcc ICE 重试的 runner**

实测该文件编译 40 次撞 2 次 ICE（`during GIMPLE pass: alias` 段错误）。
没有重试的后果不是"偶尔变红"，而是**该项被静默跳过**：编译失败走 `exit 2`，
`RUN_ALL` 按 rc=2 约定记成 ⏭️「环境不满足」—— 看起来一切正常，
实际那一轮这条契约没跑。**实测确实发生过一次**（全量回归里
`身份 syscall 伪装` 显示 ⏭️ rc=2）。

已给该 runner 补上与其余 runner 对齐的 ICE 重试（10 次 + 逐级降优化级）。
压测 30 次 **30/30 通过**（此前约 50% 会 rc=2）。

> 注：本轮往 `main()` 里加代码曾把该文件 ICE 率从 ~5% 推到 ~50%，
> 已把新增逻辑抽成独立函数缓解，但**根治靠的是重试** ——
> 因为 5% 的基线 ICE 本来就会让这项偶发 SKIP。

### P1-1. AF_UNIX DGRAM 不翻译（上游 #8 残留）

### P1-2. launcher 未设 `$PWD`（上游 #64）

**状态**：`grep -rn '"PWD"' src/` = **0 命中**。

**机制**（已用 bash 5.2.21 实测）：bash 的 `pwd` 内建只在 `$PWD` stat 后与 `.`
同 inode 时才回显 `$PWD`，否则回落 `getcwd`。`-b <host>:/test -w /test` 时 guest 的 `.`
就是宿主那个目录，launcher 又没覆盖 PWD → 继承宿主 `PWD` → `pwd` 回显宿主路径。

**修法**：launcher exec 前 `setenv("PWD", cfg.workdir, 1)`。

**未能端到端复现**：本容器 `mount --bind` 返回 ENOTSUP，无法构造真实 bind+cwd 场景。
机制已证，端到端**待真机**。

### P1-3. execve 失败诊断不足（上游 #402/#21）

`launcher.c:1464` 只有一行 `strerror(errno)`，缺上游式原因提示；
`proc.c:4239` 的 `execveat` 无 ENOSYS 回退。
**对照**：同族的 `fexecve`（`proc.c:4222`）**有** `/proc/self/fd/%d` 回退 ——
唯独 `execveat` 漏了。

### P2-1. kill-on-exit 孤儿进程（上游 #97 引申）

### P2-2. l2s 相对路径断链（本地复现，无上游同类）

**文档措辞不准确，需修正认知**：断链**只在非集中布局下成立**。实测两形态对照：

```

[集中布局] l2s_dir=<rootfs>/.l2s   → 落盘 target 是**绝对**路径 → 读得通（launcher 默认走这条）
```

即生产经 launcher 启动时**被偶然缓解**；但 `--link2symlink` 未开、直接经 bridge 跑、
或显式清空 `BXROOT_L2S_DIR` 时仍复现。成因是"相对形态落盘"，不是普适。

## 四、复核纪律（本轮踩到的坑，后续请沿用）

1. **判定"已修复"必须看代码，不能看文档**。本轮实测：9 项标"修复中"的全部没动；
   而有些文档声称的"已修"也需要 `grep` 复核。

2. **gate/测试的"覆盖面"本身要有判据**。本轮两处失效同型：
   告警门禁漏了 2 个编译单元（无判据发现）、`RUN_ALL` 漏项时整行消失（无判据发现）。
   已分别加自检。

3. **断言要有反向（负向）判据**。`RUN_UPSTREAM_CLI.sh` 的否定式判据让
   "完全不可用"得满分。凡是"输出里没有 X 就算通过"的写法都要警惕 ——
   它无法排除**探针恒真**。

4. **不要用 libc 符号观测自身状态**（§1.2）。本环境外层 proroot 会改写。

5. **路径视角问题（本项目最高频缺陷模式）**：判断标准是"**这个值由谁消费**"，
   不是"统一用某种视角"。已知需**宿主**视角：`--preload`、`--argv0`、
   `BXROOT_*` 环境变量、guest 可执行文件路径。已知需**容器**视角：
   guest 的 argv（脚本、目标文件）。

6. **并行 agent 会互相破坏**。本轮两次踩到：一个子代理的 `mkdir` 实验在 rootfs 内
   造出了 `data/data/com.dsh.client` 空壳目录（污染了 `RUN_ALL` 的真机判据，
   它声称已清理但实际没有）；固定路径 + 无条件 `rm -rf` 是协作陷阱。

7. **`rm -rf` 前先 `mv`**。本轮所有破坏性实验都用 `mv` 到 `/tmp` 或做在副本里，
   不直接删。
